## 二、主要变更

### 1. 排程核心：餐次跟随活动，不再切碎景区

**原来错在哪**：午餐时刻在景点排定**之前**就按固定默认值（12:00）算好了，
于是长时景区被午餐切成两段（例：西湖 240 分钟被切成 90 + 150），用户看到的是
"游玩被打断"；报表只给一句"偏紧"，不与用户协商。

**现在怎么做**：

- 景点**先连续排定**，餐次时刻随后由 `app/meal_flow.py` 解析：
  默认时刻 → 撞上景点则顺延到该段结束后 → 再退到段前 → 最后按 5 分钟步长就近找空档。
- 删除了"用午餐把景区切成两段"的分支，游览只出一段连续记录。
- 新增 `schedule.meal_inside`：游玩跨过饭点时，该餐**在游玩过程中**解决
  （只延长游程时段，**不缩短游玩时长**）。
- 两类餐次分别处理（用户确认的规则）：

  | 情况 | 处理 |
  | --- | --- |
  | 未指定餐厅（自行安排） | 折进游程内，不再单独出行 |
  | 已选定具体餐厅 | **必须单独出行**，让用户在计划书里看到那家店 |
  | 已选餐厅确实放不下 | **不静默改动用户的选择**，给出提醒 + 跳转入口 |

- 判定超窗用**游玩结束时刻**（此前误用开始时刻，导致该分支从不触发）。
- 早餐固定 08:00、40 分钟，09:00 开始游览；不按"用户起床时间"推断。
- 最晚到达住宿 23:30：越限先压缩可伸缩空档，仍越限则如实提醒，不默默排到次日。
- 午休按需：在景点与餐次排定之后找真正空着的时段，放不下可取消（可伸缩）。

### 2. 时间轴与计划书：住宿、退房、餐次要看得见

- **补回住宿行**：此前按"移除未确认入住时刻"的规则把住宿行整个删掉，时间轴上
  完全看不到住宿。改为如实呈现——每晚一行，`time` 留空，注明"入住时间以酒店确认为准"。
  （用户此前反对的是**伪造 22:00 入住时刻**，不是住宿本身。）
- **退房表述**：退房是"当天 12 点前的**截止要求**"，不是"12:00 去退房"这一项活动，
  因此不占具体时刻；换酒店当天退房固定在早餐前办妥并寄存行李。
- **返程链条改名**：原第一项按「发车 − 接驳准备 − 15 分钟」生成却命名为"退房与出发准备"，
  看起来像"16:24 才退房"。实际是"回住宿取寄存行李后出发"，已改名为
  「返回住宿取行李并出发」。
- 住宿/退房行抽成 `schedule.stay_rows`，**预览时间轴与计划书共用**，避免两处不一致。

### 3. 预算：从"只有住宿"到逐项汇总

**原来错在哪**：预算表里除住宿外全部显示"待核实"，但这几类里**多数数据其实都有**，
是被硬编码进了 unknown 列表。

**现在怎么做**（新增 `planning.fill_budget`）：

| 项目 | 计价方式 |
| --- | --- |
| 往返交通 | 单人席别票价 × 成人数（逐项明细） |
| 市内交通 | 按每条路线的实际方式：打车取 `taxi_cost`、公交取 `fare`，**每条路线只取一个，不双收** |
| 餐饮 | 按计划书里真实排出的餐次逐餐计价；已选餐厅用其参考人均，未选餐厅用本地参考人均中位数估算（标明是估算）；**只计成人** |
| 门票 | **成人票 × 成人数 + 儿童票 × 儿童数**；只认 `product_group=='admission'` 且在售的产品 |
| 住宿起价 | 沿用逐晚起价汇总 |
| 可确认小计 | 以上之和；**未取得资料的项不按零计入**，单独列为待核实 |

- 生成计划书时**自动查询已选景点的门票**（有额度保护：额度不足即停并如实说明；
  单点失败不打断计划书生成）。
- 计划书**展示时按当前代码重算预算**：修"代码已改、界面还显示旧条目"的问题
  （旧快照不随代码更新）。

## 三、为什么这么改（评审关注点）

本批改动几乎都源于**同一类缺陷**：**约束被写死在错的环节上**。

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 景区被午休/午餐切碎 | 餐次先于景点排定 | 先排事实（景点），再套约束（餐次） |
| 时间轴看不到住宿 | 为"防伪造时刻"把整行删了 | 如实呈现、不编造时刻 |
| 预算只有住宿一项 | 四类费用硬编码进 unknown | 有数据就算，没数据才列待核实 |
| 改了代码界面还显示旧的 | 计划书是快照、不随代码更新 | 展示时重算预算 |

另有一类缺陷是**判断条件的取值与实际数据对不上**（同型共 4 处）：

- `nights()` 只认 `selection_status=='confirmed'` 的抵达日，且不看 `outbound_date`
  → 填了去程日却不能选当天住宿；
- `time_policy.resolve_station` 定义了却**没有任何调用方** → 站点坐标永远为空，
  "赶早班靠近出发站"的既有逻辑从未生效；
- 市内交通只在 `mode=='taxi'` 读 `taxi_cost`，而高德返回的是 `'driving'`
  → 打车预估完全没算（¥70 漏计）；
- 门票计价未过滤 `product_group`，把演出票（¥10）、讲解包团（¥198）当成门票
  → 既可能低估也可能高估。

## 五、已知边界（**请重点评审**）

1. **门票为区间起价**：随日期与票种变化，文案已注明"需以购票页为准"，
   未当作已确认价格。
2. **餐饮估算**：未选餐厅的餐次按当地参考人均中位数估算（已排除酒店内餐厅与
   离群高价），属估算值，文案已标明。
3. **打车为预估**：来自路线接口的 `taxi_cost`，非实时叫车价。
4. **返程日"活动 → 回住宿 → 车站"的结构仍在**：当最后一个活动离车站比住宿更近时，
   理论上可省一趟折返；此前尝试过"最后一晚锚在景区与车站之间"的方案，
   因收益有限且影响面大已**撤回**（见 `revert(住宿)` 提交），留待后续。
5. **自动查门票会消耗途牛额度**（受 `TUNIU_DAILY_LIMIT` 限制），已有额度保护，
   但频繁重新生成会加速消耗。
6. **数据源限制**：门票价格、酒店退房时间等字段，平台未提供时一律列为待核实，
   **不编造数字**。
