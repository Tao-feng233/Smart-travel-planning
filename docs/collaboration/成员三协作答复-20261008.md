## 一、需要成员三确认的三项（先答复）

### 1. 日期字段：三级来源

**我接受 `user_explicit` / `shift_fact` / `system_suggestion` 这套命名**，并说明我这边现状与迁移动作：

| 级别 | 含义 | 我这边的现有位置 |
| --- | --- | --- |
| `user_explicit` | 用户在对话里明确给出的日期/时段 | `requirements.start_date`、`requirements.return_date`、`visit_requests[id].date/period` |
| `shift_fact` | 已确认班次带出的事实时刻 | `selected_transport` / `selected_return` 的 `departure`/`arrival`，且 `selection_status=='confirmed'` |
| `system_suggestion` | 模型或程序推算的建议 | `catalog[id].visit_suggestion.date/period`、`journey.return_date_status()` 的 `suggested` 结果 |

**需要你注意的一处不一致**：`foods.spot_intent()` 现在返回 `source: 'user' | 'suggestion' | None`，
与你的三级命名不同。我在本分支把它对齐为 `user_explicit` / `system_suggestion` / `None`，
你按三级名取值即可，不必兼容旧值。

**日期口径的三条硬规则**（已实现并有回归）：

1. 未确认的返程日期**不写入硬约束**，只作为 `suggested` 建议，并附依据说明。
2. `journey.return_date_confirmed()` 要求 `selection_status=='confirmed'`；推荐态不算确定。
3. 跨日时刻保留完整日期语义：`departure`/`arrival` 一律是 `YYYY-MM-DD HH:MM`，
   不传只有时刻的字符串；时区固定 Asia/Shanghai。

### 2. "班次标 recommended 不等于已确认"——同意，且已是实现

这条我完全同意，并且已经是本分支的行为，不是待办：

- `choices.py` 写入时按是否推荐打标：`selection_status = 'recommended' | 'confirmed'`。
- `journey.return_date_confirmed()`：只有 `confirmed` 才算确定；`recommended` 给出
  `suggested` 并写明"需用户确认后才是确定条件"。
- `plan['warnings']` 会带"推荐交通班次尚待用户确认"。
- `planning` 的时间口径按 `selected_return` 计算，但**状态标注**会因推荐态降为待核实。

**给你的接口约定**：判断班次是否可用作硬约束，请调
`journey.return_date_confirmed(w)`（去程同理由 `selection_status` 判断），
不要只看 `departure` 是否存在。

### 3. 规划阶段的输入输出与失效规则（你需要用它做阶段复用）

我已经把它落成代码，不再只是口头约定：

- `planning.stage_identity(w)` → 字符串身份（稳定、可比较、排序键固定）
- `planning.stage_reusable(w, stage)` → 身份一致且 `has_plan` 为真才为 `True`
- 生成的计划带 `plan['stage']`：

```python
plan['stage'] = {
    'action': 'plan',
    'identity': '<stage_identity(w) 的返回值>',
    'has_plan': True,
    'produces': 'plan',
    'depends_on': ['requirements','selected_spots','visit_requests','visit_order',
                   'meal_choices','hotel','selected_room','selected_transport','selected_return'],
    'created': '<计划生成时刻>',
}
```

**身份包含哪些内容**（任一项变化都失效，不需要你逐个比较）：

| 来源 | 具体字段 |
| --- | --- |
| `requirements` | city、origin、start_date、days、end_date、return_date、outbound_date、adults、children、child_ages、rooms、budget、pace、transport_mode、day_start、day_end、preferences、food_preferences、hard_constraints、local_trip |
| 选择 | selected_spots（排序后）、visit_requests（date/period）、visit_order |
| 餐次 | meal_choices（mode/food_id/binding/binding_method/bind_spot_id）、meal_mode |
| 住宿 | hotel（id 与 **location**）、selected_room.id |
| 班次 | selected_transport、selected_return（id、location、departure、arrival、**selection_status**） |

**两处刻意设计，请照此使用**：

1. **位置与时刻进身份，不只是 ID**。同 ID 换坐标（例如酒店重新定位）必须失效，
   否则会复用旧的时间口径——这正是复核报告 S3 指出的那类问题。
2. **`selection_status` 进身份**。班次从 `recommended` 改为 `confirmed` 会让身份变化，
   计划需要重排（时间口径不变，但状态标注与硬约束地位会变）。

**失效后必须重跑，不能做的三件事**：

- 不能把"重新运行整轮模型调用"称为断点恢复；
- 不能复用与新旅行条件不一致的旧阶段；
- 不能因为"测试全绿"就宣布阶段复用已验收（见第五节的容量口径待办）。

**注意一个副作用**：`generate()` 会写回 `w['time_policy']`。你在复用旧计划时，
必须把旧计划里的 `plan['time_policy']` 一并恢复到工作区，否则时间轴、餐次窗口与
容量会退回兜底值，出现"计划是旧的、口径是默认的"这种不一致。

## 六、项目测试轮 live_v8 失败的根因证据（请转给成员二）

项目测试轮记录：`live_v8`（真实 LLM 完整规划）失败，归因在
`app/visit_analysis.py` 的 `distribution_errors`（104–109 行）把"钉死时段容量"当硬校验。
我复核确认该归因成立，并已在应用侧修复（提交 `d68c8e4`）。证据如下。

**复现（精确到边界）**：一个景点钉在上午、模型给 240 分钟建议时长时

```
duration 180 → 错误数 0        # 恰好等于上午窗口，不误报
duration 181 → 错误数 1        # 超过即报
duration 240 → 错误数 1
```

当时的提示是"**保留指定安排并提示用户调整**"——模型既不能改用户指定的上午，
又必须保留下时长，两次修复都不可能满足，因此整轮失败。

**修复后的行为**（三种来源分开）：

| 情形 | 修复前 | 修复后 |
| --- | --- | --- |
| 用户明确指定时段且装不下 | 报错但无解，要求"保留指定安排" | 报错并给出可执行修法：保留用户指定的日期、把该活动时段改到当天其它可用时段，附带"需要 240 分钟 / 该时段只有约 180 分钟" |
| 用户只指定日期（时段是初稿） | 同样报错阻断 | 不阻断，只提示"时段建议而非硬约束，最终按当天实际可用时间安排" |
| 时段只是系统建议 | 同样报错阻断 | 不阻断，只提示 |

另外发现并修正一个筛选缺陷：原先只在 `visit_requests` 带 `period` 时才进入检查，
所以"用户只钉日期"的情况其实**完全没被检查**；现在按活动声明时段归组。

分析提示词也补了各时段可容纳时长（上午约 180 / 下午约 285 / 晚上约 300 分钟），
要求超过就标 `any` 或换时段，从源头避免模型自己超订时段。

**建议**：`live_v8` 脚本属组长，我没有改动脚本原件；请在重跑前同步本提交，
若仍失败请把失败阶段的原始输出发我，我按同一路径继续定位。

**后续更正（第二轮复核后）**：上面第 214 行那条修法本身是错的——让模型"把该活动时段改到
当天其它可用时段"与 `visit_schedule` 禁止修改用户时段的硬条件冲突。已在下一节更正。
