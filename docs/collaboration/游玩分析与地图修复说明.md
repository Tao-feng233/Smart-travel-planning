# 游玩分析与地图修复说明

日期：2026-10-08。基于整合分支9d38e09，未合入成员二、三待修订的分支。

## 游玩安排

新增`app/visit_analysis.py`。完成景点选择、修改指定安排或点击时间轴“优化分配”时，将全部已选景点、坐标、已知特色与营业资料、用户偏好、指定日期/顺序、往返交通及每日时间预算交给模型。模型返回每个地点的建议时长、日期、时段和原因，程序验证ID完整且不重复、日期范围、硬约束、容量及可避免的每日负担失衡。一次修订仍未通过时，保留用户选择，使用明确标注的估算分配；模型连接失败也不丢失选择。

未调用模型前的初步时间轴按地点类型、节奏和每天可用时间估算，不再统一90分钟或把候选推荐日期当固定安排。不是要求每天景点数量相等：大型景区可独占一天，其余日期安排多个短停留点。稀疏、紧凑及超容量提示依据估算分钟数，不能自动新增或删除景点。模型知识允许辅助建议玩法和时长，不用于编造开放、价格、客流或路况。

分析签名随日期、景点事实/选择、住宿位置、班次和用户指定安排变化而失效。时间轴、周边餐厅参照和默认门票游玩日期共用同一预分配。正式规划获得同样的预算和建议，提案做负担校验并支持半天/全天时长，再查询真实路段；20分钟转场以及现有抵达/返程接驳预留仍是估算，不能解释成实际交通耗时。

成员三后续接入统一时间策略时，优先替换`budgets()`、`schedule.windows()`及初步估算来源，保留建议与运营事实的区分、输入签名、硬约束校验、一次修订和失效语义。不要恢复两份互不联动的餐饮参照与景点分配。当前尚未实现已选餐次随景点排期自动迁移，已有日期固定餐次仍由正式计划核对，不静默挪动。
