# 规划警告处理与地图优化建议

日期：2026-10-08。本次已修改规划警告流程；地图仅做现状分析与方案设计，没有改动地图实现。

验证：完整服务端回归 **221 passed**；浏览器验证警告确认、取消保留、确认后发布，以及历史、地图和票务界面均通过。新增场景使用隔离数据库及合成数据，不代表真实供应商全链路验收。

## 一、提前抵达日与三天游玩

游玩日期由 `requirements.start_date + days` 决定。若12日开始、游玩3天，游玩范围是12—14日；11日抵达会进入完整旅途日期，可安排交通、入住和休息，但不参与这三天的景点负担比较，不要求增加一天景点。

已复现的实际缺陷是：程序将“可进一步均衡建议分钟数”的启发式判断作为生成失败条件。三天都有景点也能触发，而且旧文案笼统说“其他日期有时间”，没有说清是在比较同一游玩范围内的负担。不能把这种提示理解为系统要求填满所有空白日期。

## 二、已经修改的行为

- 结构和身份错误继续校验：模型输出未知、重复、遗漏的景点，日期越界或违反明确指定日期等，不会被“继续生成”放行。
- 估算容量偏紧、建议负担不均先交模型尝试改善一次；仍存在提醒时保留有效提案，继续核对路线并准备草稿，向用户显示具体日期和估算分钟数。
- 用户可选择“继续生成带警告的草稿”或“返回调整”。确认前保留当前选择和原计划；确认后发布已准备的草稿，并将提醒写入计划书，避免重复整轮模型调用。
- 确认绑定当前旅行及已选内容，15分钟有效，条件变化后需重新生成。取消不清空选择，不覆盖原计划。
- 明确的抵达、返程、指定时段或路线衔接冲突仍单独说明并提供修改入口。继续一个估算提醒不等于授权忽略新的班次冲突，也不代表所有安排已确认可执行。

## 三、地图现状

当前是高德静态底图加前端 Canvas 的标记与折线。路线由服务端逐段比较步行、公交、驾车；有道路几何时显示实际查询折线，无几何时显示顺序示意。已经具备拖动、缩放、重置、浮窗和当前地点高亮。

现有局限：

1. 未选择日期时，将多天路段统一铺到地图上，容易混淆当天路线与全部路线。
2. 折线展示没有完整保留路段的起终点身份、顺序、交通方式及状态，点击路线时缺少可读说明。
3. 景点点位可能是景区中心，算路使用入口，缺少标注时看起来像路线没接到图钉。
4. 排序先由模型与位置建议给出，再逐段核对，尚未用真实路程持续优化整日顺序。
5. 手势后需要获取新的静态底图，缓存按中心点和缩放区分，拖动到新区域仍有加载延迟。

## 四、建议的优化顺序

### 第一步：规范路线数据与显示

统一保存每段路线的起点、终点、日期、顺序、方式、耗时、距离、折线、来源、查询时间和核实状态。默认显示当前日，其它日可切换；全程视图按天区分，当前路段加粗，其它路段淡化。增加方向箭头与点击详情，示意线保持虚线，查询失败和待核实分别标注。

景区位置与实际入口分别标注；已确认的车站或机场端点纳入路线。反复返回同一地点保留访问顺序，不能因为标记去重就让往返过程消失。

### 第二步：让地图与时间轴联动

点击景点或饭点只高亮相关路段与地点，自动适配该段路线的范围；已选其它地点仍显示。主地图、浮动小地图和详情地图消费同一份数据，按旅行隔离。摄像机状态尽量保留，不因普通消息刷新而重建地图或跳回中心。

### 第三步：改进实际顺序

模型负责初始区域分组、玩法与时间偏好，程序用真实道路耗时在可移动活动之间做局部顺序优化。固定日期、时段、餐次和班次不自动改动。优化结果比较总接驳分钟数、折返、步行负担及冲突，不将直线距离当成通行时间。

先查询少量相关候选路段、缓存已有结果，再做邻近交换或2-opt等局部改善；不要一上来对所有点、所有交通方式做完整平方数量的查询。受影响的日期局部重算，保持供应商并发与调用量受控；不承诺全局最优或未来实时路况。

### 第四步：地图底层换成高德 JS SDK

主地图优先使用 SDK 的地图、标记和折线能力，浮窗和详情按需创建、复用状态；既有静态地图保留为加载失败时的降级。SDK处理底图和覆盖物显示，服务端继续保存路线与计划，避免前端另算一份路线导致计划书不一致。

高德官方文档提供了[标记与折线覆盖物](https://lbs.amap.com/api/javascript-api-v2/getting-started)及[路线绘制](https://lbs.amap.com/api/javascript-api-v2/tutorails/car-dir)能力。正式接入需核对Web端JS API类型Key及安全配置，当前Web服务Key不能直接视为已满足要求。路线数据仍可使用现有后端调用；高德[路径规划2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)支持多种交通方式，但整日业务约束优化仍需由项目自身实现。

本方案可分阶段推进，优先解决显示混乱与数据一致性，再改算法和地图底层，不需要一次重写整个规划模块。
