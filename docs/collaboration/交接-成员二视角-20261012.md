## 3. 项目是什么（一句话 + 一条边界）

**一句话**：面向自由行用户的交互式旅行规划 Agent——自然语言 + 可视化工作台完成
需求收集 → 景点 → 住宿 → 往返交通 → 餐饮 → 地图 → 计划书，并支持局部修改与版本留存。

**一条边界（最重要）**：**不做订票、不做下单、不做支付。**

### 3.1 为什么这是设计选择，不是没做完（5 处硬证据）

| 证据 | 位置 | 原文/含义 |
|---|---|---|
| 契约级声明 | `app/travel/choices.py:1` | docstring：`Selections use provider-backed snapshots; no booking operations.` |
| 安全隔离 | `app/integrations/enrichment.py:63-73` | 字段白名单主动把 `payment` / `prebook` / `token` / `password` / `secret` 挡在快照外 |
| 反编造规则 | `app/travel/price_hints.py:1` | docstring：`an unknown or zero POI cost is not free admission` |
| 代选提示 | `app/agents/auto_selection.py:179` | "车票、机票由你手动确认；此操作只用于规划，不进行预订" |
| 界面声明 | `frontend/index.html:255` | "选择用于行程规划，不代表预订成功。查询信息保留来源与时间" |

**口径铁律**：说成"我们明确不做订票，并用代码强制它"，**不要说成"还没做订票"**。
前者是设计判断，后者是欠债——老师批的正是后者。

### 3.2 OTA 的真实订票链路（行业通用流程，非本项目实测）

库存直连（航司/铁路/酒店 PMS 或 GDS 分销）→ 查询 → 预占锁位 → 出行人 → 支付 →
出票/确认 → 订单管理，外加退改签规则引擎、资金对账、履约客服。
**需要票务代理资质与支付合规**——不是技术问题，是牌照问题。我们客观做不了，也不该做。

## 7. 商业化改造方案（2026-10-12 产出）

顺序铁律：**先算账 → 拆约束 → 才谈功能。绝不先加功能。**

| 步 | 动作 | 成本 | 补哪个洞 |
|---|---|---|---|
| 0 | 调 `usage_summary()` 跑一次完整规划，算出单次 LLM 调用数与 token | **1 小时，零改造** | "没算过成本" |
| 1 | 拆三道硬约束：数据源配额 / 账号留存 / 单进程+SQLite | 见下 | "没有合理化" |

| 4 | 成本结构优化（分级调用、骨架缓存） | 拿到第 0 步数字后才做 | — |

**三道硬约束**

| 约束 | 现状 | 改造 |

## 8. 造亮点：公式与三条路径

> **亮点 = 你做到了 + 别家没做到 + 能用一个数字或一次演示证明**

三条缺一，讲出来就还是"技术堆叠"。

**已有三个真亮点，只是被归错了类**（原在"局限性"章节）：
未知不写成零 / 坐标核验门 / 事实·建议·未知三档。它们缺的是**第三条：数字与演示**。

| 路径 | 做什么 | 成本 | 强度 |
|---|---|---|---|
| **1. 核验覆盖率（首推）** | 每份行程显示：N 项事实，X 已核实、Y 待核实，**覆盖率 X/N** | 半天 | ★★★★★ |
| 2. 对比演示 | 同一需求，通用 AI vs 识途，逐条核差异 | 半天 | ★★★★★ |
| 3. 路线顺序优化 | 带时间窗的最近邻 + 2-opt，量化"省了多少路上时间" | 2–3 天 | ★★★★ |

**路径 1 是最强且几乎不用改代码的**：`price_hints.py` 已在给每个事实打 `basis` 分档，
只需聚合一层，在行程头部显示。这个数字**别家根本没有，因为别家压根不区分**。
有了它，被问"亮点是什么"只需指一个数字。

## 10. 工作规矩红线（最高优先级）

1. **Git 提交/推送必须逐次授权**。用户没说「commit / 提交 / 推送」之前，只做只读操作

2. **删除文件必须精确到单个文件**：删前报告路径、确认唯一命中、做备份、删后复核 diff。

7. 不主动更新展示稿/手册/共享文档。
