# 成员三任务说明

## 目标与开发基线

负责推荐与行程规划升级，建立统一时间引擎、动态时长、路线与餐次联动、局部重排和可信预算。重点解决当前固定占位时间、不同阶段规则不一致和调整后安排失联的问题，不扩展为支付出票或全局最优求解。

源码基线为 `Tao-feng233/Smart-travel-planning` 的 `feat/shitu-v11-review-integration`，已完成代码提交 `40374bc590bedefd78e03b759f61d7c9b1ddeb82`。该版本包含酒店位置恢复和通行预检查，基线148条后端测试。本文为待开发工作说明，不代表动态时间引擎已实现。

从包含本说明的最新整合分支创建工作分支，建议 `feat/shitu-v12-planning`。路径相对于仓库根目录；不从旧main或体验ZIP开始。

## 职责与对接边界

| 能力 | 本人负责 | 输入来自谁 |
| --- | --- | --- |
| 候选推荐 | 偏好、时间、距离匹配，推荐理由和时段建议 | 协调者提供地点事实与RAG资料 |
| 时间与排程 | 建立可用窗口、时长建议、冲突检查和顺序调整 | 成员二提供明确日期、状态与任务上下文 |
| 路线与餐次 | 选择交通方案、决定餐饮参照点、核对衔接 | 协调者提供真实地点与路线结果 |
| 计划审核与评测 | 验证ID、日期、遗漏、依据和调整结果 | 与两人的接口、状态和数据共同联调 |

主要负责 `app/planning.py`、`app/proposals.py`、`app/schedule.py`、`app/access.py`、`app/visits.py`及新增时间模块；`foods.py`的餐次、`choices.py`的规则、`agent.py`的推荐部分为共享边界，拆成小范围提交。协调者负责foods中的供应商查询，成员二负责Agent动作和状态保存。

不在本分支替换MySQL、MCP或向量库，不重新写地图底图和日期文本解析。通过统一接口使用数据，提供计划顺序、事件和道路几何给成员二展示。

## 第一批 统一时间契约与基础引擎

先与成员二确认时间字段与任务回调，提交一个较小契约PR。建议新建 `app/time_policy.py` 或等价模块，集中时间计算；现有schedule、meal_guard、access、proposals和planning均调用它，不能只改最终生成提示词。

建议能力如下，方法名可调整但语义需稳定：

| 能力 | 输入与输出约定 |
| --- | --- |
| 构建时间配置 | 旅行需求、明确意图、班次、地点事实；区分确定、建议和未知 |
| 计算当天可用时间 | 输出完整datetime开始/结束、边界依据及待核实事项 |
| 建议活动时长 | 输出最小/建议/较宽松时长、依据和可调整状态 |
| 校验或构建日程 | 输出事件、路段、冲突及受影响选择，不直接写数据库 |
| 局部重排 | 输入原计划与变化，输出新版事件及变化说明，保存交给业务层 |

时长单位统一为分钟；日期时刻包含时区并采用Asia/Shanghai。事件区间建议按左闭右开解释，结束时刻等于下一项开始不算重叠。计划保留schema_version，旧计划可读；新字段只在定义后由共同契约模块引用，不复制两份模型。

成员二牵头公共契约的存储和任务定义，本人提供TimeProfile与时长结构，协调者合并统一版本。统一定义通过前，可以用对应测试夹具开发计算逻辑，不依赖对方尚未完成的MySQL服务。

建议时长结果示例（只是拟定接口）：

```json
{
  "minimum_minutes": 60,
  "suggested_minutes": 120,
  "relaxed_minutes": 180,
  "basis": "来源建议与用户深度游偏好",
  "evidence_ids": ["document-id"],
  "status": "estimated"
}
```

实际数值需根据当前地点与资料生成，不将示例值写成新默认。缺少资料可给可调整估计，但必须标estimated，不能改写成接口事实。

## 第二批 动态时间与整体衔接

### 时间判断

明确班次、预约、用户指定日期和时段是硬条件。营业资料是带适用范围的事实；每日起止、休息、用餐和游玩时长是可调整建议。用户未明确返程日期时，不直接固定为游玩结束次日；向业务层返回待确认建议，由成员二保存来源与确认状态。

首日最早活动时间根据班次预计到达、出站或取行李估计、到首站路线、入住/寄存需求计算。末日最晚离开末站时间等于返程出发减去到车站/机场路线、已核实候车/值机要求与机动。

不再统一加90分钟或减120分钟。暂缺站点坐标、接驳或承运规则时，输出带依据的可调整准备估计或待核实状态，不将未知当零、不根据模型猜测声称已核实。协调者负责车站、机场和酒店实体定位；本人负责时间拼接。

内部使用完整datetime处理跨午夜，不将次日事件切成23:59，也不按旅行天数强行填满空白返程日。用户给出的旅游日期范围是允许范围，是否有足够可游玩时间另行核算。

### 活动与餐次

游玩时长结合地点规模、资料建议、快逛/深度游、老人儿童和用户明确时长，允许用户调整；不继续每个景点固定90分钟或统一限制在30至240分钟。主景区与内部子景点避免重复计算全套时长。

用餐窗口优先采用用户习惯，未明确时提供可修改默认；实际开始依据上一事件结束、路线和餐厅营业资料计算。临时时间轴标估计，正式计划标已核对部分，但两者共用同一时长来源和时间引擎。

当数据明确不足时给具体冲突，不为了塞入全部选择压缩至不合理时长。提供减少地点、改日期或班次等可操作建议，不能静默删除选择。

## 第三批 推荐 联动与局部重排

### 路线顺序与餐饮绑定

使用已查询道路耗时比较可行顺序，以减少折返、满足开放与预约、符合用户体力和时段为目标。可以先实现区域分组、最近可行点与有限顺序比较；不承诺全局最优。用户明确顺序优先，无法满足时解释。

同一区域、重复或父子景点在候选推荐时合理归组，记录推荐时段与依据。餐饮按实际或暂定日程对应的附近区域查询；不要把直线距离作为道路时间，也不将“没有公交”认定为所有方式不通。

新增两种餐次语义：固定日期餐次保持用户指定；明确跟随某景点的餐次保存anchor_id和绑定方式。景点改期时，计算该餐次的受影响状态，提示需要调整或重新查餐厅；没有明确绑定的旧餐次不自动挪期。

### 局部更新

更换餐厅重算相邻路段及后续可变事件；返程变化优先更新末日；景点改期重算受影响日期与绑定餐次。局部调整跨过日期容量边界时，可扩大影响范围，但必须说明原因。

输出新计划与变更清单，业务层使用expected_revision保存。旧任务不能覆盖新选择，模型不重新选择未经用户确认的酒店、车次或餐厅。与成员二的阶段任务接口配合，已有效的查询与提案可复用。

### 预算

分别显示已核实金额、估计范围和未知项。依据所选房型、报价覆盖、入住退房与房间数计算住宿，确认单价口径后再相乘；往返交通按席别及已知人群规则计算，儿童规则未知时不套成人价格。

门票区间最低价不当作指定日期金额；餐厅人均只形成估计；缺少费用不记零。总预算和人均预算歧义由Agent询问，本人计算已明确口径。超预算指出主要费用及可调整选择，不补造价格。

## 验收条件

| 场景 | 预期 |
| --- | --- |
| 相同16:00返程，末站到车站20分钟或80分钟 | 活动截止随路线变化，不能都减固定120分钟 |
| 高铁与航班 | 准备依据、待核实状态有区别，不套同一固定值 |
| 晚到/跨午夜/早班返程 | 完整日期时刻正确，无虚构游玩或强制早餐 |
| 大型景区与短时参观点 | 建议时长有区别，依据和调整方式可查看 |
| 时间轴、选餐、预检查与生成 | 同一输入使用统一时间结果，不在前后阶段相互矛盾 |
| 固定餐次与跟随餐次 | 固定不挪期，明确绑定可提示联动；旧记录不误改 |
| 改餐厅与改返程 | 保留其他有效选择，仅更新受影响范围并解释 |
| 无方案、超时与缺坐标 | 分别处理，不把未知当无法通行或零耗时 |
| 报价与预算 | 起价、确认口径、估计与未知分开，单价和总额不混用 |

用合成数据建立确定性时间/约束测试；再用小批真实路线核对接口假设。模型建议需单独评估相关性、候选完整、硬约束满足、引用和修改结果。已有148条测试的场景要保留，旧固定值断言应改为业务语义，不直接删除。

## 如何与协调者通过GitHub对接

分公共契约、统一时间、联动/局部重排三个批次提交。创建目标为 `feat/shitu-v11-review-integration` 的PR或提供明确compare链接，不直接推main或整合分支。

PR写明基线、变化、需要的数据字段、调用方法、验收样例、已知边界和对旧记录的处理。需要新字段或工具时，向协调者提出明确的“输入/输出/来源/未知状态”，不在规划分支另接供应商或直接实现向量检索。

负责人将PR链接贴到当前Codex会话，协调者审查、运行场景并整合。公共接口合并后先同步；成员二返回的时间/状态字段变更需共同确认。共享文件按职责范围修改，文件整体重写前在PR说明受影响调用。

本期必须成套替换的是统一时间规则：不能只改planning，而让schedule、foods和access继续使用旧固定窗口。其他功能可分批接入，在同一工作分支保持可检查的独立提交。
