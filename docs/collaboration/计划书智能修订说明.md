# 计划书智能修订更新说明

日期：2026-10-08。本文说明本次整合的应用功能与验证范围。

## 原问题

“帮我优化一下”可能只触发景点分配分析，没有重写计划书；进入新任务时，加载状态又覆盖了上一轮的具体冲突。模型缺少原计划及失败条件，容易重复输出同一方案。长时间连续游览还可能越过午餐时段，导致已选午餐未进入日程。

## 当前行为

1. 已有计划书或规划冲突时，可以在对话中要求优化，或点击计划页的“智能修订”和错误说明中的“自动修订计划书”。
2. 模型会接收本轮要求、原计划、全部已选景点与位置、住宿及房型、逐餐选择、往返交通、票务和天气快照、官方资料、已有路线耗时及具体冲突。
3. 模型可以调整灵活日期、顺序、建议时段、游览范围、建议时长和玩法说明。时长是建议估计，允许按合理游览范围调整并解释取舍，不能压缩成明显不合理的打卡时间。
4. 用户明确指定的日期、时段、顺序，以及已选景点、住宿、餐厅和车票均保留。泛泛要求优化不会应用模型自行推断的新旅行日期或天数。更换选择仍走已有确认流程。
5. 修订会重新核对路线及时间，并检查全部景点、已选餐次是否保留。长景区游览支持午餐前后两段，总游玩分钟数不变；餐厅往返耗时另计，二次入园条件仍提示待核实。
6. 通过检查后更新计划并说明变化；失败或停止不会覆盖原计划。失败仍显示具体冲突和修改入口，不无限重试。
7. 用户明确修改景点日期或顺序时，保存该要求后也会联动修订已有计划书，而不是只改变临时时间轴。

## 验证与边界

- 本地完整回归：**214 passed**。
- 浏览器合成场景通过：授权弹窗、取消保留、具体错误跳转、点击自动修订后更新计划书；历史列表、地图和票务界面回归同样通过。
- 回归覆盖上一轮冲突跨任务传递、泛优化不改旅行日期、失败保留旧计划、明确改期联动、长景区的已选午餐及继续游览。
- 本次流程验证使用隔离数据库、合成候选和受控模型响应，不能称为真实供应商全链路验收。建议时间和计划核对不代表票价、库存、开放或入园已确认。
- 未改动真实用户旅行、根目录 `.env` 或真实 MySQL 数据。使用更新需重启本地服务并刷新页面。
