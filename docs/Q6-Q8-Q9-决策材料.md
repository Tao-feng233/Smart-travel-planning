## Q6 追问结构化

### 实测事实

1. **前端不解析任何文本**。`assistant_message` 只有一处去处：
   `frontend/src/stores/session.ts:291` → 直接推进聊天气泡。
   全仓库没有任何按「数字+点」拆行的代码（grep `assistant_message` 前端仅 2 处命中：这里 + 类型定义）。

2. **结构化通道已经存在**，走的是统一信封的 warning：
   - 后端 `services/reply_builder.py:188-196` 产出
     `WarningItem{code:"MISSING_PROFILE_FIELDS", details:{字段名: 字段名}}`；
   - 前端 `utils/clarification.ts:82-92` 的 `extractMissingFields()` 取 `details` 的 **key**，
     并显式注明「不要依赖 value 的语义」；
   - 追问卡 `ClarificationCard.vue` 拿到的 `props.fields` 就是这个数组。

   所以「要么加 `questions` 字段，要么冻结文案」这个二选一的前提不成立——
   前端早就不靠文案吃饭了，它靠的是 `details` 的 key。

3. **真正的脆弱点是文案双份，而且已经漂移**：

   | 字段 | 后端 `services/missing_fields.py:_TEXT` | 前端 `utils/clarification.ts:META` |
   |---|---|---|
   | start_date | 大概哪天出发？（例如：10月2号） | 大概哪天出发？ |
   | end_date | 哪天回来？（例如：10月6号；也可以直接说玩几天） | 哪天回来？ |
   | budget | 这趟旅行总预算大概多少？（例如：5000 元） | 这趟旅行总预算大概多少？ |

   前端源码注释写着「与后端 `build_questions()` 的追问文案保持一致」——
   **5 个字段里已有 3 个不一致**。同一屏里聊天气泡和追问卡会用两套措辞。

4. 兜底行为：后端加了前端不认识的字段时，前端会渲染出「请补充 start_date」这种**英文字段名**（`clarification.ts:68-70`）。

### 选项与代价

| 方案 | 内容 | 代价 | 收益 |
|---|---|---|---|
| **A** | `SendMessageData` 新增 `questions: ClarificationQuestion[]`（field / question / label / kind） | 契约 + 模型 + fixture + B 改前端渲染；B 需再动一次追问卡 | 文案单一来源，前端删掉 META 副本；未知字段不再露英文 |
| **B（建议）** | 不改 `SendMessageData`。改为**把 `WarningItem.details` 的结构写进契约**（即顺手关掉 Q2），明确 `MISSING_PROFILE_FIELDS.details = {字段名: 追问文案}` | 改的是 Q2 那处定义，不加字段；前端可选用 value 当文案 | 现在这条隐式通道变成合法契约；改动量最小 |
| **C** | 「文案冻结」：把 `build_questions()` 输出冻结为用户可见文案，写进契约 | 零代码改动 | **实际保护不了什么**——文本没人解析，而真正的双份文案在前端 META 里；冻结后端文案反而固定了漂移 |

### 建议

**选 B**：把 `details` 定型（顺带关闭 Q2），并**正式声明 `assistant_message` 只面向人、永不被程序解析**。
若三人更看重「文案只有一份」，就选 A——但要接受 B 再改一次前端。
无论选哪个，**「文案冻结」都不能替代 B**，因为冻结的是没人读的那一份。

拍板后改动清单（B 方案）：
```text

backend/app/schemas/v04/rest.py   WarningItem.details 收紧类型
frontend/src/utils/clarification.ts  注释订正（去掉"与后端保持一致"的错误声明），或改为读 value
handoff/B_待办总表.md Q6 描述订正
```

## Q8 候选卡片中文名

### 实测事实

1. **确实只能显示 ID**：`frontend/src/components/ChatPanel.vue:100` 渲染 `{{ candidate.destination_id }}` → 用户看到 `dest_chengdu`。
2. **契约确实没有名字**：`backend/app/schemas/v04/recommendation.py` 只有
   `destination_id / readiness_id / suggested_days / suitable / reason / tradeoffs / risk_flags / evidence_ids`，
   `CONTRACTS.md` §6 同样没有 name。
3. **中文名后端早就有，而且已经在用了**：
   - `services/v04_mock_provider.py:135` `destination_name()` / `:140` `known_destinations()`；
   - `api/deps.py:46` 把 `known_destinations()` 装进 `NodeDeps`；
   - `graph/nodes.py:613-614` 用它填攻略的 `destination_names`；
   - `services/reply_builder.py:100` 用它写聊天文本。
   **结果是一屏之内不一致**：聊天气泡说「成都」，旁边的卡片写 `dest_chengdu`。
4. **「攻略里已有 `trip_summary.destination_names` 可先兜」——不成立**。
   `trip_summary` 只在攻略里（`guide/composer.py:449-464`），而攻略的产生顺序是
   `确认目的地 → 排程 → 验证 → compose_guide`（`graph/nodes.py` / `guide_service.py`）。
   候选卡片出现在 `RECOMMENDING / AWAITING_DESTINATION_CONFIRMATION` 阶段，
   **此时 `guide` 还是 null**，前端 `store.guide` 取不到任何 `trip_summary`。
   兜底方案只在 GuideView 里成立，救不了 ChatPanel 的卡片。
5. 前端也没有自己的中文名表（`utils/labels.ts` 里没有目的地映射），符合「前端不编事实性内容」的约定。

### 选项与代价

| 方案 | 内容 | 代价 |
|---|---|---|
| **A（建议）** | `DestinationRecommendation` 加可选 `name: str \| None`，由 **Provider**（它才持有目的地资料）在 `search_planning_ready_destinations` 里填 | 契约 §6 + 模型 + fixture；Provider 补一个字段；前端 1 行（`candidate.name ?? candidate.destination_id`），**不加字段也不会崩** |
| B | 不改契约，前端再调一次 MCP 工具取名字 | 前端多一次调用、多一条与 `planning_ready` 无关的依赖；且 MCP 工具面向 Agent 而非 REST 客户端 |
| C | 前端用 `known_destinations` 的副本（前端硬编码中文名） | 违反「前端不产生事实性内容」，且三处数据源 |

### 建议

**选 A**，并且顺手明确**名字的权威来源**：
现在 `api/deps.py:46` 直接 `import` mock provider 的 `known_destinations()`——
这等于把「目的地名从哪来」绑在了 Mock 实现上。A 换真实 Provider 后，这个映射必须跟着搬到 Provider 接口后面，
否则 Q8 加完字段反而拿不到名字。建议把「目的地中文名」列为 Provider 契约的一部分（例如目的地画像的一部分），
`deps` 只从 Provider 取。

拍板后改动清单：

## Q9 数据覆盖门槛

### 实测结果（当前 main，实跑 Provider）

```
天数   required = 天数×2+1   planning_ready
2天         5               True
3天         7               True
4天         9               True
5天        11               True      ← 恰好卡在等号上
6天        13               False     failed = [VISIT_PLACE_COVERAGE]
7天        15               False
8天        17               False

真实 VISIT_PLACE 候选数 = 11 | 硬编码常量 = 11      ← 两者当前一致
推荐（3天行程）= [('dest_chengdu', 3)]
推荐（5天行程）= [('dest_chengdu', 3)]              ← 注意
```

### 与台账的差异（重要）

- 台账（`docs/contract-open-questions.md` Q9、`PROGRESS_REPORT.md`）写的是
  「成都 12 / 乐山 6 / 都江堰 2，Provider 实际返回 3 / 0 / 0」。
- 实测：A 补数据后 `visit_place_count` 已改成 **11 / 0 / 0**，Provider 真实返回 **11 / 0 / 0**——**常量与数据当前是一致的**。
- 而且 A 加了守护测试：`backend/tests/test_v04_mock_provider.py:84`
  `assert DESTINATIONS["dest_chengdu"]["visit_place_count"] == len(resources)`。
  所以「常量没人能核对」这条**对成都已经不成立**了。

### 仍然成立的三个真问题

1. **常量重复，且只守了成都**。`RESOURCE_META` 里已经有真实候选，`DESTINATIONS` 里又抄一份计数。
   测试只断言了成都（11），**乐山 / 都江堰的 0 没有任何断言**——
   A 明天给乐山补 3 个地点，`readiness_evaluation` 仍会判它不可规划，而且没有测试会响。
   建议：计数从 `RESOURCE_META` 推导（或至少在 Provider 里算一次、元数据不再存计数），
   并把断言扩到全部目的地。
2. **`suggested_days` 用了同一个常量，公式偏保守**（本轮新发现）：
   `v04_mock_provider.py:1128` `suggested_days = min(duration_days, max(1, visit_place_count // 3))`
   → 11 // 3 = 3，所以**5 天行程的推荐卡片仍显示「建议 3 天」**，
   而同一份元数据里 `recommended_max_days = 5` 明明写着 5 天。
   这个数字直接渲染在候选卡上（`ChatPanel.vue:103`），用户会看到「我要 5 天，系统建议 3 天」。
   建议改用元数据里的 `recommended_min_days / recommended_max_days` 夹逼 `duration_days`。
3. **`failed_requirements` 命名不齐**：访问计数写 `VISIT_PLACE_COVERAGE`，
   其余写 `OPENING_RULE_COVERAGE / ROUTE_COVERAGE / LODGING_COVERAGE`，
   而 `required_capabilities` 里又是 `VISIT_PLACE`。写进契约时统一一下。

### 对门槛本身的判断（复核后没变）

`每天 2 个地点 + 1 个替代` **不建议现在改**：
- 它衡量的是「数据够不够支撑这么长的行程」，成都恰好 11 个候选、5 天正好打平、6 天不够，是**数据量**问题，不是算式问题；
- 真实目的地上线后候选数是几十量级，这条线基本不会碰到；
- 现有备选 `ceil(天数 × 1.5) + 1`（5 天→9、6 天→10）可以用，但应该**等第 1、2 条修完再评估**，
  否则又是在有缺陷的输入上讨论参数。

拍板后改动清单：
```text

backend/tests/test_v04_mock_provider.py    断言扩到全部目的地
CONTRACTS.md §3.2                          ruleset_version + 门槛公式写进契约（若决定改公式）
```
