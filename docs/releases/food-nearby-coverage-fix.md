# 景点周边餐饮「0 候选」修复

## 现场

体验者在「洛阳 · 龙门石窟 / 2026-10-08 / 7 天」的工作区里，餐饮步骤出现：

- `2026-10-08 午餐 · 龙门石窟 · 周边5公里 · 0家候选`
- 该餐已选「真不同饭店」，但下方无候选、按钮只有「本餐自行安排」与「完成餐饮安排，继续」
- 反馈原话：**"你不能人家就是在这旅游完啥都选不了吧"**

## 成员提供的原始复现记录

`app/foods.py` 在没有餐饮偏好时用默认词 **「当地餐厅」** 搜高德。这是给模型看的意图词，
不是真实地点名称，高德按名称检索时在景区周边经常返回 0 条。以下数量来自成员的原始接口测试，不是本次整合的新查询结果：

| 查询 | 结果 |
|---|---|
| 龙门石窟周边 5km + `当地餐厅` | **0 条** |
| 龙门石窟周边 5km + `美食` | 12 条 |
| 龙门石窟周边 5km + `洛阳水席` | 11 条 |
| 城市范围 + `当地餐厅` | 11 条 |

第二处是 UI 死结：该餐已有选择，但没有任何「只取消这一餐」的入口——
`本餐自行安排` 会清掉该餐选择、`全部用餐自行安排` 会清掉全部，用户没有别的出路。

## 改动

1. **`app/foods.py` 关键词兜底**：默认泛指词（当地餐厅/餐厅/本地餐厅…）查不到时，
   依次换 `美食 / 中餐厅 / 小吃 / 面馆 / 火锅` 重试；用户明确说了口味（如海鲜）时首选词不变。
2. **三档查询顺序**：`参照点周边 5km` → `换关键词 / 放大到 10km` → `城市范围`，任何一档有候选即停。
   先换关键词再放大半径：扩大半径不保证得到更多或更适合当前餐次的候选。
   每轮查询使用真实关键词，`food_query.keyword` 记录真正查到结果的那个词。
3. **城市范围回落并如实标注**：周边怎么都查不到时退回城市范围，`scope` 记为「城市范围」，
   卡片与回复都写明"本次为城市范围候选，不是景点周边"，不把城市候选冒充周边。
4. **`app/foods.py` 单餐取消**：`select_meal` 新增 `mode='remove'`，只清该日期+餐次的选择，
   其他餐次保留，已有计划书标记为待更新。
5. **`frontend/app.js` / `experience.js`**：已选餐次旁新增「取消这一餐」；`0 候选` 文案改为
   可执行的下一步（换日期/餐次、指定参照地点、报具体菜系或店名、或本餐自行安排）；
   取消餐次不触发"自动进入下一餐"的推进逻辑。

## 成员原分支的历史验证记录

- `pytest tests -q` → **139 passed**（新增 `tests/test_food_coverage.py` 5 条：
  换词兜底、放大半径、城市范围回落与标注、显式偏好优先且不被兜底顶掉、单餐取消不影响其他餐次）。
- 真实接口复验（同一洛阳工作区，只读，不写回）：
  `当地餐厅`(0 条) → `美食` → **5 家候选，全部在龙门石窟 0.5 公里内**（0.1/0.4/0.4/0.5/0.5 km）。
- 浏览器检查：`browser_experience_v11.cjs`、`browser_map_v9.cjs` 均通过；
  另加真实浏览器用例验证「取消这一餐」按钮发出的请求为 `meal_choice{...,mode:'remove'}`，
  且只移除该餐、其他餐次保留。

## 边界

- 仍然可能出现三档都查不到的情况（例如景区周边高德确实没有餐饮 POI）。此时不编造候选，
  而是明确告知已查过的范围，并给出可执行的替代动作。
- `food_query.scope` 只反映本次查询实际命中的范围，不代表该区域餐饮供给的真实分布。

整合复核补充：周边扩展遵守当前数据接口的10公里上限，展示范围与实际发送范围一致。供应商连接失败、限流等错误会终止本轮并保留旧候选，不当作空结果继续扩大查询。新整合保留原有通行预检查与基础资料预览。
