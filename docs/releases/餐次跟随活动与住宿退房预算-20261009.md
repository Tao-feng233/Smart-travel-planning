# 餐次跟随活动、住宿退房与预算汇总

日期：2026-10-09
分支：feat/shitu-v12-arrival-and-return
范围：`56b0887` → `7d168fec`（本批 8 个提交）

本批全部改动源于同一类问题：**约束被写死在错的环节上**。餐次先按固定时刻排好再去塞活动，
住宿与退房在时间轴上没有位置，预算只算了住宿一项。三处都改成"先排事实，再套约束"。

---

## 一、餐次与游程的关系（`56b0887`）

### 问题

午餐时刻在景点排定**之前**就按固定默认值（12:00）算好了，于是长时景区被午餐切成两段
（如西湖 240 分钟被切成 90 + 150），用户看到的是"游玩被打断"。

### 改动

- **景点先连续排定**，餐次时刻改由 `app/meal_flow.py` 的 `resolve_meals` 在景点之后解析：
  默认时刻 → 撞上景点则顺延到该段结束后 → 再退到段前 → 最后按 5 分钟步长就近找空档。
- **删除**"午餐把景区切成两段"的分支（`planning.py`），改为单条连续游览；
  `spot_continue` 不再产生。
- 新增 `schedule.meal_inside`：游玩跨过饭点时，该餐**在游玩过程中**解决，
  游程时段 = 游玩 + 用餐（只延长 span，**游玩时长不缩短**）。
- 新增 `schedule.clip_visit`：只在硬边界（开放时间、当天上限、24:00）收窄时长，
  跨过午餐**不算**收窄理由。

### 两类餐次分别处理（用户确认的规则）

| 情况 | 处理 |
| --- | --- |
| 未指定餐厅（自行安排） | 折进游程内，游程时段含用餐；不再单独出行 |
| 已选定具体餐厅 | **必须单独出行**，让用户在计划书里看到那家店 |
| 已选餐厅确实放不下 | **不静默改动用户的选择**，改为 `meal_not_placed` 提醒 + 跳转入口 |

### 超出窗口过多时

判定用**游玩结束时刻**（此前误用开始时刻，导致永远判为"还早"、该分支从不触发）。
超窗时给出提醒：说明超出多少、建议自行安排、同时**保留用户的选择**，计划书照常生成。

> 曾尝试"自动把该餐改为自行安排"，被 `plan_revision` 的"更换已有选择需用户确认"保护拦下——
> 该保护是正确行为，说明不能替用户改选择，最终定为只提醒。

### 午休按需

在景点与餐次排定**之后**，找一段真正空着的时段安排；放不下就取消（可伸缩），
并支持 `requirements.cancel_rest` 显式取消。仍作为"钉住时段"的边界：
下午/晚上的活动从午休结束后开始。

### 早餐固定（`a5117d3`）

- 早餐时长 45 → **40 分钟**，开饭时刻固定 **08:00**，09:00 开始当天游览。
- 不按"用户起床/睡眠"推断时刻。
- 返程日/抵达日仍由窗口与 `as_late` 调整（此前已确认的规则）。

### 相关文件

- 新增 `app/meal_flow.py`（餐次解析四级策略）
- 新增 `app/opening_hours.py`（开放时间，`EVENING_LIMIT` / `NIGHT_HINTS`）
- `app/schedule.py`：`meal_inside` / `clip_visit` / `meal_window` / `meal_start` / `meal_too_late`
- `app/planning.py`：去掉拆分分支，接入游程内用餐与餐次提醒
- 新增 `tests/test_meal_and_rest_timing.py`（9 项）、`tests/test_opening_hours.py`（7 项）

## 二、最晚到达住宿 23:30（`a5117d3`）

当天排完后，若"返回住宿"晚于 23:30：先从后往前压缩可伸缩的空档（自由活动/机动），
使到达时刻回到限额内；确实压不动则记一条 `late_checkin` 提醒说明超出多少。
**不再默默排到次日。**

## 三、餐次提醒的跳转入口（`a5117d3` / `84a49c6`）

`meal_not_placed` 等提醒带 `candidate_ids` 与 `meal_period`，前端点击后切到餐饮页并选中该餐。

**关键细节**：跳过去之后不能立刻被"自动进入下一餐"顶掉，故加 `suppressMealAdvance` 标记。
该标记：
- 初值 0，**只有点击提醒链接才会设为 1**；
- `action()` 内无重置，故其它动作不会消耗它；
- 只包住"自动进入下一餐"那一段，界面刷新/错误提示照常；
- 切到餐饮页为纯渲染（不发请求）。

因此**正常选餐完全不受影响**，最多只有一次"不自动跳"。

## 四、时间轴看不到住宿与退房（`a53cb55` → `91946aa`）

### 住宿行

此前按整合方规则移除"未确认入住时刻"时，把住宿行**整个**删掉了。
用户此前反对的是**伪造 22:00 入住时刻**，不是住宿本身。改为如实呈现：

- 每晚一行「当晚住宿：&lt;酒店&gt;」，`time` 留空，注明"入住时间以酒店确认为准"。

### 退房

- 退房是**当天 12 点前的截止要求**，不是"12:00 去退房"这一项活动，
  因此时间轴上**不占具体时刻**：`退房（当天 12 点前；多数酒店如此，具体以酒店为准）`。
- **换酒店当天，退房固定在早餐前办妥**并寄存行李（用户口径）；提前办理没有限制。
- 退房行落在该晚住宿的**次日**；续住同一家时不重复提示。

### 返程链条不再声称"退房"

`transport_links.events` 的返程链条第一项原按「发车时刻 − 接驳准备 − 15 分钟」生成
（本例 16:24）并命名为"退房与出发准备"，看起来像"16:24 才退房"。
实际是"回住宿取寄存行李后出发"，已改名为「返回住宿取行李并出发」。

### 数据口径修正

发现 `nights()` 只覆盖抵达日所在段（如 10-10、10-11），而 `stay_hotels` 里还有 10-12：
以 `nights()` 为准会漏掉用户后来选定的那一晚，退房日也会算错。
已改为以**实际分配**为准：合并 `assignment_view` 与 `stay_hotels` 的键后按日期排序。

### 预览与计划书统一

住宿/退房行抽成 `schedule.stay_rows`，`provisional`（预览时间轴）与 `plan_rows` 共用，
避免"计划书里有、预览里没有"的不一致。

### 数据核对结论（重要）

候选酒店与房型记录中**没有退房时间字段**（只有 `meal` / `refund`）；
房型的 `cancel` 是"免费取消截止"（如"入住当天 11:00 前可免费取消"），
**不是退房时间**。因此 12:00 只作为惯例提示，不当作已确认时刻。

## 五、prune 误删用户餐次选择（`c646b6d`）

### 问题

`foods.prune_unavailable` 的判据原为"不在 `meal_slots` 里就删除"。
但**折进游程的餐次本来就不作为独立槽位出现**，因而被误判为"排不下"并删除用户已选的餐厅，
界面弹出"已移除排不下的餐次选择：…"。

实例：10-11 午餐窗口 (12:00, 15:00)、`meal_start` 12:00，完全安排得下，却被删。

### 改动

改为：只要该餐当天窗口容得下（窗口起点 + 用餐时长 ≤ 窗口终点）就保留；
只有窗口本身为空（如 10-12 晚餐 17:00–16:49，因 18:24 返程）才清理。

实测三个工作区清理均无移除（含各两个午餐选择）。

**边界**：判据放宽后，因其它原因没排上的餐次不再被自动删除，
而是由计划书的 `meal_not_placed` 提醒告知——符合"不静默改动用户选择"的口径。

## 六、预算只算了住宿一项（`7d168fec`）

### 问题

预算表里除住宿外全部显示"待核实，尚未计入完整预算"，但这四类里有三类数据齐全：

| 费用项 | 系统里的数据 | 原显示 |
| --- | --- | --- |
| 往返交通 | `selected_transport` / `selected_return` 的 `price` | 待核实 |
| 市内交通 | 计划内各 `route` 的 `fare` | 待核实 |
| 餐饮 | 已选餐厅的 `cost`（地图参考人均） | 待核实 |
| 门票 | `cost` / `ticket_price` 均为 `None` | 待核实（确实没有） |

根因：这几类被硬编码进 `unknown` 列表。

### 改动

新增 `planning.fill_budget(plan, w)`，在预算构造后调用：

- `items`：往返交通（票价 × 成人数，含逐项明细）、市内交通（仅计入已核实票价的公交/地铁，
  注明打车与自驾未计入）、餐饮（已选餐厅参考人均 × 成人数）；
- `known_subtotal`：已知项之和（住宿起价 + items），**未含待核实项**；
- `unknown`：只保留**真的没有数据**的项；
- `basis`：注明"已按现有资料汇总可确认部分（N 元），未取得资料的项仍列为待核实，不按零计入"。

前端预算表渲染 `items` 与"可确认小计"。

### 实测（杭州工作区，端到端生成）

```
往返交通   ¥1212     G1959 二等座 470.5×2 + T38 硬座 135.5×2
市内交通   ¥15       4 段已核实票价的公交/地铁
餐饮       ¥234      3 家已选餐厅参考人均 × 2 人
住宿起价   ¥431
──────────────────
可确认小计 ¥1892

待核实：
  - 门票实际日期及适用票种（平台未提供票价资料）
  - 打车/自驾油费与停车费
```

新增 `tests/test_budget_summary.py`（5 项），含"票价为 0 仍要计入"与
"未知项不按零计入"两个易错点。

- **门票价格**：平台确实未提供，`price_hint` 明确"未取得可靠费用资料，不能据此判断免费"，
  因此始终列为待核实，不编造数字。
- **打车费用**：路线里 `taxi_cost` 为 `None`（计划书正文的"打车预估"是单独的估算），
  未计入市内交通小计。
- 杭州工作区 10-12 仍偏紧（一天内西湖 + 返程），属行程本身的容量问题，
  需减少景点或改晚班次。
