# Tavily 搜索接入与选择耗时排查

日期：2026-10-12。此次范围为接入旅游联网搜索、解除本地资料覆盖限制、保留但不在应用流程调用RAG，以及查明选择动作的执行链路。精细景点攻略、宽松排程、交易边界及其他企业场景建议仍待后续逐步实施。

## 配置与工具

- 使用根目录 `.env` 的 `TAVILY_API_KEY`，不更改用户填写的密钥，不发送到前端或模型。
- 新增 MCP `search_travel_web(query, city, source_type, max_results)`，通过 HTTPS POST 调用 Tavily Search API，以 Bearer 认证。返回来源链接、正文、查询时间、发布日期（如接口提供）、来源类型及可核实的互动数。
- `source_type=official` 限制为政府域名、已有明确登记的官方机构/景区域名；可通过 `TAVILY_OFFICIAL_DOMAINS` 追加已确认的官方域名。不能仅凭网页标题写“官方”就认定来源。
- `source_type=popular` 搜索支持的平台域名，只有提取到页面明确标注的点赞数且不少于10000时才采用，评论仅辅助参考。搜索相关性、阅读量、商户评价量及摘要中的点赞字样不代替本文点赞数。
- 许多平台不公开或不向搜索服务提供互动计数，这类文章会被排除。当前数字核对支持提取正文中独立标注的计数行，不承诺能读取全部平台的动态页面、登录内容或计数。

依据：[Tavily Search 官方文档](https://docs.tavily.com/documentation/api-reference/endpoint/search)。使用 `include_domains`、`include_raw_content` 和关闭 `include_answer`，综合工作由项目模型完成；相关性 `score` 不是点赞数。

## 业务流程

模型通过真实 function tool 调用 MCP 搜索，可按城市、主题发现候选，也可核对具体地点；每次研究最多3次搜索，不重复相同条件。程序只接纳引用实际证据且名称在材料中出现的候选，并用地图查询核对实际地点与坐标。资料中确有出现的别名或曾用名可以用于匹配地图登记名，不能用相似名称替代身份核对。

目的地比较、景点发现和正式计划的资料查询均已切换；推荐、意图理解、游玩分析和计划修订使用 `web_guides`。保留本地RAG语料与索引，以及 `retrieve_guides`、`knowledge_status` 和旧资料批次工具，独立调用能力不删除，但应用流程不使用旧批次和RAG资料检索。

城市与具体景点不再必须存在于本地名单。全国查询的实际覆盖取决于公开搜索资料及地图返回结果，不代表所有地点都保证有介绍、坐标或实时运营信息。分页只展示本次实际核对的候选；继续推荐重新搜索并排除已有选择、看过和拒绝的地点。

官方旧文章可以支持背景介绍，但不能自动当作当前或未来开放、预约政策。模型接收来源及时间，来源内容是资料，不获得工具或修改权限。查询失败与没有结果分开处理，不虚构补齐候选。

Tavily查询复用现有HTTP连接与相同请求合并，成功结果缓存10分钟。研究传给模型的每篇正文限制2400字符，推荐输入引用证据ID并避免重复传送整篇文本。接口资料保留更完整的正文片段与来源供查看；仍需通过实际任务评估推荐质量。

## 选择为什么会等待

普通卡片按钮提交 `action=select`，直接通过 `actions.run`、`do_select` 修改草稿并提交，**不经过模型意图识别，也不需要模型代选**。随后 `post_processing.refresh` 等待预览刷新，再完成整个任务。

已有日期与地点时，预览会生成程序估计并查询住宿、景点和餐厅之间的通行。单个有效起终点通常依次核对步行、公交、驾车，接口还有并发与频率约束；普通选择采用程序预览和程序审核，没有主动请求模型排程或审核。预览主体的等待上限为25秒，但此前站点接驳核对也可能有额外等待，因此25秒不是整次选择任务的总耗时保证。

“完成景点选择”是另一种动作：可能运行模型游玩分析并自动查询住宿。通过聊天要求“帮我选”则需要模型识别意图并调用编辑工具。不能把这三种情况混为一谈。同一旅行已有任务时还会受到任务串行锁影响。

“选择目的地”会直接记录城市，条件允许时自动查询景点，后续查询与推荐使用模型和外部接口；这不是由模型决定城市按钮如何保存。正式餐次选择还可能在保存前核对餐厅通行，也会产生接口等待。

本轮仅排查，未将预览移到后台、未降低既有交通核对要求。下一步若优化选择响应，可让选择先提交并显示，相关预览另行更新；这需要处理版本、取消和过期结果，不能简单删除等待。

## 备份与验证

变更前源代码、测试和文档备份：`repository-backups/before-tavily-search-20261012-221204/source.zip`。不包含密钥、用户数据库或历史对话；用户配置与已保存旅行未迁移或清理。

- `tests/test_web_search.py` 覆盖来源域名边界、明确点赞门槛、相关性分数不能冒充点赞、来源引用、未知城市、真实工具循环、地图匹配、失败与空结果，以及计划资料不调用RAG。
- 原有计划与推荐测试的外部资料获取夹具更新为搜索契约，排程单元测试隔离新增搜索模型阶段；带 `web_search_integration` 标记的用例执行实际搜索获取逻辑。
- `scripts/checks/check_web_search.py` 使用独立验证数据库，启动真实MCP，确认新工具与保留的RAG工具都已注册，运行模型搜索和地图核对，不写入用户旅行。
- 真实长沙两日测试的一次结果：发现12个来源支持的候选，8个取得匹配地图ID与坐标，约54秒；本次只作接入验证，不是全国覆盖、效果或响应速度保证。RAG工具调用为0。
- 限制模型输入正文长度、避免重复传送整篇资料后，另一次长沙检查约34秒，发现9个候选、6个取得匹配地图ID与坐标；查询与候选不同，不能据此声称固定提速比例。
- 最终573项后端回归通过；景点卡片、嵌套详情、选择控制，以及计划导航、旧计划和会话恢复浏览器夹具通过。页面资料视图分别展示官方来源与达到点赞门槛的平台来源。
- `scripts/checks/probe_selection_path.py` 驱动实际选择任务，用隔离存储和可控预览等待验证：选择已执行、模型调用为0，任务仍等待预览。`--assert-immediate` 会因当前同步等待而失败，这是保留的问题证明，不是宣称已经提速。

验证明细与回归输出位于忽略的 `data/runtime/tavily-search-20261012/`。新增资料工具不代表已完成详细景区攻略，也不保证未来运营事实；正式汇报尚未随本轮改动重写。
