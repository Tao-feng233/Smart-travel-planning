## 关键分歧：锚定餐次跟随景点改期时，是自动挪期还是提示确认

该分支的做法（`app/planning.py` 新增 `meal_alignment()`，注释原文）：

> 这里先把锚定景点的餐次挪到该景点的实际排期日（结果写回 `w['meal_choices']`）

即**程序自动改写餐次日期**，并追加说明"已按锚定景点「X」的实际排期调整到 Y，如需保留原日期请改选班次或改为自行安排"。

PR #2 的做法：**不自动挪期**，把该餐次标为 `affected` 并给出原因（景点改到哪、原日期是哪），保留餐厅选择，由用户决定是否跟随。依据是任务说明第三批原文：

> 景点改期时，计算该餐次的受影响状态，提示需要调整或重新查餐厅；没有明确绑定的旧餐次不自动挪期。

需要协调者判断：**"没有明确绑定的旧餐次不自动挪期"这条是否也约束"明确绑定"的餐次。**
如果约束，则本分支的自动挪期与任务说明冲突；如果只约束未绑定餐次，则自动挪期可以接受，
应按该语义调整 PR #2 的 `follow_spot` 行为。

## 该分支中值得单独评估的两处（与上述分歧无关）

1. **尚未抵达的日期不排用餐**：`infeasible()` 对 `dt < 抵达日` 直接返回可读理由，而不是留给排程阶段。
   PR #2 目前只在排程阶段按当天窗口处理，没有这一层前置拒绝。
2. **抵达当天不单独安排早餐**：`dt == 抵达日 and period == 'breakfast'` 直接拒绝。
   PR #2 的实测行为是"晚到当天不排早餐"，但没有把这条写成显式规则与用例。

这两条与 PR #2 现有语义不冲突，若协调者同意，可以单独移植并补测试。
