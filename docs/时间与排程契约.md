# 时间与排程契约（成员三 → 协调者 / 成员二）

对应《成员三任务说明》第一批"统一时间契约与基础引擎"。
实现位置：`app/time_policy.py`（纯函数，不访问数据库、不调用新供应商）。

## 一、本期替换掉的固定值

旧版本在 7 处各自硬编码"抵达后 90 分钟""返程前 120 分钟"，各阶段互不一致：

| 旧行为 | 现状 |
| --- | --- |
| `planning.py` 抵达日 `到达+90` | 改调 `time_policy.arrival_ready()`，按"出站取行李 + 实查车站→首站路线 + 机动"计算 |
| `planning.py` 返程日 `出发-120`（4 处） | 改调 `time_policy.return_preparation()`，按"实查末站→车站路线 + 候车/值机 + 机动"计算 |
| `schedule.windows()` 内同样的 90/120 | 复用同一份 `time_policy` 结果，班次变更即失效重算 |
| `foods.infeasible()` 文案里的 90 | 引用 `time_policy.FALLBACK_ARRIVAL_BUFFER_MINUTES` |
| 生成提示词里教模型的 90/120 | 删除，改为"首尾两天可用时间由程序统一计算" |

旧值只保留为**缺关键依据时的兜底**（`needs_check`），并写明"沿用旧口径待替换"。

## 二、需要协调者提供的数据

| 输入 | 用途 | 缺失时的行为 |
| --- | --- | --- |
| 车站/机场实体坐标（`kind` 为 `station`/`airport`/`transport_hub`，名称与班次的 `arrival_station`/`departure_station` 一致） | 查询"最后一站→车站"与"车站→首站/住宿"的道路耗时 | 不查询、不猜坐标，返回 `needs_check` 并列出待核实项 |
| 承运方候车/值机规则 | 替换 `WAIT_REQUIREMENTS` 中的估计值（航班 120、高铁 30、普速 45） | 使用估计值并标注依据来源为一般建议 |

`time_policy.station_place()` 只读取工作区 `catalog` 中已有坐标的实体，不会去调用地图
供应商找站点。站点定位属协调者职责，本分支不新增供应商调用。

## 三、调用方法

```python
from app import time_policy

# 抵达日：还差多少分钟才能开始活动（需要车站→首站的实查分钟数）
ready = time_policy.arrival_ready(transport, route_minutes)
# -> {minutes, status, basis, unverified, evidence_ids, unit, timezone}

# 返程日：需要提前多少分钟离开最后一项活动
prep = time_policy.return_preparation(return_transport, route_minutes)
cutoff = time_policy.return_cutoff(departure_minutes, prep)   # 活动必须结束的最晚分钟数

# 缺路线依据时传 route_minutes=None：minutes 为保守兜底，status=needs_check
```

`status` 三态：`verified`（依据来自已查询路线与已确认班次）、`estimated`（有依据的可调整
估计）、`needs_check`（关键依据缺失，展示为待核实）。

## 四、交给成员二的输出

生成计划后，`w['time_policy']` 与 `plan['time_policy']` 同时携带同一份口径：

```json
{
  "unit": "minutes", "timezone": "Asia/Shanghai", "schema_version": 1,
  "arrival": {"2026-10-12": {"minutes": 70, "status": "verified",
                             "basis": "…出站与取行李估计30分钟；到首站或住宿道路耗时20分钟；接驳机动20分钟",
                             "transport_id": "…"}},
  "return":  {"2026-10-14": {"minutes": 160, "status": "verified", "basis": "…",
                             "station": {"id": "hub", "name": "青岛北站", "location": "120.38,36.10",
                                         "location_status": "verified"},
                             "route": {"mode": "walking", "minutes": 20, "polylines": []},
                             "transport_id": "…"}},
  "notes": ["2026-10-14 返程准备：…"]
}
```

* 每个条目带 `transport_id`：班次一改，时间轴就不再复用旧准备时长。
* `route` 含 `polylines` 与 `mode`，可直接给地图展示，不需要成员二再算一遍。
* 事件区间左闭右开；结束时刻等于下一项开始不算重叠。

## 五、验收样例

| 场景 | 结果 |
| --- | --- |
| 相同 16:00 返程，末站→车站 20 分钟 | 活动须在 13:20 前结束（准备 160 分钟） |
| 相同 16:00 返程，末站→车站 80 分钟 | 活动须在 12:20 前结束（准备 220 分钟） |
| 同样 20 分钟接驳，高铁 vs 航班 | 准备 70 分钟 vs 160 分钟，依据文本不同 |
| 缺站点坐标 | `status=needs_check`，准备 120 分钟并注明"待替换"，不猜坐标、不当零 |

旧固定值断言按业务语义改写，未删除用例。

## 六、已知边界

* 候车/值机与出站时间仍是估计值，等承运方规则确认后替换常量。
* 未确认返程日期时仍按 `days` 生成游玩日，尚未引入"返程待确认"状态（本批未做）。
* 站点实体未进 `catalog` 前，所有场景走 `needs_check` 分支，时间轴与旧版本数值一致。
