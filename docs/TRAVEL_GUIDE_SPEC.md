# 定制可执行旅游攻略规格 v0.4

> 兼容启动包v0.4。本文件定义用户最终看到什么和使用体验；字段、类型和枚举以`CONTRACTS.md v0.4`为唯一标准；数据采集字段以`DATA_REQUIREMENTS_CATALOG.md`为准。

## 1. 最终目标

用户确定想去的城市或旅行区域后，系统尽量替用户完成信息搜集、比较、路线组合和风险检查，使用户按照攻略即可完成旅行，不必再自行拼接景点、住宿、餐饮和交通。

“单目的地”指一个城市或旅行区域，不是一个景点。一个目的地内部必须安排多个游玩地点、餐饮、休息和本地交通。

系统不能保证现实信息永远不变，因此攻略必须明确哪些是已验证、估算、模拟、过期或待确认数据，并支持刷新和局部重规划。

## 2. 七部分结构

### 2.1 旅行总览

用户应看到：

- 出发地、日期、人数和同行者情况。
- 目的地、旅行天数、时区和整体主题。
- 旅行节奏、兴趣、必去、排斥和身体限制。
- 主要游玩区域和住宿分段。
- 为什么这样安排，以及关键取舍。

数据来源：`TripProfile`、`DestinationRecommendation`、`TripSegment`和`StaySegment`。

### 2.2 抵达与离开

用户应看到：

- 建议高铁、火车、飞机、客运或其他方式。
- 主方案和备选方案。
- 起终站、门到门时间、费用区间、换乘和预订提醒。
- 到站后先去住宿、吃饭还是先游玩。
- 返程方式和建议离开住宿地的时间。

没有实时班次时只能展示典型方式和时间/价格区间，不能虚构车次、航班和余票。

### 2.3 行前准备

用户应看到：

- 证件和预约清单。
- 车票、门票、住宿等购买或确认事项。
- 衣物、鞋、雨具、健康和活动装备。
- 与天气、山区、涉水、长距离步行、老人儿童等条件关联的准备建议。
- 出发前24～48小时应刷新的项目。

准备建议必须来自规则库、事实或证据，不能由LLM凭常识无来源补写。

### 2.4 住宿方案

用户应看到：

- 每个日期入住的住宿区域和候选住宿。
- 一个主推荐和若干备选。
- 酒店/连锁/本地特色住宿/青旅等类型。
- 价格区间、评分和评论量、质量标签、设施和交通适配。
- 是否需要换住宿以及换住处的理由。
- 实时库存不可得时的明确提示。

默认尽量少换住宿；只有用户要求、已预订或路线明显受益时才换。

### 2.5 每日详细行程

每个旅行日应从当天起点开始，安排多个游玩地点、餐饮、休息和回住宿地的过程。

用户应看到：

- 当日主题和主要游玩区域。
- 每个节点的时间、名称、地址、开放窗口、最晚进入、预约、费用、理由和提示。
- 节点间建议步行、地铁、公交或打车，以及耗时、费用、拥堵和步行负担。
- 早餐/午餐/晚餐或用餐区域建议。
- 休息和缓冲时间。
- 当日总游玩时间、总通勤、强度、费用、警告和备用安排。

具体导航由地图应用完成，本系统不输出逐路口指令。

餐厅数据足够时插入具体店铺；数据不足时降级为用餐区域和餐饮类型，不虚构店铺。

### 2.6 预算与备用方案

用户应看到：

- 城际交通、住宿、本地交通、门票、餐饮、购物和机动费用。
- 已知、估算区间和未知费用。
- 已付款、可退和不可退项目（有数据时）。
- 预算余量和超预算原因。
- 下雨、起晚、地点关闭、用户疲劳、餐厅不可用等备用方案。

预算只能由`CostItem[]`计算，不能由LLM直接生成总数。

### 2.7 来源与更新时间

用户应看到：

- 关键事实的来源和更新时间。
- 当前使用的数据快照。
- 过期、降级、模拟和未知项目。
- 是否需要出发前复核。
- 当前攻略的数据可信状态。

## 3. 攻略状态展示

### DEMO模式

- 允许使用Mock数据跑通完整功能。
- 页面必须显示明显的“演示数据”标识。
- 不得宣称攻略已经由真实数据验证。

### VERIFIED模式

- 关键开放、路线、住宿起点等事实必须达到发布门槛。
- 非关键餐厅、天气等数据不足时允许降级，但要显示警告。
- 关键数据不足时攻略状态为`NOT_READY`。

用户界面应同时展示：

- 计划是否逻辑可行。
- 数据是否真实可靠。
- 攻略处于草稿、已确认、执行中或已过期哪个阶段。

## 4. P0必须完成

- 单个目的地内多个游玩区域和多个游玩地点。
- 七部分TravelGuide后端组装和Vue展示。
- 抵达方式建议及到站后第一步安排。
- 行前准备清单。
- 住宿区域和人工整理的具体住宿候选，不要求实时库存。
- 景点、基础餐饮、本地交通、休息和回住宿地安排。
- 预算、来源、风险和备用方案。
- 通用重规划流程；至少用一个事件完成端到端验收。
- 每次成功修改生成新计划和攻略版本。
- Mock、Snapshot、Live、Hybrid数据模式可替换，可信状态可见。

## 5. P1可优化

- 双目的地真实规划。
- 实时酒店库存、房型、价格和退改。
- 具体车次/航班、票价和余票。
- 餐厅菜单、排队、预约和评论聚合。
- 天气或外部事件自动触发重规划。
- 攻略版本撤回界面。
- Markdown/PDF导出和地图可视化。

## 6. 结构预留

P0仍必须使用：

- `destination_requests[]`
- `trip_segments[]`
- `stay_segments[]`
- `travel_legs[]`
- `CostItem[]`
- `DataSnapshot`
- `VersionLineage`

因此以后增加多目的地、换住宿和更多事件时不需要破坏性重构。
