# 三人团队项目执行计划书

本文件面向三位项目成员，用来安排工作、判断进度和组织联调。系统设计以 `PROJECT_DESIGN.md` 为准，接口以 `CONTRACTS.md` 为准。

## 1. 项目目标

在一组受控知识库数据上完成可运行的AI旅行决策与动态行程助手，证明下面的完整链路成立：

```text
自然语言需求
→ 主动追问
→ RAG检索
→ LLM目的地推荐
→ MCP获取事实和路线
→ LangGraph编排
→ 行程生成
→ 约束验证与修复
→ 用户修改或突发重规划
```

完成标准不是“所有旅游功能都实现”，而是核心演示流程能够从Vue页面端到端运行，且每项技术都有明确业务作用。

## 2. 开工前共同确认

三个人先共同填写并确认：

- [ ] 当前知识库数据目录和版本。
- [ ] KnowledgeCoverage最低规划门槛和至少一组planning_ready数据。
- [ ] 数据源调研任务和Fake Provider方案。
- [ ] 首批住宿候选和基础餐厅数据范围。
- [ ] 主LLM Provider已通过结构化输出和工具调用POC，API Key按 `.env` 配置。
- [ ] 地图和天气使用真实API还是模拟Provider。
- [ ] 建立回归测试场景集，最终演示输入不提前写死。
- [ ] Git仓库和各自开发分支。
- [ ] `CONTRACTS.md` v0.3冻结。

在这些项目没有确认前，不要让三个AI分别生成完整工程。

## 3. 功能优先级

### P0：必须跑通

- Vue对话输入和行程展示。
- LLM输出结构化TripProfile。
- 至少一次主动追问。
- RAG检索并返回evidence_id。
- LLM只在知识库检索出的planning_ready候选中推荐。
- 至少一个MCP工具被LangGraph实际调用。
- 根据日期过滤闭馆或不可用景点。
- 生成带时间、交通和预算的行程。
- 验证并修复至少一种冲突。
- 用户修改后重新规划受影响部分。
- 七部分TravelGuide能够从后端组装并在Vue完整展示。

### P1：有时间再完善

- 两个相邻目的地的天数分配。
- 天气影响户外景点。
- 历史人流高、中、低预测。
- 住宿区域推荐。
- 计划版本和撤回。
- Docker Compose一键启动。

### P2：只保留设计和接口

- 真实酒店库存和预订。
- 实时票量和支付。
- 全国目的地。
- 任意数量的多城市优化。
- 大规模评论分析。

如果P0没有全部跑通，立即停止P1开发。

## 4. 三人工作划分

### 成员A：数据、RAG与MCP

| 任务 | 输出 | 依赖 | 完成判断 |
|---|---|---|---|
| A1 设计数据表并导入试点数据 | MySQL表和初始化脚本 | 共同确认字段 | 能查出目的地、景点和开放规则 |
| A2 建立认知卡片 | Chroma集合和索引脚本 | 试点数据 | 查询返回内容、entity_id和evidence_id |
| A3 完成RAG检索 | 检索服务 | A2 | 能按省份、目的地和类型过滤 |
| A4 实现MCP工具 | MCP Server | A1、A3 | 至少3个工具可独立调用 |
| A5 提供Provider | 真实或模拟地图/天气接口 | 无 | 接口失败时可切换fake数据 |
| A6 数据源可行性表 | 各数据项获取状态和降级方案 | 数据测试 | 明确AVAILABLE/LIMITED/MOCK_ONLY等状态 |
| A7 提供测试Fixture | 正常、过期、未知数据 | A1 | C可脱离A的运行环境测试 |

A不负责Vue、TripProfile解析和行程排程。

### 成员B：LLM决策与Vue前端

| 任务 | 输出 | 依赖 | 完成判断 |
|---|---|---|---|
| B1 搭建Vue项目 | 对话和结果页框架 | 契约 | 能使用fixture展示结果 |
| B2 提取TripProfile | 结构化LLM服务 | 契约 | 非固定输入能生成合法JSON |
| B3 主动追问 | 缺失字段策略 | B2 | 缺日期/预算等会继续询问 |
| B4 目的地推荐 | 推荐结果和证据ID | A的RAG接口或fixture | 只返回候选ID并解释取舍 |
| B5 修改意图识别 | ChangeRequest | 契约 | 能识别删除、替换、减轻强度等意图 |
| B6 攻略组装 | TravelGuide | A的证据、C的验证计划 | 七部分数据可由固定JSON组装 |
| B7 前端联调 | 完整交互页面 | C的API | 可推进会话并展示完整攻略和冲突 |

B不负责判断开放时间真假，也不在前端复制规划规则。

### 成员C：LangGraph、规划验证与后端集成

| 任务 | 输出 | 依赖 | 完成判断 |
|---|---|---|---|
| C1 实现共享Schema | Pydantic模型 | 契约 | 示例JSON全部校验通过 |
| C2 搭建FastAPI和LangGraph | API和状态图 | C1 | 可以推进到追问/推荐/规划节点 |
| C3 前置过滤 | 可用候选集合 | A的数据或fixture | 不可用地点不会进入规划 |
| C4 生成行程 | ItineraryPlan | C3 | 输出时间、交通、预算和节点 |
| C5 实现验证器 | Conflict列表 | C4 | 能发现时间窗或预算冲突 |
| C6 实现修复和重规划 | 新计划版本 | C5、B5 | 修复后重新验证，锁定节点不变 |
| C7 完成后端集成 | 统一REST接口 | A、B接口 | Vue可端到端调用 |

C不负责重新建设RAG，也不让LLM绕过验证器直接输出已验证计划。

## 5. 三四天推进顺序

### 第0阶段：共同定标准

三人一起完成范围、目的地、数据对象、API和演示输入确认。C建立后端空壳和共享Schema，B建立Vue空壳，A准备小规模样例数据。

阶段结束时必须存在：

```text
固定的示例TripProfile
固定的ResourceCandidate列表
固定的ItineraryPlan示例
三个人都能运行的仓库
```

### 第1阶段：三线独立跑通

- A：MySQL、Chroma和MCP工具可独立测试。
- B：用fixture完成需求解析、推荐和页面展示。
- C：用fixture完成LangGraph、规划和验证。

这一阶段不互相等待，缺少的依赖全部使用契约中的示例数据模拟。

### 第2阶段：第一次联调

按以下顺序连接：

```text
B输出TripProfile
→ A返回RAG证据和ResourceCandidate
→ C生成并验证ItineraryPlan
→ B组装并展示TravelGuide
```

只跑一条最简单的单目的地场景。联调失败时优先检查契约，不允许三个人各自增加临时字段。

### 第3阶段：补充闭环

- 加入主动追问回路。
- 加入验证失败→修复→再验证回路。
- 加入一次用户修改或突发情况。
- 有余力再加入双目的地、天气或人流预测。

### 第4阶段：冻结和演示

- 停止增加新功能。
- 修复端到端问题。
- 固定演示输入和数据。
- 准备异常情况下的备用fixture。
- 三人分别准备自己负责部分的解释。

## 6. 每次联调要检查什么

- [ ] B输出的TripProfile能通过C的Pydantic校验。
- [ ] A返回的候选ID、证据ID在数据库中真实存在。
- [ ] LLM没有返回候选集合外的目的地或景点。
- [ ] MCP工具确实被调用，而不是只写了代码没有使用。
- [ ] 不可用地点在规划前已经过滤。
- [ ] 行程中包含移动时间和预算。
- [ ] 验证失败不会输出 `VALIDATED`。
- [ ] 重规划没有修改锁定节点。
- [ ] 外部API失败时页面仍能展示明确的降级结果。
- [ ] TravelGuide七部分存在，无法获取的字段明确标为未知或待确认。

## 7. Git和AI协作规则

建议分支：

```text
main
feature/data-rag-mcp
feature/llm-vue
feature/graph-planner
```

每天至少进行一次集成，不要等所有功能完成后再合并。

每个人给AI任务时应只描述本人的交付边界。AI生成代码后，成员本人至少确认：

- 是否使用了共享Schema。
- 是否偷偷新增字段。
- 是否把模拟数据当成真实数据。
- 是否真正运行了测试。
- 是否修改了其他成员的目录。

## 8. 回归测试业务流程

下面三类流程用于开发期间回归测试，不是必须照读的最终演示文案，代码不得针对固定输入特化。

### 演示一：不知道去哪

用户提出模糊需求，系统追问缺失信息，RAG检索支持目的地，LLM比较后推荐，用户选择并生成完整攻略。

### 演示二：已确定目的地并生成完整攻略

用户指定一个目的地。系统完成抵达方式、行前准备、住宿候选、多个游玩地点、基础餐饮、本地交通、预算和数据来源的七部分攻略。

### 演示三：计划发生变化

用户起晚或遇到下雨。系统锁定已完成和已预约节点，只重规划当天剩余部分，并展示修改内容。

双目的地真实规划为P1附加演示，不影响P0验收。

## 9. 个人讲解重点

- A说明事实数据与RAG知识为什么分开、MCP如何统一工具、数据过期怎样降级。
- B说明LLM如何理解不固定输入、为什么采用“先过滤再让LLM判断”、Vue如何承载对话流程。
- C说明LangGraph两个回路、规划前/中/后的三层验证、局部重规划如何保留锁定节点。
