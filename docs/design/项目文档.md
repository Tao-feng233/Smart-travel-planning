# 识途项目文档

编写日期：2026-10-09

编写说明：本文档基于对当前项目源码、测试运行结果与数据文件的直接核查整理，未采用目录内早期文档中的历史结论。文中数字均为实际清点结果；如与早期文档不一致，以源码与本文档为准。

## 1. 项目概述

### 1.1 项目定位

识途是一套面向自由行用户的对话式旅行规划系统。用户通过自然语言与网页工作台协作，完成需求收集、景点选择、住宿与交通安排、餐饮选择，并生成一份可以继续修改、导出与打印的旅行计划书。

需要解决的问题：通用大模型可以直接生成旅行攻略文本，但旅游信息有日期与适用条件，仅凭模型记忆容易出现旧价格、错误班次与不存在的预约规则；同时，景点、住宿、餐饮、交通信息分散在不同平台，用户自行汇总费时，并容易产生绕路、时间冲突以及多轮修改后条件丢失的问题。

### 1.2 三条设计原则

1. **事实来自真实接口**。地点、路线、天气、酒店、班次、门票均通过供应商接口查询，不依赖模型记忆生成。
2. **模型只提交提案，程序校验后执行**。模型输出的动作与候选选择，都要经过真实候选 ID、日期范围、数量边界与状态检查。
3. **未知不补造**。查询失败、无结果、字段缺失分别处理，保留"待核实"状态，不用模型生成的内容冒充事实。

### 1.3 当前形态与规模

本机可运行的完整原型：后端服务（FastAPI，端口 8767）、浏览器工作台、知识库与 Windows 便携体验包。选定与推荐不代表已预订，不包含支付、出票与实时导航。

## 2. 系统架构

系统按六层组织，自上而下为：

| 层次 | 实现 | 职责 |
| --- | --- | --- |
| 交互层 | frontend/（原生 JavaScript 与 Canvas 地图） | 登录、对话、候选卡片、工作台、地图、计划书 |
| 服务层 | FastAPI（main.py）、auth、storage、replies、guidance | 接口、鉴权、任务调度、SSE、持久化 |
| 编排层 | LangGraph（understand / check / execute）与语义任务循环（goal_agent） | 意图识别、动作分发、受控查询循环 |
| 业务模块层 | discovery、foods、choices、visit_analysis、planning、proposals、plan_revision、auto_selection 等 | 景点、住宿、交通、餐饮、规划与修订 |
| 工具层 | 本地 stdio MCP（自建 7 个工具）与途牛官方 Streamable HTTP MCP（7 个只读工具） | 把供应商能力统一为按名称调用的工具 |
| 数据源 | 高德地图、和风天气、途牛、本地官方资料库 | 真实事实来源 |

本地自建 MCP 的 7 个工具：地点搜索、地点详情、车站与机场检索、路线计算、每日天气、资料检索、知识库状态。途牛侧限定为 7 个只读工具：酒店搜索与详情、最低价列车搜索与列车详情、航班搜索与舱位详情、最低价门票查询。

存储使用 SQLite（WAL 模式）。整个旅行工作区以一份 JSON 整体保存（需求、候选、选择、计划、版本都在其中），另有账户、会话、任务、缓存、供应商调用计数与反馈等独立表，便于账户隔离与审计。

一次请求的典型链路：前端提交动作（携带 request_id 幂等键与 revision 版本号）→ 服务端创建后台任务 → LangGraph 意图识别 → 规则校验与动作分发 → 通过 MCP 工具查询供应商 → 结果写回工作区并持久化 → 通过 SSE 把进度与流式回复推送给前端。

## 3. 用户流程

### 3.1 注册与新建旅行

用户注册登录后可创建多次旅行，每次旅行的对话、条件、选择与计划相互独立；支持历史列表、搜索、切换、重命名、归档、删除与数据导出。

系统行为：密码使用带随机盐的 scrypt 加密存储；会话使用服务端可撤销令牌，数据库只保存摘要；账户隔离由服务端校验，跨账户访问返回 404。

### 3.2 需求收集（对话）

用户用自然语言描述旅行（目的地、出发地、日期、人数、预算、偏好）。模型输出结构化意图（submit_intent，提交意图），包含三部分：本轮动作、需求补丁 patch（只允许本轮明确说过的条件）、简短回复文本。

程序对补丁逐字段检查边界：游玩天数 1–60、成人数 1–10、儿童数 0–6、房间数 1–5、午休 0–120 分钟、日期不得早于今天等，超出范围直接报错。缺少关键条件时系统提问补齐；已经提供的条件不重复询问。

### 3.3 景点选择

系统根据目的地与偏好查询真实地点（高德），生成候选批次（每批上限 24 个，每页展示 4 张卡片），支持翻页、不感兴趣、拒绝并换一批、指定某景点的游玩日期与时段。候选卡片可打开详情（介绍、门票、图片、电话、营业资料）。地图页签提供全国范围内可拖动、缩放与双击放大的交互地图。

### 3.4 住宿

完成景点选择后，系统以已选景点的中心位置为参照查询途牛酒店，并与高德坐标交叉核对（名称、分店与门牌），核对不通过不接收坐标。列表展示房型起价与位置；选中酒店后可选具体房型与房间数，房型为可选项，只选酒店位置即可继续。酒店报价带日期与覆盖期概念，日期变化会使报价过期并标记，避免把旧价格当作当前价格。

### 3.5 往返交通

去程与返程分别查询（列车为最低价搜索，航班为搜索加舱位详情），用户可比较班次时刻与价格后选定。同一方向只保留一个当前方案，改选需要明确替换；无票的班次在前端禁用、后端同样拦截。未选票时系统按旅行日期给出推荐，待用户确认。

### 3.6 餐饮

按"日期 + 餐次（早餐/午餐/晚餐）"逐项选择餐厅。查询以当日景点或住宿为参照：先查周边 5 公里，必要时扩大至 10 公里或城市范围，且查询范围如实标注。餐厅候选展示人均参考、营业资料与来源。每一餐可以单独取消或改为"自行安排"，不影响其他餐次。

### 3.7 计划生成与校验

系统把已选内容（景点、酒店、班次、餐次、游玩偏好）组装为结构化上下文，由模型分批提出每日安排（每批最多 16 个景点），随后由程序执行：

- 校验候选 ID 与日期的真实性与有效性；
- 查询各段实际通行方式与耗时（步行、公交、驾车）；
- 检查时间窗口：到达后准备时间、返程前准备时间、三餐窗口（早 7:30–10:00、午 12:00–15:00、晚 17:00–21:00）、每日顺序与缓冲；
- 对安排过密、结束时间过晚等情况给出警告，经用户确认后才发布；
- 由独立的审核环节（另一次模型调用）复核需求遗漏与资料引用。

### 3.8 查看、修改与导出

生成后可查看每日计划、右侧时间轴与地图路线：已查询到道路坐标的日程绘制红色实线，未查到的显示顺序示意并明确标注。用户可用自然语言提出修改（如"第二天轻松一些"），系统对整份计划做受保护的修订——用户明确固定的日期、顺序、已选餐厅与门票不允许被改动。计划书支持 Markdown 导出与打印 PDF；每次修改保留撤销入口。

## 4. 关键实现机制

### 4.1 受控的模型调用

模型通过 Function Calling 只能输出唯一的 submit_intent 调用；输出不符合约定时，程序最多允许一次修正。模型可选动作共 22 个：目的地发现、景点搜索、景点翻页、完成景点选择、住宿搜索、天气、列车、航班、门票、地点详情、生成计划、普通对话、房型选择、完成住宿、餐饮搜索、餐次选择、游玩日期安排、游玩分析、计划修订、完成餐饮、请求自动代选、取消自动代选。

前端可提交的动作受 33 项白名单限制；模型提出"选择某个候选"时，程序核对候选 ID 确实存在于当前旅行目录中，否则报错而不执行。

### 4.2 模型提案与程序校验

所有模型输出都按"提案"处理：候选选择过 ID 白名单；计划过日期与时段校验；游玩时长限定在 15–720 分钟；达到重试上限时向用户报告具体原因，不静默丢弃用户选择。程序校验与模型审核分离：审核环节补充检查遗漏，但不替代程序对时间、预算与固定约束的检查。

### 4.3 MCP 工具层与供应商治理

- 本地自建 MCP 提供 7 个工具，业务代码只按工具名调用，底层由适配层负责 HTTP、认证、超时与字段解析。
- 途牛调用受只读白名单限制；调用前用启动时抓取的官方 schema 校验参数；设有每日调用预算（默认 40 次）与最小调用间隔（13 秒），避免超出配额。
- 高德请求做了串行节流（约 0.4 秒间隔、少量并发上限）与结果缓存；天气按接口实际覆盖窗口返回，超出窗口保留为待核实。
- 相同条件的重复查询复用缓存（不同数据有不同的有效期）；并发中的相同请求合并为一次。

### 4.4 RAG 知识检索

知识库用于景点介绍、开放与预约规则、城市与文化背景等文档性内容；实时价格与余票不走检索，直接查询接口。实现要点：

- **受控采集**：来源由显式注册表管理（当前为 5 条常规来源加 34 条山东来源），采集时检查 robots、跳转域名与正文有效性；采集失败保留旧版本并标记状态。
- **父子切分**：以 360 字符子块建立索引，命中后回取所属的 1400 字符父块，兼顾召回精度与上下文完整。
- **混合检索**：BM25 关键词召回与中文向量召回（本地 ONNX 模型加 Qdrant 向量库）两路结果用 RRF 融合；向量不可用时明确降级为 BM25，不静默失败。
- **适用性过滤**：每条资料带城市、实体与适用日期范围，检索结果携带来源与"适用/过期/待核实"状态。

### 4.5 时间与行程校验

- 路线耗时来自真实查询（步行、公交、驾车三种）；公交查询要求城市代码，缺代码时标为"待核实"，不使用默认城市。
- 到达后的准备时间与返程前的准备时间采用明确假设（默认 90 分钟与 120 分钟）；车站或机场到酒店的接驳单独估算，并在计划中标注为待核实。
- 冲突分级处理：日期、班次这类硬冲突直接报错；安排过密、结束过晚这类软提醒给出警告，用户确认后带警告发布，由用户决定，不做静默修改。

### 4.6 状态与可靠性

- 工作区整体 JSON 保存；任何修改先写版本快照，支持撤销。
- 修改旅行条件时按依赖关系批量失效：改城市清空候选；改日期或人数使酒店报价、班次与计划标记为过期，保留用户选择但要求重新确认。
- 任务持久化：刷新页面后可继续查看进行中的任务与已产生的回复；任务状态包括排队、运行、完成、失败、取消、中断（服务重启会把运行中任务标记为中断）。
- 并发控制：同一旅行同时只允许一个任务，全局与单用户的任务并发也有限制；request_id 幂等键防止重复执行。
- 进度与流式回复通过 SSE 推送；处理过程只列实际执行的步骤。

### 4.7 账户与安全

密码使用 scrypt（n=2^17、r=8、p=1）加随机盐；会话令牌只在数据库保存摘要；Cookie 为 HttpOnly 与 SameSite=Strict；写请求检查来源与 CSRF 令牌；登录失败有速率限制。请求体限制 64 KB，接口限定 JSON。

## 5. 开发过程回顾

按可验证的产物与代码痕迹，项目经历了四个阶段：

1. **原型阶段**。根目录保留了两个早期文件：《业务逻辑模拟.html》（与同名 .py 文件内容相同，是一个用模拟数据演示交互意图的单文件原型）与《识途-最终效果展示.html》（静态效果展示页）。这一阶段用于确定产品交互与业务流程，未接入真实数据。
2. **真实系统搭建**。确定技术主线为 Python + FastAPI + LangGraph + MCP + SQLite，前端采用原生 HTML/JavaScript。先对四类供应商（高德、和风、途牛、DeepSeek）做接口核对与最小调用验证，再搭建从对话到计划书的完整闭环。
3. **功能迭代**。从测试文件与浏览器脚本的命名可以看到迭代节奏：interaction_v5/v6/v7、experience_v8/v11、map_v9、enrichment_v10 等，对应流式回复、业务日期修正、长行程分批、详情卡片与地图、交互地图相机、供应商字段补全等一系列改进；其中若干节点产出了 Windows 体验包（dist/ 中从 v6 到 v11.2 共 9 个，集中在 2026-10-06 与 10-07 两天完成打包），并保留了对应的浏览器验证截图。
4. **协作与平台化**。项目随后进入多人分支协作阶段（docs/collaboration 下有成员任务说明与数据服务接入文档，山东资料 52 条等改动合入主线）。面向未来 MySQL 与独立 Worker 的公共契约层（app/contracts.py）已经落地，但 MySQL 与多进程 Worker 尚未启用——当前依赖清单中没有相应依赖，系统实际仍按单机 SQLite 运行；契约层的作用是先固定接口语义，为后续迁移做准备。

（说明：以上阶段划分依据仓库中的实际文件与产物——原型文件、测试与脚本命名、dist 打包记录、contracts.py 与其未被启用的现状；未引用早期文档对各版本的描述。）

## 6. 验证与效果

### 6.1 后端测试

tests/ 共 37 个文件、295 个测试函数，pytest 实际收集 305 项。本次复核完整运行结果：**304 项通过，1 项未通过**。

未通过项为 tests/test_transport_links.py 中的接驳时间窗断言：该测试要求返程机场的出发准备时间早于 09:00，当前实现给出恰好 09:00，属于边界条件不一致，需要修复。其余用例覆盖账户与 API、业务编排、知识检索、契约语义、计划生成/修订/警告、餐饮覆盖、地图、性能等主题，且测试均为离线运行（供应商调用使用固定数据），不依赖网络。

### 6.2 浏览器场景

scripts/ 中有 28 个 Playwright 场景脚本（覆盖 v5 至 v11 的交互回归、真实链路、地图、账户、餐饮覆盖等），运行记录以 JSON 形式保存在 data/runtime（其中 25 份为浏览器运行记录），截图保存在 .展示检查（74 张）。

### 6.3 供应商接入

四类数据源均已接入并可只读查询：高德（地点、详情、路线、静态图）、和风天气（预报与预警）、途牛（酒店、列车、航班、门票）、DeepSeek（意图识别、推荐、提案、回复、审核）。调用带缓存、节流与预算控制；查询失败与"无结果"语义区分，失败不当作"没有"。

### 6.4 数据资产

- 知识库 90 条资料记录；目的地目录 19 个城市；1 条已核对的免费入园政策（青岛市博物馆，附带复查期限机制）。
- 来源注册表 39 条（常规 5 条加山东 34 条），记录 URL、允许域名、正文选择器与实体约束。

### 6.5 交付物

- dist/ 中 9 个 Windows 便携体验包（自带 Python 运行环境，解压即用，附 SHA-256 校验和）。
- 汇报材料：output/ 下有汇报 PDF 11 份、图表 3 套（业务逻辑图、技术架构图、Agent 执行流程图）。
- 验证记录、截图与运行数据保存在 data/runtime 与 .展示检查。

### 6.6 总体评价

功能上，项目覆盖了从需求收集到计划书导出的完整闭环；景点、住宿、交通、餐饮四个环节都有真实供应商数据支撑与明确的选择、校验流程。工程上，具备账户体系、任务持久化、幂等与并发控制、状态失效管理以及测试与浏览器回归体系。可靠性上，"模型提案、程序校验、未知标注"三条原则在代码层面得到一致落实。

按当前状态，项目适合作为本机与小规模体验使用；主要待办是修复个别未通过的测试，并保持文档、测试与真实数据验证之间的同步。

## 8. 目录与运行

主要目录：

```text
app/            后端全部 Python 代码（入口 main.py）
frontend/       工作台页面与脚本（无构建步骤）
data/knowledge/ 官方资料语料；data/catalog/ 目的地与政策目录
scripts/        构建、采集、验证、启动与打包脚本
tests/          后端测试
docs/           协作文档与发布记录；output/ 汇报材料与图表
dist/           Windows 体验包
```

本机运行步骤：

1. 准备 Python 3.11 及以上版本的虚拟环境，安装依赖：`pip install -r requirements-lock.txt`；
2. 复制 .env.example 为 .env，填写 DeepSeek、高德、和风天气、途牛配置；
3. 可选：首次初始化知识索引（启用完整混合检索）：`python scripts/build_knowledge_index.py --download-model`；
4. 启动：运行 启动.cmd（或 `python -m uvicorn app.main:app --host 127.0.0.1 --port 8767`），浏览器访问 http://127.0.0.1:8767；
5. 运行后端测试：`python -m pytest -q`。
