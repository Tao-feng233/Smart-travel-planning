# 整体代码审查与分阶段重构方案

本轮先做只读梳理、源码检查和内存合成验证，未搬动文件、修改功能或更换提示词。以下是当前问题清单与执行方案，不是重构完成报告。

## 1. 结论

需要分阶段处理，不能把目录迁移、状态修复、工具能力、提示词和前端全部混在一次修改中。

建议顺序：统一基线与备份 → 修复状态一致性 → 按职责拆分后端 → 接通完整编辑执行链 → 对齐提示词与工具合同 → 整理前端与脚本 → 发布统一版本。

第一批应优先处理“查询会改掉选择、取消不彻底、修改无关条件清空选择”等实际缺陷。否则新编辑工具会扩大现有状态错误。文件分目录必须伴随职责和依赖整理，不能仅移动文件，也不能长期保留新旧两套完整实现。

## 2. 当前基线与协作范围

- 本机保留了提示词模块化重构、明确午休约束、房型可选、可选往返交通、四账号配置，以及计划书展示适配。
- 已接入成员三此前截至 `c6a81f0` 的主要行程改动，后续车站定位修复，以及成员二 `92cac1d` 的部分展示内容。
- 最新新增 5 个提交已从 `e80f164` 对比接入至 `e6edca2`，涉及筛选与资料更新。本机知识库为 20 个城市、116 条来源记录，向量索引已更新。
- 当前运行目录不是 Git 检出目录。本机独有改动尚未作为统一版本推送；后续应在受管理的 Git 工作区形成包含双方有效改动的基线，再创建重构分支。
- 成员已被要求收尾上传、暂停修改，但最终各工作区是否仍有未上传内容，需要在开始大改前依据交接核对。
- 之前未接入的自动门票加载、新预算重算、返程截短、分享链接不能当作本机当前功能，也不能借重构整条覆盖接入。

最近验证：原全量后端 441 项通过；新增筛选 5 项通过；推荐与计划展示浏览器检查通过。这不是所有用户场景都已覆盖，下面的合成验证就发现了既有测试未覆盖的行为缺陷。

## 3. 结构现状与成因

| 观察 | 当前状态 | 影响 |
| --- | --- | --- |
| 后端目录 | `app` 共 70 个 Python 文件，主要只有 `integrations`、`prompts` 两个子目录 | API、模型决策、旅行规则、数据查询和持久化边界不清 |
| 动作分发 | `agent.py` 859 行；`handle()` 328 行 | 查询、选择、状态更新与生成都由分支判断交织处理 |
| 计划生成 | `planning.py` 663 行；`_generate()` 489 行 | 模型提案、路线获取、排程、餐次、住宿、预算与审核相互嵌套 |
| HTTP 与任务 | `main.py` 433 行；`perform()` 142 行 | API、任务执行、审核、消息拼装和保存耦合 |
| 前端 | 12 个文件；`app.js` 约 62 KB；多个脚本共享全局状态与函数 | 修改顺序、加载顺序与名称覆盖影响行为；难以独立验证组件 |
| 脚本 | 51 个文件，浏览器历史检查、采集、启动、迁移、打包混放 | 不容易判断哪些是当前验收入口，哪些是历史工具 |
| 原型 | 两个业务模拟 HTML 内容完全相同 | 有可归档的重复，但必须先核对文档引用，不能直接删除 |
| 提示词与合同 | 已拆分提示词，但执行能力仍分散在合同、模式分流和业务守卫中 | 只精简提示词无法修复执行受阻 |

文件多本身不是缺陷。真正需要整理的是重复的状态入口、跨模块职责、长流程和混杂的变更。拆分后可以有更多小文件，但每组文件的职责与调用方向应清楚。

## 4. 本机仍未解决的问题

### 4.1 本轮合成数据复现的状态与执行缺陷

验证均在内存中进行，供应商调用被模拟，不写用户数据库。

| 编号 | 优先级 | 现象与结果 | 当前入口 | 处理方向 |
| --- | --- | --- | --- | --- |
| S1 | 高 | 查询另一日返程票后，工作区返程日期被更改、已选返程清空；接口随后失败也没有恢复 | `agent.handle()` 的 train 分支、`update_requirements()` | 查询参数与正式旅行条件分离；查询不能通过修改正式条件实现 |
| S2 | 高 | 只修改游玩天数，或只修改房间数，往返已选班次被清空 | `agent.py:272` 一组条件共用清空逻辑 | 按实际依赖使报价或安排待复核；无关条件不得直接删除选择 |
| S3 | 高 | 取消主住宿后，`stay_hotels` 中的酒店 ID 仍存在，`hotel_for()` 仍返回原酒店 | `agent.execute()` 的 remove_ids、`stay_plan.assign()` | 统一住宿删除操作，同步相关逐晚分配和房型，不修改无关夜晚 |
| S4 | 中 | 原偏好“海滨”，提交新的“人文”后变成两者都存在 | `update_requirements()` 偏好合并 | 显式支持追加、替换、移除；模型不能只靠列表猜操作含义 |
| S5 | 高 | act 目标带 `multi_step=true`、`generate_plan=true`，仅执行首个查询就被标为 completed，计划未生成 | `agent.execute()`、`goal_agent.continue_goal()` | 多步执行按目标与剩余工作判断完成，不能只对 query 开启循环 |

S1 验证条件为已选 11 月 15 日返程、查询 11 月 14 日；S2 保持已选班次不变，仅改变 days 或 rooms；S3 使用实际支持的 `stay_hotels={日期:酒店ID}` 格式。S5 使用已解析的合成意图验证执行器，不声称完整模型对话必然每次产生该意图。

### 4.2 此前复现、当前源码路径仍存在的问题

| 编号 | 优先级 | 问题 | 本轮依据与限制 |
| --- | --- | --- | --- |
| E1 | 高 | “车票不用管，其他帮我安排”被归为 edit_plan，直接生成而未查询/代选，报“请先选择想去的景点” | 此前实际任务与回放复现；本轮确认相同的模式分流仍存在，未重复调用外部模型 |
| E2 | 高 | 模型主执行循环只暴露读工具，缺少选择、删除、替换、计划生成、撤销等完整编辑工具 | `goal_agent.READ_TOOLS` 与 execute 路径检查 |
| E3 | 中 | remaining 代选只要已有一个景点就跳过景点补充，不判断是否足够组成完整旅行 | `auto_selection.run()` 中 spots 条件 |
| E4 | 中 | 一日行程在自动安排住宿路径中仍被跳过；直接酒店查询已经允许一日住宿 | `auto_selection.py:181` 与住宿查询路径不同；需要补“一日游、住一晚、次日走”入口场景 |
| E5 | 中 | 对话选择住宿缺少按具体夜晚明确分配的完整合同；选择 ID 路径未透传 stay_date/stay_dates | 意图合同与 `execute()` 的 select_ids 参数检查；UI 某些逐晚路径已支持，不能混为全部不支持 |
| E6 | 中 | day_start/day_end 可被后端更新，但主意图 patch 合同没有完整暴露；撤销、跳过住宿等能力也未全面暴露给模型 | `intent_contract.py` 与业务处理支持范围不一致 |
| E7 | 高 | 业务处理中先改状态，再查询或校验；失败之后通用任务处理仍保存工作区，可能保留半完成改动 | `main.perform()` 失败分支到统一保存的路径；需按操作区分可保留的查询结果与必须回滚的编辑 |

这些问题说明需要补齐“执行能力与状态边界”。单独增加意图关键词、把 edit_plan 改名、强行设置 delegate，无法解决所有真实场景。

### 4.3 仍需专项验证的边界与性能

- 用户固定时长、固定日期和已预订条件，应和系统建议区分；现在部分约束仍是文本，不能声称已实现完整锁定。
- 入住时刻可讨论但没有完整结构化编辑路径；调整时间工具与旅行条件中对休息时长的边界也需统一解释。
- `plan-view.planMinute()` 不接受 `24:00`，而计划生成存在午夜截断。需补该合法结束边界的显示检查；源码可见，不声称已复现整页崩溃。
- 批量候选缺失坐标、路线查询失败后的重试与状态保存，需要入口级验证，避免在“保留选择”的文案下发生隐性状态变化。
- 外部 API、模型轮次、路由查询、缓存、队列等待分别记录耗时，再决定优化。不能直接认定供应商慢，也不能为加速取消有效限速或日期核验。
- 房型详情、天气等补充查询是否在不必要的操作中被重复触发，需要从真实调用路径计量。当前已有部分按需处理，不能一概认为每步都重复查询。

“未接入风险”和“本机实际缺陷”必须在任务清单中分开，避免为了修一个本机不存在的问题而引入整套新功能。

## 6. 编辑能力补齐的目标

模型应作为统一旅行助手，根据目标使用工具，查询、编辑和生成可以在同一个任务中衔接。权限应落实到工具与状态提交，模式标签只能提供上下文，不应成为无法跨越的业务阶段。

建议最小能力组：

| 能力组 | 所需操作 | 边界 |
| --- | --- | --- |
| 观察 | 获取完整旅行状态、候选、正式计划、建议时间轴、固定约束与数据有效性 | 正式数据、建议与未知项可区分，避免只给页面摘要 |
| 查询 | 按独立条件查询景点、酒店、餐饮、交通、天气与资料 | 保存查询结果可以；不擅自覆盖正式旅行条件或选择 |
| 修改条件 | 设置条件、追加/替换/移除偏好 | 返回受影响的安排和报价，不能清空所有选择作为通用失效策略 |
| 修改选择 | 添加/删除/替换景点、按夜晚修改住宿、按餐次修改餐饮 | 使用真实 ID；保护未授权修改的选项；房型和往返票仍可选 |
| 修改日程 | 改日期、顺序、合理时长、开始下限、休息和餐次建议 | 用真实交通与开放信息校验；不能改已确认约束来掩盖冲突 |
| 生成与修订 | 从当前状态生成完整计划，局部重排并核对 | 只在成功提交后说明完成；失败保留可用旧版 |
| 恢复 | 撤销、继续未完成任务、取消本轮 | 区分已完成步骤、失败步骤与待执行步骤，不重复执行已成功操作 |

这些首先是项目内部可调用工具，不默认要求新建 MCP 服务。已有 MCP 保留真实查询与资料来源职责。

授权规则：用户明确“帮我安排、替我修改”应视为授权范围内的操作请求，不每步重复确认。未知的重要条件或需要改变用户固定约束时再询问。选定不等于预订，工具不能自动执行购买或把推荐当成预订成功。

## 7. 推荐目录结构与迁移边界

保持当前 Python/FastAPI、前端技术和本地启动方式，不同时进行 Vue 迁移或数据库平台迁移。以下是建议结构，执行时按依赖核对，不为分层添加空壳。

```text
app/
  main.py                   # 启动、生命周期、路由组装
  core/                     # 配置、公共错误、基础文本/时间约定
  api/                      # 账户、旅行、任务、导出等 HTTP 接口
  agent/                    # 意图、上下文、执行循环、工具合同、提示词
  travel/
    requirements/           # 需求更新与偏好操作
    recommendations/        # 景点/住宿/餐饮推荐与候选核对
    selections/             # 选择、逐晚住宿、餐次关联与撤销
    planning/               # 提案、路线、排程、校验、修订与导出
  integrations/             # LLM、高德、天气、途牛与外部 MCP
  knowledge/                # 语料、采集、Embedding、索引、检索
  persistence/              # 数据库、工作区、任务和缓存保存
frontend/
  index.html
  api/                      # 请求、流式事件和连接恢复
  state/                    # 工作区状态与视图状态
  views/                    # 景点、住宿、交通、餐饮、计划书
  components/               # 候选卡片、地图、时间轴、弹窗
  styles/                   # 基础、布局、组件样式
tests/
  unit/
  integration/
  scenarios/
scripts/
  dev/
  data/
  checks/
  release/
docs/                       # 当前设计、协作、发布、参考与历史记录
data/catalog/               # 可提交的目的地资料
data/knowledge/             # 可提交的来源语料
data/runtime/               # 忽略的数据库、索引、模型缓存和运行文件
repository-backups/         # 忽略的本机备份
```

目录中每个子组必须有实际责任。若一组只有很少简单文件，不继续细分；`travel/requirements` 等可按实际规模作为包或模块，不硬凑目录层级。

### 主要旧模块的归属

| 当前模块组 | 新归属与拆分方向 |
| --- | --- |
| main、auth | API 与任务服务；认证校验和 HTTP 路由分开；main 只组装 |
| agent、goal_agent、auto_selection | 统一 agent 执行器与工具注册；具体查询/修改调用旅行服务 |
| intent_contract、contracts、prompts、replies、guidance | agent 合同、提示词与结果呈现；日期基础逻辑归公共时间模块 |
| discovery、spot_candidates、recommendation_context、access、locations、enrichment、price_hints | 旅行推荐与候选核对；避免外部获取和业务筛选混用 |
| choices、stay_plan、foods、meal_flow、journey | 旅行需求、选择、逐晚住宿与餐次；页面阶段提示从核心修改服务中分离 |
| planning、schedule、pacing、visits、visit_analysis、time_policy、transport_links | 计划提案、路线资料、排程与时间规则；明确输入与输出 |
| proposals、plan_revision、timeline_tools、timeline_review、travel_review、travel_preview、schedule_quality、plan_warnings、diagnostics | 对应计划编辑、预览、程序校验、模型审查及结果分类；合并重复责任，不要求一个旧文件对应一个新文件 |
| report | 统一计划导出，使用同一份可解释的数据版本 |
| providers、integrations、tools、mcp_server、maps | 外部接口客户端、MCP 接入/暴露与地图；主模型编辑工具和外部查询工具分开 |
| knowledge、knowledge_collection、public_fetch、public_directory、data_coverage、data_contracts、embeddings、vector_index、rag | 知识服务，资料覆盖与查询合同边界清晰 |
| storage、request_cache | 持久化，工作区、任务、缓存分清楚 |
| config、data_settings、text | 公共配置与基础能力，业务规则不继续堆进公共工具文件 |

迁移时需特别核对：`config.ROOT` 当前依赖文件层级；搬进子目录不能继续沿用旧 `parents[1]`。静态资源路径、启动脚本、测试导入、MCP 启动路径和索引路径都需要配套更新。`.env`、数据库和模型缓存默认位置保持稳定。

允许短期兼容入口用于过渡，但阶段结束应移除无用转发和旧实现，不长期靠双套入口增加维护负担。

## 8. 分批实施与验收

| 阶段 | 做什么 | 完成标准 |
| --- | --- | --- |
| 0：基线 | 核对上传内容、整合有效差异、创建正常 Git 基线与重构分支、源码/配置/数据库/索引备份 | 未上传内容有归属；可按提交与备份恢复；已知问题有记录 |
| 1：状态修复 | 优先 S1–S4，统一需求更新、选择与取消入口，定义报价失效和修改提交边界 | 查询不改变选择；无关条件不清空班次；取消住宿同步关联；偏好操作含义明确 |
| 2：后端整理 | 先迁移低耦合知识/接口/持久化，再拆动作处理、计划流程和 HTTP 任务 | 正常启动与既有接口可用；不同时改变业务行为；无永久重复实现 |
| 3：编辑执行 | E1、E2、S5 及 E3–E6；完整观察、查询、编辑、生成、撤销与继续 | 用户授权后能完成目标；部分失败准确报告；固定安排保护到工具层 |

## 9. 必须覆盖的真实场景

验证分为纯逻辑、入口流程、浏览器、有限模型评估。使用合成数据与接口模拟为主，不创建镜像实现的重复测试。

- “玩两天、12号走、车票不用管、其他帮我安排”：授权范围内查询、代选并生成，不要求先手选景点。
- 仅比较另一日班次：正式日期、已选班次与计划保留。
- 修改房间数、游玩天数：只更新真实受影响项，不清空无关选择。
- 更换某一晚酒店、取消酒店：逐晚分配、房型与路线锚点一致。
- 一个景点已选但不足三天：继续补充；一日游住一晚次日走：可以安排住宿。
- 替换偏好、排除某类活动：不会不断追加互相冲突的偏好。
- “换第二天景点、找附近午餐、更新计划”：多步工具执行、结果观察与完成条件正确。
- 中午/下午到达、提前返程、明确固定游玩时间：调整可变安排，无法满足时不压到无效时长。
- 失败发生在修改中间：正式状态一致；已取得的候选可以作为部分结果，不能把未完成目标写成成功。
- 撤销、刷新、恢复、跨工作区：不串用旅行状态，不重复已成功步骤。
- 父子景区、缺坐标、资料不覆盖、无新候选：不重复估时，不编造地点，不隐藏旧选择。
- 计划章节、空时间、午夜结束、地图按需加载、报价过期与导出：展示与事实口径一致。

性能评估记录接口调用次数、缓存命中、模型轮次和各阶段耗时；改进前后使用相同条件比较，保留失败路径，不只看一次成功请求。
