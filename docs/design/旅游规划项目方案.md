# 识途：通过对话逐步构建旅游计划

日期：2026-10-05。状态：第一版真实项目已实现并完成浏览器联调；本方案同时包含后续目标。实际已实现范围及边界以 [README.md](../../README.md) 和 [开发状态.md](../status/开发状态.md) 为准。

用户对展示页面的反馈确定了默认先选景点与体验，再按景点分布、交通、住宿环境推荐住宿，以及最终交付完整旅行计划书的主线。2026-10-05用户提供目录中的 `.env` 与途牛文档，第一版已用实际配置完成只读验证与开发；当前网页版计划书支持 Markdown 导出和打印/PDF，尚有景区规则、费用与接驳等待完善内容。

用户已有途牛 MCP、高德 API、和风天气、DeepSeek。旧 HTML 用于说明交互意图；本方案不评审演示内容，也不把前一版模块清单当设计约束。官方参数和能力边界见 [官方接口核对](../reference/官方接口核对.md)。文档核对与所用接口的最小实际调用已完成，不代表所有能力、额度和边界均已验证。

## 1. 产品围绕正在形成的旅行计划展开

用户需要的是有人带着他比较、选择，并把选择组织成行程。系统每轮回答都应推动一个具体决定，同时保留已经做出的选择。

核心对象是“旅行工作区”。它包括当前需求、候选、用户决策、行程草稿、预算和需要处理的事情。聊天是操作工作区的入口，右侧候选卡片、地图、草稿是同一份业务状态的不同展示。

默认流程为：理解需求 → 景点与体验推荐 → 用户标记必去、想去、备选 → 按日期和区域形成初步游玩分组 → 推荐住宿区域及酒店 → 补齐往返交通与餐饮 → 校验和协商调整 → 交付完整旅行计划书。

交通的到达与返程时间应作为早期可用时间约束逐步确认，避免先排满日程再发现无法到达；用户不必先选好交通才能比较景点。景点意向确定后才进入主要住宿推荐。

已有交通或住宿的用户保留预订，按已有位置与时间反推适合的景点。用户主动希望先找酒店时允许跳转。完成计划不要求把所有候选类别逐个填满；没有确定的部分保留为弹性安排。

每轮应做到：理解本轮要做什么 → 找出缺少的必要条件 → 取得对应数据和资料 → 展示少量可比较候选 → 解释推荐与取舍 → 等待选择 → 更新工作区。一次输入里已经给出的条件不再重复询问。

## 2. 一次具体交互

以下只是业务示例，不含真实报价或天气结论。

用户：“从上海出发，想带父母去青岛玩三天，别太累，预算大概六千。”

系统先提取城市、三天、同行人、节奏和预算。对“六千”保留总预算/人均的待确认状态；查询交通和住宿需要明确日期，先问日期和人数等关键缺项，而不先追问所有偏好。

条件足够后先推荐景点与体验，结合真实 POI 和检索资料介绍特色、取舍及游览规则。用户标记“必去”“感兴趣”“备选”；系统按体力、可用日期和区域初排，指出无法兼顾的组合。

再根据这批选择介绍两三个适合住宿的区域：往返景点是否方便、接驳和步行负担、预算，以及用户在意的景观与休息环境。结合途牛酒店与房型信息展示候选。“临近海边”与“房间能看海”分别描述，后者需要具体房型证据。

用户选房型后，更新各日出发点和通行段，再补齐交通、餐饮及休息。选酒店可以促使用户调整某个远距离景点；调整要解释影响，由用户决定。

用户：“第二天不去这个景点，换成室内的。”系统理解这是局部修改，检索与查询室内候选，展示替换后的通行、预算和时间变化。用户接受后形成新版本，其余选择保留。

## 3. 状态比聊天记录更重要

不让模型从长聊天记录里反复猜“用户到底选了什么”。建议持久化以下业务对象，命名属于项目内部设计，不是供应商字段。

| 对象 | 内容 | 原因 |
|---|---|---|
| 需求 | 日期、人数、预算口径、偏好、硬约束；记录已确认/暂定/缺失 | 区分“想要”与“必须满足” |
| 候选快照 | 查询条件、来源、查询时间、候选内部 ID、外部 ID、实际字段 | 支持比较，避免模型编造候选 |
| 决策 | 收藏、选择、拒绝、用户自行处理；理由和对应快照 | 保持用户选择，支持撤销 |
| 行程草稿 | 日程项、关联候选、通行段、开放约束、缓冲、版本 | 让计划逐步形成并能局部修改 |
| 待处理事项 | 日期缺失、价格未确定、超预算、路线失败等 | 让下一步有明确目标 |

途牛商品 ID、高德 POI ID、知识文档 ID 使用不同命名空间。内部候选 ID 绑定这些来源，不要求模型凭空生成外部 ID。按钮携带候选 ID 和工作区版本；后台校验归属和新鲜度，避免旧卡片覆盖新选择。

用户改变出游日期后，相关酒店/交通/门票快照标为需要更新，保留选择意愿；用户改变一家餐厅后，只更新受影响的餐段和路线。系统通过依赖关系判断更新范围。

## 4. Agent 的职责：按需协作，程序检查可执行性

角色分工是候选设计，不要求第一版把每个角色都实现成独立 Agent。根据用户对规模及审核的最新考虑，第一版建议采用主 Agent 加按需运行的审核 Agent；资料查询和规划先作为主流程中的工具及任务步骤。只有实际出现上下文负担、工具选择困难或独立评估需求时，再拆分资料/规划 Agent。可以使用同一个 LLM，通过不同提示词、工具权限和上下文分工，不要求每个角色配置不同模型。

| 角色 | 工作 | 输出与边界 |
|---|---|---|
| 主对话 Agent | 意图识别、条件提取、必要澄清、派发任务、解释取舍和理解修改 | 任务与建议；用户选择和预订状态由业务服务保存 |
| 资料 Agent | 按当前问题调用 MCP/API 与 RAG，整理地点、规则、报价和相关知识 | 带来源、时间和未知项的候选；不能凭常识补齐缺失事实 |
| 规划 Agent | 基于用户选择与约束组织日期、顺序、交通方式、用餐和休息，处理校验反馈 | 结构化日程草稿及建议理由；不能覆盖用户已确定的安排 |
| 审核 Agent | 检查是否遗漏需求、推荐与证据是否一致、计划书是否易用 | 问题清单；不取代程序对时间、预算和固定约束的检查 |

每轮只调用需要的角色。例如介绍景点使用资料 Agent；选定已有卡片主要更新业务状态；生成行程使用规划与校验；修改餐厅只更新受影响的餐段和路线。独立资料查询可并行，存在依赖的步骤按序执行，住宿推荐默认等待景点意向确定。工具调用额度、迭代次数和超时由程序控制，各 Agent 共享事实与决策状态，但只接收本次任务必要的上下文。

后端处理：供应商请求、参数校验、限流、候选保存、报价口径、决策写入、预算计算、时间冲突、版本管理。LLM 提议结构化动作，后端验证后执行。卡片上的价格和时间由保存的事实数据渲染，说明文字绑定证据；模型描述中的新增事实也要检查，不能靠“只输出 ID”宣称消灭所有幻觉。

建议内部动作覆盖查找、比较、选择、修改条件、修改日程、解释、生成草稿。这些是应用意图，不是新增的官方 MCP 工具名称。

排程采用“LLM 提案 → 程序校验 → 有问题时回传具体原因 → 有限次修订”。第一版程序重点检查日程重叠、实际通行时间是否留足、已知开放/预约窗口、返程时间、用户硬限制和预算口径。关键规则缺失时保留待确认状态，不能把“未发现冲突”称为已验证可执行。达到重试上限仍有冲突时，向用户展示取舍，不能无限反思或偷偷删掉必去项。

开发需要明确业务流程、角色职责、输入输出和校验规则；不需要用提示词预写所有景点组合。LLM 在当前任务范围内做推荐和组织，业务服务控制步骤、状态与约束。提示词按角色和任务提供相关规则，不把整个方案及全部供应商数据每轮都塞给模型。

已核实的参考：HuangLianjin 的[架构文档](https://github.com/HuangLianjin/ai-travel-agent/blob/main/docs/ARCHITECTURE.md)描述按 `changed_fields` 派发最小子任务集及有限次反思；yufang-fan 的[工作流代码](https://github.com/yufang-fan/langgraph-multi-agent-trip-rag/blob/main/backend/app/workflows/trip_planner_graph.py)将 RAG、景点、天气、酒店查询分支汇合后交给 Planner。借鉴职责拆分与状态汇合；本项目按照逐步选择和先景点后住宿的交互调整依赖关系。多 Agent 自检不是新增独立事实来源。

LangGraph 可以组织状态更新、查询、推荐、等待用户、排程和修改分支。使用 checkpoint 保存进度，关键选择可以暂停后恢复；具体支持见 [官方 interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)。一般卡片浏览和翻页不必都暂停整个图，也可以作为普通请求操作工作区。

## 5. MCP 的职责：真实工具接入与能力发现

途牛直接连接现有远程 MCP。建立查询工具白名单，在启动或接入检查时保存 `tools/list` 的真实 schema，按照当前话题筛选开放工具。不改写官方工具名字再假装供应商提供了统一接口。

高德和和风是 HTTP API，可在项目侧通过一个本地 MCP Server 封装所需能力。内部 Python 客户端负责 HTTP、认证、超时和解析，MCP 层只负责暴露工具及其 schema。工具名称由项目定义，并明确标为自建封装；参数转换依据官方文档及实测，不把用户意图直接拼到 URL。开发期同一服务进程即可，不需要为每项能力部署独立服务。

MCP 规范提供工具发现和参数 schema，但不会自动统一各供应商业务含义。应用仍需要适配层，例如酒店列表与房型报价、火车城市搜索与车站详情，以及跨平台地点匹配。见 [MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。

RAG 检索可以作为本地业务工具给 Agent 调用；需要跨客户端复用时，再通过同一 MCP Server 暴露。项目会实际使用 MCP 查询与 RAG 检索，而不是只在文档中列出名称。

## 6. RAG 的职责：让介绍和推荐有依据

RAG 在用户做选择时就参与：回答目的地区域有什么差别、候选适合怎样的玩法、选择某景点需要注意哪些规则。生成最终路书只是其中一个用途。

第一批知识优先包含城市与区域介绍、景点特点、官方游览规则、交通接驳说明、游览与休息建议。通过少量认真整理的目的地内容形成可展示的检索闭环。优先官方景区/文旅/博物馆资料；授权明确的经验内容可以作为经验来源。模型总结不能作为独立证据来源。

文档按景点、区域和主题组织，切片保留来源 URL、标题、获取时间、适用地点、适用条件和内容类别。获取时间不等于内容发布时间；未知时间需保留未知。预约规则等动态内容和文化背景等稳定内容使用不同新鲜度策略。

检索流程为：依据本轮问题和候选构造查询 → 按城市/实体/主题过滤 → 关键词与向量召回 → 排序 → 把少量片段交给模型 → 推荐理由关联引用。体力和适合人群等推断应标为建议，不能伪装成 API 的事实标签。

实时价格、余票不依赖向量检索。已选商品与报价进入业务库。用户会话状态也进入业务库，不能混入公共攻略知识库。

## 7. 数据在一次选择中怎样组合

| 决策 | 实时或结构化数据 | 检索资料与程序计算 |
|---|---|---|
| 怎么到达 | 途牛国内机票或火车查询 | 程序比较到达时间、费用口径及可用游玩时间 |
| 住哪里 | 途牛酒店/房型；高德地点与路线 | RAG 解释区域；程序比较去已选景点的通行情况 |
| 去哪里 | 高德真实地点；途牛门票起价 | RAG 提供特色与规则；按用户偏好和已有安排推荐 |
| 吃什么 | 高德餐饮地点及实际返回的商业字段 | RAG 提供菜系与经验；程序限制地点和预算 |
| 怎样安排 | 高德路线、可用天气预报 | 排程算法检查时间、休息、开放窗口和冲突 |

以上能力依赖账号实测结果。餐厅完整评论、真实客群构成、指定日门票准确价等尚不能由当前已核对接口保证。缺字段时缩减卡片，保持正常决策过程。

事实不必一律标 A/B/C/D。初版更适合展示来源、查询时间、适用日期，以及“供应商起价”“查询时可售”“工具预计”“资料建议”“待核实”等直观状态。调用成功不代表所有字段都准确或覆盖指定日期；推荐依据需要字段级出处。

## 8. 行程生成和修改

### 8.1 最终交付：一份完整旅行计划书

产品交付包括可编辑的网页版计划书，以及与当前版本一致的打印/PDF 路书。工作区的卡片与时间轴用于讨论；计划书汇总形成可直接使用、保存和分享的结果。

计划书结构：

1. **旅行概览。** 目的地、日期、同行人、预算口径、节奏与偏好，以及已确认和暂定条件。
2. **方案说明。** 选择哪些景点、怎样分天、为什么住这个区域，以及关键取舍。
3. **全程总览。** 每日主题、主要地点、住宿、通行与休息，附总体地图。
4. **逐日执行安排。** 时间段、地点、怎么玩、建议停留、下一段交通、用餐与休息、当天开销、预约与开放提醒；避免精确到分钟的虚假确定性。
5. **交通与住宿。** 用户已订/仅选方案分别标明，列出到达返程、接驳、酒店位置、房型、餐食和退改的已知信息。
6. **预算明细。** 已查报价、起价、估算、已支付与尚未确定项分开，包含按人、按房、按晚的计价口径和费用余地。
7. **备选与变化应对。** 雨天、体力不足、迟到或景点不可用时的替代及其影响。
8. **出发清单与待办。** 需要预订/预约、待核实规则、装备、官方核实入口。
9. **资料与版本。** 重要信息的来源、查询/采集时间、适用日期、生成版本与修改记录。

计划书由已保存的需求、用户决策、校验后的日程和证据共同生成。数字、地点与选择从结构化数据渲染，模型补充解释和描述；不能临到导出再让模型另写一份与已选内容不一致的攻略。用户修改后，网页版与导出版本同步更新。

### 8.2 景点决定住宿推荐的依据

先看每天要去的区域，再比较候选住宿区与少量酒店，使用实际路线估计通行；不只按几何中心或最近距离排序。考虑每日通行总负担、最远一段、车站/机场接驳、夜间返回、步行偏好、住宿预算和环境。

展示不同取舍，例如“去已选景点更方便”“住宿更便宜但通行增加”“附近景色更好但部分景点较远”。价格、时间和房型景观有对应来源；安静、适合休息等建议与证据区分。模型不能从临海坐标推断海景房。

用户已有住宿时，将其作为约束保留。景点变动后仅重算受影响的比较和路线，先说明是否值得考虑换住宿，避免自动推翻已选内容。

### 8.3 生成与修订

用户选择先作为时间和地点约束。系统根据可用时间、地域聚类、必去项、交通方式和节奏形成候选日程，再查询需要的路线，调整顺序，检查开放窗口、饭点、返程、休息和缓冲。

开始不需要求全局最优 TSP，也不为全部候选计算两两路径。先把地点分组和粗排，只查询进入草稿或比较所需的通行段。路线是工具估算，游玩时长和缓冲是建议值，两者分别标明。

预算保留已查报价、起价、参考消费和待确定项。明确总预算还是人均，区分按人、按房、按晚、按车计价，不把估算加总称为已确定费用。若无法满足预算或节奏，输出可选择的调整方案。

修改先生成待接受的变更：删除/加入哪些项、为什么、时间与费用怎样变化、还有哪些未知。用户接受后保存新版本，支持撤销。用户明确要求直接采用某个变更时，可以直接应用并说明结果，避免每个小操作都再次确认。

## 9. 请求成本与数据更新

途牛公开文档的 API Key 配额较小，见 [限流页](https://open.tuniu.com/mcp/docs/guide/ratelimit.html)。服务端要维护账号级调用预算和限流，候选搜索一次后供用户浏览，展开少量详情，修改关键条件才重新查。失败重试必须受次数和额度约束。

在供应商允许范围内，按查询条件保存响应快照和有效期；不同数据采用不同更新策略。浏览起价可以用明确标时的旧快照，最终选择可刷新相关报价，但刷新仍不是保价或库存预留。同轮用户选择、工作区提交等操作不应重复请求外部供应商。

天气超过预报范围就标尚不可预报。第一版在用户打开计划、修改相关日期或主动刷新时检查可用数据。后续需要订阅监控时，再按出发时间和实际配额设计后台任务。当前预警、余票查询、景区开放资料是不同来源，不能把它们笼统实现为一个全天持续监控功能。

## 10. 技术建议与实现顺序

建议 Python 后端，以 FastAPI 承接会话、卡片动作和流式事件，LangGraph 管理规划分支，MCP Client 连接途牛及自建工具服务。业务库和检索存储通过接口解耦：开发时可以用 SQLite 加本地向量索引；需要部署、多用户和统一管理时再用 PostgreSQL/pgvector。是否引入 Redis 依据实际任务调度和缓存需求，不作为启动前置条件。

前端先拆分聊天、候选、地图和计划工作区。框架选用户熟悉的 React 或 Vue 即可。按钮发送明确动作和候选 ID，服务端返回结构化卡片及状态变更；不用让模型生成 HTML。LLM 提供商尚未知，具体调用方式待其官方接口核对。

分四个可验收的交付推进：

1. **接口验证与首批景点资料。** 使用现有环境配置验证真实能力，导出途牛 schema；以一个城市做资料样本，支持真实 POI 加有出处的介绍、规则及检索。验收能按需求推荐真实地点并让用户选择。
2. **景点 → 住宿 → 计划书的完整业务闭环。** 景点意向与分组驱动住宿区和酒店比较，用户选房型；加入路线、天气、餐饮和预算，生成网页版完整计划书及 PDF/打印导出。验收计划书与用户选择一致，包含待确定项。
3. **往返交通与局部修订。** 完成班次/舱位/席别选择、到达返程约束与接驳，支持已有预订、预算取舍和雨天变更，计划书随修改更新。
4. **覆盖与可靠性扩展。** 扩展景点资料和目的地，完善恢复、撤销、限流和失败降级；测试未知日期、无票、数据缺失、地点歧义等场景。

验收重点是用户选择是否保留、推荐是否有出处、修改是否影响正确范围、行程约束是否满足，以及每次规划成本是否可控。用相同用户需求对比“直接让 LLM 写攻略”和本系统，记录来源覆盖、工具支持字段、用户完成选择的轮数、响应耗时和实际调用量。不引用未经验证的行业错误率或开源项目自报成绩作为本项目效果。

正式编码前还需确定：用户实际途牛服务的 schema/认证/额度、各账号查询结果、LLM 提供商及模型、首个演示目的地和知识来源。这些会影响接口配置，但不阻碍当前业务设计。

## 11. 景点资料的收集与使用

景点资料由不同来源组合。高德用于真实地点查询；官方页面提供介绍与游览规则；途牛提供其覆盖的可售门票产品。对免费景点、街区、公园和博物馆，不能以“途牛有门票商品”作为能否进入候选的条件。

| 资料 | 起步来源 | 使用方式与边界 |
|---|---|---|
| 名称、地址、ID、坐标及实际返回的商业字段 | [高德 POI 2.0](https://developer.amap.com/api/webservice/guide/api-advanced/newpoisearch) | 按城市与类型查询，绑定实体；字段覆盖须实测。不把人均消费当准确门票价 |
| 景点种子与类别 | 当地文旅、政府介绍栏目；[文旅部数据服务](https://sjfw.mct.gov.cn/site/dataservice/base) | 补充可信候选名录；A级名录只覆盖部分旅游地点，并非全国完整实时景点库 |
| 特点、历史与体验说明 | 景点/博物馆/当地文旅官方页面 | 按实体整理资料，进入检索库，生成带引用的介绍 |
| 开放、停止入场、闭馆日、预约与游览限制 | 场馆参观须知和最新官方公告 | 同时抽取成带来源的结构化约束，排程可检查；发布时间未知、已过期或冲突时不能默认有效 |
| 门票商品与报价 | [途牛门票工具](https://open.tuniu.com/mcp/docs/apidoc/mcp/ticketMCP.html) | 以实际可查字段展示，区间起价与指定日售价区分；商品与景点核对匹配 |
| 停留建议、体力负担、亲子/老人适配 | 人工整理及有出处资料上的推断 | 标为建议，记录依据与未知项；不能声称已验证设施或无障碍通行 |

第一批先做一个城市约15–25个地点，覆盖海边/自然、街区、公园、文化场馆、付费体验和室内备选。这个数量是起步工作量建议，不是API提供的覆盖承诺。暂以青岛作为验证案例，后续目的地可以扩展。

本次已找到可用的官方资料入口：

- [青岛文旅特色景点栏目](https://www.qingdao.gov.cn/yfqd/qdwl/cjfw/wyqtsjd/)：包含景点列表，另有海边、公园、博物展馆等分类入口，可辅助建种子目录。
- [青岛市博物馆参观服务](https://www.qingdaomuseum.com/visit)：提供参观公告、开放及讲解信息，可验证规则抽取与排程约束。
- [崂山景区官方网站](https://qdlaoshan.cn/Index-index.html)：有景区介绍、票价与临时通行/预约公告入口，可验证动态规则更新。不能直接使用旧公告价格作为当期价格。

这些是公开网页资料入口，本次没有验证公开批量API或取得完整数据导出。采集时逐站确认获取方式和使用范围；首批可以人工辅助整理、校对，允许采集的页面再编写定向更新脚本。不依赖大规模抓取社交攻略作为启动前置。

收集流程：种子地点 → 高德匹配与去重 → 关联官方来源 → 保存原始资料及元数据 → 抽取结构化规则与知识片段 → 人工校对关键规则 → 建关键词/向量索引 → 按规则类型更新。API结果按供应商允许的范围缓存和使用，不视为可无限期复制的公共数据集。

每条资料保存来源URL、发布/采集时间、适用实体、适用日期、证据段落与处理版本。稳定背景知识与动态公告分开；抓取日期不等于内容最新。模型可以协助清洗和抽取，出处和规则核对仍需保留。

## 12. 现在是否可以开始

可以开始数据验证、基础业务实现和首批资料整理。项目主线足以开展迭代开发，不能宣称接口和景点覆盖已经验证完备。

用户提供业务反馈和本地环境配置位置。开发者负责配置项核对、官方schema比对、最小调用验证、景点资料整理及系统实现。密钥值不进入聊天、报告或Git；不要求用户自行设计各技术模块。

第一条真实交付应贯穿景点介绍与选择、基于景点的住宿推荐，以及最终完整计划书。先完成一个城市的这条闭环，再扩展覆盖。技术基础和资料采集可以并行推进，未核实字段要保留未知。

## 13. 把不同事件组合成可执行日程

本节将用户新增的时间组合、购票/预约不确定性、路线方式选择和其他业务问题纳入统一规划机制。这些是应用业务模型，字段并非声称供应商API直接提供。

### 13.1 每个安排是带条件的事件

第一版用轻量事件记录，不要求一次建模所有场景，也不要求用户填写这些字段。基本记录包含：

- 类型与关联候选 ID，例如景点、交通、用餐、休息或固定预订。
- 日期与地点；入口可查时使用入口，未知时标出路径计算的局限。
- 开始/结束或允许时间窗口；未知规则保留未知。
- 时长或建议范围，以及用户重要程度、是否已确定。

来源、查询时间、选择/预订状态和待核实项复用业务数据，避免每个事件重复存一套。当天购票/预约条件关系到可执行性时必须纳入检查，不能因采用轻量模型而省略。其他扩展按场景触发：带行李才处理寄存，到达日才细化出站与接驳，带老人或孩子才增加相应休息与连续步行约束。没有触发时不强行细化。

后续需要时再增加参与者、行李、前置事件、内部接驳、天气适配与体力指标等字段。第一版主要采用少量日程项的粗排、路线查询和规则检查；复杂求解器属于后续能力。

购票截止日期属于出发前待办，入场预约时段属于当天事件，不能混成一个时间字段。景区允许入场窗口与游览结束前的闭馆期限分别检查。演出等固定活动不能随意压缩时长；柔性游览可以在用户接受的范围内调整。

### 13.2 固定条件、重要目标与可调整偏好

固定条件包括已有预订、已确认入场时段、返程时间、有效开放规则和用户明确不可改变的要求。它们若相互冲突，输出原因及需要由用户决定的变更，不能为了生成方案而忽略。

必去景点属于高优先目标，仍要检查能否买到票或完成预约；未取得名额时保持条件性安排并准备替代。少走路、晚起、清淡、景观、经济等按用户声明区分硬限制与偏好，不能把所有偏好当成随时可牺牲的软条件。

可调整项包括未确认景点顺序、适当范围内的停留时长、餐饮地点、弹性休息和交通方式。未知开放/库存等条件要保留未知；不能由排程算法推断查询已成功或预约已完成。

### 13.3 时间要算完整

下一项活动的可行开始时刻，需要考虑上一项结束、必要的准备、实际路线、必要的等待与缓冲，并满足下一项允许的窗口。活动结束也要满足闭馆等期限。

路线响应若已包含等车或步行，不重复计入相同耗时。出站、安检、取行李、景区内部接驳、排队和换乘准备等按有无覆盖单独处理。入口坐标与景区中心分开，住宿与酒店房间入住条件也分开。

同一参与者的出行和游览不能发生时间重叠。确实可兼容的安排，如列车上用餐，仅在用户接受且条件允许时组合。未到入住时间可以安排先寄存、附近用餐/游览，但寄存能力必须核实，不能默认酒店允许。

第一天依据实际到达时间、最后一天依据返程和接驳需求安排，不把它们都视为完整游玩日。跨午夜、跨日班次及当地时区明确处理。拥挤或拥堵估计用于缓冲情景，不冒充实时排队数据。

### 13.4 先形成可行组合，再比较体验

建议工作顺序：

1. 收集需求和已有预订，建立每天可用时间与必须满足的条件。
2. 取得真实地点和规则资料，让用户选择必去、想去和备选；及时检查相互冲突。
3. 依据开放/预约窗口和地理位置初排日期与区域，不直接锁死全部顺序。
4. 推荐少量住宿区域与酒店，以景点通行、接驳、环境和预算解释取舍。选酒店后更新日程起终点。
5. 对需要比较的通行段查询步行、公交/地铁、驾车等实际支持的方式；结合餐饮和休息，检查完整日程。
6. 先满足固定条件与硬限制，再提高重要体验覆盖、减少通行和体力负担、控制费用、增加余地。用户偏好决定取舍顺序。
7. 必要时展示两三个有明显差异的可行方案，并指出“少走路多花多少钱”“省钱会多花多少通行时间”等可核实差异；数据不足则说明未知。

技术上可采用时间窗口与事件约束排程，再结合路线搜索。OR-Tools 的[带时间窗口路线问题](https://developers.google.com/optimization/routing/vrptw)和[约束排程示例](https://developers.google.com/optimization/scheduling/job_shop)提供了相关基础能力，但旅游中的可选事件、多交通方式、规则缺失和用户修改需要自行建模，不能直接套用示例并声称保证最优。

实现时先用规则与有限搜索得到可行草稿，查询有限的候选路线并复核；复杂度确实需要时再引入约束求解器。排程要有耗时上限；超时保留已有可行草稿或说明尚未找到可行解。不把搜索未找到当成已证明绝无方案。

### 13.5 缓冲与冲突处理

每个时间段保留范围、余地和依据。固定班次/预约用确切时刻，弹性事件尽量展示时间段。缓冲依据换乘、同行人、行李和可用数据设置；固定建议值标为规划假设，不声称是实测延误分布。

生成后至少复核常规情景和保守情景：某段通行变慢、前一事件延长或排队增加时，重要预约和返程是否仍可赶上。不具备统计依据时不输出“成功概率”。

冲突要解释具体原因，并提供可执行取舍，例如移动到另一天、换临近地点、调整交通、减少可选项目或降低停留时间。不得自动删除用户的必去项、取消预订，或以零通行/零等待伪造可行性。所有用户条件同时无法满足时，明确列出需要放宽的条件。

### 13.6 变化时保留已确定内容

时间、天气、库存或用户需求变化后，从受影响事件沿依赖关系检查。已经完成的活动和不能改的预订优先保留，重新安排未执行的部分；如果影响会传播到后续日期，也要明确说明，不能承诺所有变化都只影响一天。

修改预览包含：原安排、替代、通行与费用变化、预约是否需要重做、受影响的其他事件和待核实条件。用户接受后保存新版本，最终计划书同步更新。用户明确指令可以直接执行相应可逆变更，再报告影响。

## 14. 出行不确定性的统一处理

### 14.1 事实、推断与行动

每个重要事项同时保存“当前事实”“适用范围与未知”“建议或下一步”。例如查询时有票属于当前事实；未来能否买到、是否能买到邻座需要其他证据；购票入口和备选班次属于可执行行动。

| 问题 | 起步处理 | 不应宣称的能力 |
|---|---|---|
| 车票与航班 | 按实际可查席别/舱位展示可售状态和查询时间，给备选时段；已订信息由用户确认 | 凭单次余票给出抢票成功率、保留库存或邻座承诺 |
| 门票与预约 | 区分收费、预约政策、放号/截止、入场时段、实际名额和用户完成状态 | 商品可售等于预约已完成，区间起价等于当天价格 |
| 人多与排队 | 优先官方客流/活动公告；没有实时来源时展示有依据的拥挤预期和保守时间预留 | POI评分、热度或历史评论等于当前人数 |
| 交通方式 | 比较整段时间、费用、步行、换乘及同行人数，保留合理备选 | 驾车时长包含网约车叫车等待，预估出租车费等于实时网约车报价 |
| 住宿 | 对已选景点与接驳比较位置、费用和有出处的房型特点 | 临海位置必然有海景房，评分必然代表安静或适合所有人 |
| 同行人与预算 | 累计体力/步行，区分儿童与成人规则、行李、房间、额外项目及费用状态 | 成人价自动适用于儿童，未知设施直接标无障碍 |

关键未知影响重大预约或返程时，突出提示并保留条件性安排；一般未知以待办方式展示。日期远超天气预报范围时仍可排程，但天气条件保持待定。关键事实更新与提醒频率根据出发日期、实际配额和用户订阅决定，不无条件反复查询全部数据。

### 14.2 最终计划书应呈现什么

每日日程包括事件时间段、玩法、交通、休息、必要准备与缓冲；同时标出已订、已预约、仅选定、待确认和备选。关键事项列出核实/购票入口、适用日期、需要处理的时间以及未完成时的替代。

推荐理由简要说明当前选择解决了哪些问题和牺牲了什么。初始对话只问当前决定所需信息，自动利用已有条件，偏好逐步补充，避免前置长表单和每个细节都要求确认。

### 14.3 开发验收样本

- 上午到达、下午固定预约：出站、行李、用餐、接驳与入场准备能完整衔接。
- 酒店尚不可入住：只有确认可寄存时才安排寄存；否则提供可用替代。
- 固定活动与返程冲突：解释冲突，给出取舍，不强行排入。
- 景点闭馆/停止入场/预约时段：分别校验，不只检查当天是否营业。
- 带老人或孩子：累计步行、连续活动、休息与午休约束合理。
- 交通变慢或游玩延长：检查后续预约余地，并提供局部调整。
- 余票/门票变化、天气超范围、拥挤度未知：保留事实边界、待办和备选。
- 用户替换或删减一个事件：已有预订与其他有效安排保留，受影响部分和计划书一致更新。

以上是后续实现的验收要求，本次只完成业务设计更新，尚未实现或测试真实排程服务。

## 15. 通过实际使用逐步完善

“模拟人制作攻略”属于用户探索过的构思，不是产品必须采用的架构；多 Agent 是可选手段，审核角色可按需加入。目标是小规模、可验证、可靠的旅游规划业务。没有实测依据时，不宣称当前架构是最优方案。

开发先检查用户实际持有的接口和权限，再围绕一个城市、一到两天的场景完成端到端流程：输入需求、查地点及少量知识资料、推荐与选择、按景点推荐住宿、组织日程、查询路线并检查、生成完整计划书。每批功能都应能在网页中操作。未接入能力明确显示演示或未知，不以模拟接口运行成功代替真实接口验证；交通、天气及其他能力按验证结果补入。该范围是开发建议，尚未得到用户对具体城市与场景的确认。

开发者可启动本地项目并通过可用的浏览器自动化实际输入、选择、修改和导出，查看页面、请求与服务日志。工具不可用时如实报告；不能把只读代码或 HTTP 成功当作完整体验通过。测试使用虚构的用户需求，不提交订单、支付或发送对外消息。真实数据查询需要配置与账号权限，并受调用额度约束。

用少量固定场景复核主要业务：带父母少走路、已有酒店/班次、预算限制、局部替换和数据缺失。浏览器操作验证交互，确定性检查验证时间和预算，人工核对少量来源验证事实；LLM 审核补充检查需求遗漏和推荐表达，不作为唯一验收者。界面审美、选择是否费力以及实际旅游体验仍需要用户反馈。修改后检查受影响的场景，不无条件重跑全部昂贵接口。

持续状态保存在 [开发状态.md](../status/开发状态.md)，只记录当前目标、用户已确定要求、建议、已实现/已验证与未验证内容、阻塞和下一步。该文件与本方案及官方接口核对构成恢复上下文的依据；每批实质变更后更新，恢复工作时同时读取当前代码与验证结果。最新用户指令优先于文件，过时决定应直接修订并注明替代关系，不能靠累积旧文档推断用户仍然认可。状态记录减少上下文丢失风险，不能保证绝无遗漏或错误。
