## 1. 问题陈述

**谁**：自由行用户。拿到识途生成的计划书后，进入"审阅与修剪"阶段。

**场景**：出发前 1–3 周在 PC 上逐日审阅；旅途中在手机上按日程执行。

**痛点**：AI 生成计划书成本极高（LangGraph 全链路）。但用户对一份 5 天计划的**局部不满意度同样极高**——典型情况 4.5 天满意、0.5 天不满意。

用户只有两条路：

- **A：忍了。** 自己在心里划掉那一项，计划书从"可执行的日程"降级为"参考材料"，产品价值归零。
- **B：重新生成。** 昂贵、慢，且**会把已满意的 4.5 天一起改坏**。这是所有 AI 行程产品最致命的缺陷——改一个点，赌上整份计划。

**为什么现有方案不行**：市面没有一款产品同时做到"局部可改"和"改动可核查"。要么只能整体重新生成（马蜂窝 AI 路书：生成 40 分钟、每日限 1 次），要么只能手工从零搭建（穷游行程助手：编辑 3 天行程平均 12 分钟，自定义景点需手填全部信息），要么是预订归档而非规划工具（TripIt/携程：不检查绕路、不检查闭馆、不检查交通耗时）。

### 1.1 一句话定义真问题

> **块级编辑让"局部不满意"可以被局部消化，而不必赌上整份计划书。**
> **攻略资料展开让"AI 为什么这么排"变得可核查，而不必盲信。**

两者合起来：把 AI 的角色从**"代我决定"**降级为**"给我一份可核查、可修剪的草稿"**。

本质是**可控性（agency）+ 可核查性（verifiability）**，不是"编辑功能"。

## 2. 目标用户

### 主要画像：自由行规划者

| 维度 | 描述 |
|------|------|
| 年龄 | 25–40 岁 |
| 场景 | 国内目的地自由行，首次或低频前往该目的地 |
| 设备 | 规划期 PC 为主；执行期手机为主 |
| 技术水平 | 会用 AI 对话，但**不信任 AI 的事实陈述**（被幻觉坑过，见附录 A） |
| 真实诉求 | 要一份**能落地执行**的日程，而不是"看起来很美"的文案 |

### 次要画像 A：代规划者

帮家人/朋友规划，自己不一定去。需要能说清"为什么排这个景点"，**对 evidence 需求最强**。

### 次要画像 B：小众深度游用户

主动挖掘非热门地点。**遭遇 evidence 空态的概率最高**，空态降级对他们不是边角情况而是主路径。

### 3.2 参照竞品：圆周旅迹（Pi Travel）

横测中唯一提供 **AI 主动审查**（绕路 / 时间冲突 / 景点关闭）。长线场景下**"拖动节点立刻看到连锁反应"**——这正是本项目"时间链式累加"问题在竞品中的对应解法，已被验证为杀手锏。

> **级联可见化不是我们发明的解法，是已被市场验证的强需求。** 且我们已有更严谨的基础：`plan_revision.check()` 已在校验时间衔接、固定时段、day_end 三类冲突（见 6.3）。

测试数据显示：10 个用户用马蜂窝规划，7 人未发现至少一处时间冲突；穷游地图模式下约 60% 能发现路线问题，但**不到 20% 会主动搜索每个景点的实时开放信息**。
→ **用户不会自己去核实，除非你把核实材料摆到他面前。** 这是 evidence 展开的价值证明。

### 3.3 替代方案（交互范式参照）

| 参照 | 可借鉴 | 不可照搬 |
|------|--------|----------|
| **Notion 块编辑** | ① hover 出现六点拖拽手柄（progressive disclosure 佳作）② 所有块共享一套交互语汇 ③ 渐进披露 | 块类型转换、嵌套子块、slash 命令、duplicate——旅行日程不是文档 |
| **Linear** | ① **乐观更新** ② **撤销优先**（非不可逆操作不加二次确认弹窗）③ inline 反馈 ④ 键盘可达 | 暗色优先、极致信息密度、多人协同 |

> **口径修正（v3.0）**：Linear 式乐观更新在本项目中的正确形态是**"轻量乐观反馈"**——被改块的数字立即变化 + 后续块标记"重算中"，**不做时刻预演**。时刻由服务端权威计算后一次性渲染。理由：在前端复制一份级联逻辑等于制造两份真相，必然漂移（见 10.2）。

### 3.4 市场空白

1. **没有一款产品把"可核查"做成一等公民**——景点介绍都是营销文案或 UGC，没有"这条信息来源是什么、检索到了没有"的表达。
2. **可编辑性不一致是通病**——TripIt / Sygic 都是"部分能改部分不能改"，用户无法预测。
3. **破坏性操作缺乏撤销**——TripIt 用户误合并丢失大量备注且无补救。
4. **增量修改无解**——"把苍山加到行程里"这种最自然的诉求，头部产品普遍识别不了。
5. **重新生成成本无法承受**——40 分钟/次、每日 1 次，逼着用户必须能局部改。

## 4. 我们的差异化

> **别人给答案，我们给"带出处的草稿 + 修剪权"。**

| 维度 | 竞品 | 识途 |
|------|------|------|
| 信息可信度 | 营销文案/UGC，无来源，缺失时静默编造 | 已关联官方攻略原文 + 来源；未召回时**显式声明未知**，绝不编造 |
| 修改粒度 | 整体重新生成 / 手工从零搭 | 逐块增删改，改动后**级联可见、可撤销** |
| 改动后果 | 静默改变或完全不检查 | 链式重算 + 锚点保护 + 越界阻断级提示 |
| 可预测性 | 部分能改部分不能改 | 按块类型明确可操作集合，并**说明不可操作的原因** |
| 边界自律 | 拼命往预订/交易延伸 | 契约级不做预订，专注"规划得对不对" |
| 诚实度 | 缺失信息静默填充 | 缺失即声明缺失；占位值（如未查回路线的 30 分钟）**明确标注为占位** |

**用户为什么选我们**：他被 AI 坑过（或听过别人被坑），需要一份**敢照着走**的行程。敢照着走的前提是——能查证、能改、改完知道会发生什么。

## 5. 数据模型与三档分离

### 5.1 编辑对象

`workspace['plan']['days'][i]['events'][]`。事件 `kind` **全集 10 类**：

`transport` / `arrival` / `transfer_plan` / `free` / `route` / `unknown_route` / `spot` / `rest` / `spot_continue` / **`meal`**

> **更正记录**：v2.0 曾补 `spot_continue` 至 9 类，但仍遗漏 `meal`。`meal_events.py:17,137` 与 `schedule.py:581` 均产出 `kind:"meal"`，`plan_revision.py:207` 已在校验它。三方文档一度不一致（PRD 无、简报无、DESIGN.md 有且标为可编辑）——这正是本 PRD §3.1 批判的"可编辑性不一致"通病，此处收敛。

spot 事件结构（`daily_schedule.py:706-718`）：

```json
{"kind":"spot","candidate_id":"<稳定ID>","name":"","start":"","end":"",
 "duration":0,"note":"","poi":{},"evidence":[...]}
```

`spot_continue` 是跨午餐的长游览拆分出的续段（`CONTEXT.md:118`），**与父 spot 共享 `candidate_id`，不可独立操作**。

`rest` 有**两种语义**，需区别对待（`meal_events.py:155`、`schedule.py:529`、`pacing.py:52`）：

- `rest_type:"midday"` —— 午休，由午餐派生
- 无 `rest_type` —— 景点之间的机动时间（`daily_schedule.py:724`）

两者**均无 `candidate_id`**，重算后无法稳定回放。

### 5.2 evidence 数据现状（后端零改动）

`daily_schedule.py:592-593`：

```python
self.evidence = [
    x for x in self.ctx.guides if x["id"] in self.item.get("evidence_ids", [])

```

`:716` 内嵌进 spot 事件，`present()` 将 `w["plan"]` 原样下发前端。

> **evidence 数据今天已在前端手上，只是没渲染。F2 是纯前端渲染任务。**

### 5.3 三档分离在块编辑中的映射

| 档 | 内容 | 能否编辑 | UI 表现 |
|----|------|----------|---------|
| **事实** | POI 名称、位置、evidence 原文与来源 | **只读** | 展示原文 + 来源标识；不摘要、不改写 |
| **建议** | `duration` / `start` / `end` / `note`（系统计算值） | **可编辑** | 编辑后标记"用户已设定"，视觉区别于系统建议值 |
| **未知** | evidence 为空、开放时间未核实、票价未确认 | **不可填充** | 显式显示「暂无官方资料，需自行核实」；**绝不允许模型补写** |

> **文案口径（已定）**：统一使用「暂无官方资料，需自行核实」。
> **设计约束**：该文案与配套视觉**不得暗示"该景点不存在官方资料"**——它陈述的是系统状态（本次未关联到已检索的官方攻略），不是关于外部世界的断言。

### 5.4 可编辑性契约（沿用 `plan_revision.py:95-106` 现有声明）

系统已向模型声明 editable / fixed 契约，**PRD 沿用同一契约，不另立一套**，以保证模型与 UI 看到的定义一致：

| 系统已声明 `editable` | 对应块编辑能力 |
|----------------------|----------------|
| 灵活景点的游玩日和顺序 | spot：可改顺序（P2）/ 跨日移动（P2） |
| 建议时长与游览范围 | spot：可改 `duration`（P0） |
| 建议时段 | spot：可改时段（P2） |
| 游玩说明 | spot：可改 `note`（P2） |

| 系统已声明 `fixed` | 块编辑中的表现 |
|-------------------|----------------|
| 用户明确日期、时段、顺序 | **锚点**：级联遇之停止并报冲突（`revision_fixed_time`） |
| 已选景点、住宿、餐厅 | **不可在计划层增删**——须走选择层（`selected_spots`）后重排 |
| 已选车票机票 | `transport` / `arrival` 不可动 |
| 旅行起止日期、人数、预算与节奏要求 | 不在块编辑范围内 |

### 5.5 可操作矩阵

| kind | 可删除 | 可改时长 | 可改顺序 | 说明 |
|------|--------|----------|----------|------|
| `spot` | **是（MVP）= 取消选择** | **是（MVP）** | 是（P2） | 主编辑对象，`candidate_id` 定位稳定可回放 |
| `free` | 否（P2） | 否（P2） | 否 | **可新增（MVP）**；`replayable:false` |
| `rest` | 否（P2） | **否（P2）** | 否 | 两种语义（午休/机动）均无 `candidate_id`，无法稳定回放；见下方说明 |
| `meal` | **否** | **否** | **否** | **MVP 只读**，见下方说明 |
| `spot_continue` | **否（随父 spot 联动）** | 否 | 否 | 长游览续段，与父 spot 共享 candidate_id |
| `route` / `unknown_route` | 否 | 否 | 否 | 由前后景点派生的已查询事实 |
| `transport` / `arrival` | 否 | 否 | 否 | **固定班次锚点** |
| `transfer_plan` | 否 | 否 | 否 | 接驳计划，由班次与位置派生 |

**`meal` 为什么 MVP 只读**（架构裁定）：

- 餐次时刻由 `meal_choices`（选择层事实）+ 餐次窗口 + 游玩收尾共同决定，是**派生值**
- 块级改会让 plan 与 `w["meal_choices"]` 失同步
- "我不想吃这顿"已有正确路径：`meal_choice{mode:"remove"}`，不是块编辑该管的
- UI 原因文案：「餐次由你的餐厅选择与用餐时段推算；如需调整，请改餐次安排。」

**`rest` 改时长为什么降 P2**（沿用主理人对 F1 的同一裁定逻辑：无 `candidate_id` → 无法稳定回放）：

- 两种语义（午休 / 机动时间）需分别处理，不是单一改动
- "改"的产品完整性已由 `spot` 时长编辑覆盖，不像"增"那样缺了就少一块能力
- 若未来要做，须标 `replayable:false` 并在 UI 明说"重新生成后不保留"（沿用 `add_block` 先例）

> **不可操作的块必须显式说明原因**，不能只给个灰按钮——竞品的教训正是"用户无法预测哪些能改"。上表每一行的"否"都需在 UI 上给出对应原因文案。

### 5.6 `plan['block_edits']` 数据结构（字段名已定）

```json
plan["block_edits"] = [
  {
    "id": "rev_9f3c1a2b7e01",
    "at": "2026-03-05T14:22:31",
    "op": "duration",
    "source": "user_explicit",
    "replayable": true,
    "superseded": false,
    "target": {"kind": "spot", "candidate_id": "B0FFH7", "date": "2026-04-02"},
    "before": {"duration": 90, "start": "10:30", "end": "12:00"},
    "after":  {"duration": 150}
  }
]
```

关键设计约束：

- **`source` 复用 `app/core/contracts.py:248` 的 `SOURCE_USER = "user_explicit"`**——项目已有 provenance 词表（user > 班次事实 > 系统建议），不新造。
- **定位主键是 `candidate_id`，不是 `block_id`**：重算后 event 是新生成的对象，block_id 会变；candidate_id 不变。这是回放能命中的唯一保证。
- **`after` 只存用户真正拥有的值**（`duration` / `note`）。`start` / `end` 是派生值，**不得存入 `after`**——存了会在回放后与级联结果打架。
- **`before` 存完整快照**，兼作撤销依据。
- **不使用 `revisions` 字段名**——`revision` 在项目里已是 workspace 版本号语义，避免双关。

### 5.7 为什么 `block_edits` 必须是新字段而非扩展 `stale`

1. `stale` 是布尔量，有 **10 处写入方**（`workspaces.py:14`、`timeline_tools.py:215,261`、`visit_analysis.py:595`、`foods.py:766,795`、`locations.py:241`、`requirements.py:12`、`visits.py:54`、`auto_selection.py:406`）+ **1 处硬门禁**（`workspaces.py:225` 导出时 `if stale: raise 409`）。扩成复合语义等于要求这 11 处读者全部正确区分——沉默逻辑错误的教科书场景。
2. 两者**正交**：`stale` = 计划与上游选择的一致性；`block_edits` = 计划内部的用户手工痕迹。**可以同真**（用户改了 3 个块之后又改了景点选择），布尔量表达不了。

## 6. 时间级联策略

### 6.1 约束来源

`daily_schedule.py:719`：`self.time += self.duration + self.meal_minutes`

### 6.2 三方案选择

| 方案 | 描述 | 评价 |
|------|------|------|
| A 静默自动顺延 | 改了就往后推，不告诉用户 | **否决**。等价于 TripIt 式"界面不清导致意外" |
| B 级联可见 + 分级提示 | inline 展示变化摘要，越界时阻断确认 | **采纳** |
| C 不级联，让用户自己收拾 | 只改目标块，后面产生重叠/冲突 | **否决**。产生非法状态 |

### 6.3 复用现有校验（`plan_revision.check()`）

**F0 不是新建，是复用。** `plan_revision.py:111-196` 已有四项校验：

| 现有 issue code | 校验内容 | 对应本 PRD |
|-----------------|----------|-----------|
| `revision_overlap` | 同一天 events 时间严格单调、不重叠 | 级联一致性断言 |
| `revision_fixed_time` | 满足用户明确指定的日期/时段 | **锚点保护** |
| `revision_day_end` | spot/spot_continue 结束不超过每日结束时间 | **阻断级提示** |
| `model_output` | 修订完整保留全部已选景点 | 完整性校验 |

`plan_revision.py:192`："修订没有完整保留全部已选景点，**旧计划已保留**，可重试。"——原子回滚机制已存在。

### 6.4 锚点停止规则（精确定义）

`ANCHORS = {"transport", "arrival", "transfer_plan"}`

级联从被改块向后遍历，**遇到第一个锚点即停止**，锚点及其后的块一律不动；若此时前一块的新 `end` 已超过锚点 `start` → 报 `anchor_conflict`（阻断级）。

实测锚点只出现在**天的两端**（去程 `transport` index 0 `daily_schedule.py:118-130`；`arrival` index 0 `:178`；返程 `transfer_plan`/`transport` 末尾 `:288,968`），所以"停止 + 后续不动"的语义是干净的——**不可能把火车推走**。

### 6.5 分级提示矩阵

| 编辑类型 | 级联行为 | 提示级别 | UI 形式 |
|----------|----------|----------|---------|
| 改停留时长（C 档） | 后续块顺延/前移 | 告知级 | inline 变更条 |
| 新增自定义块（C 档） | 插入点之后顺延 | 告知级 | inline 变更条 |
| 删除 spot 块（D 档） | 取消选择 → 查 1 条新路线 → 重排 | 告知级 | inline 变更条 + "重算中"标记 |
| 改顺序 / 跨日移动（P2） | 重排 + 查多条路线 | 告知级 | inline 变更条 + loading |
| **任何编辑导致**：超出 `day_end` / 违反返程接驳约束 / 与锚点冲突 / 违反用户指定时段 | 不静默接受 | **阻断级** | 必须用户显式确认「仍然保留这一安排」才写入 |

> 阻断级文案沿用现有系统口径（`plan_revision.py:172`）："〈日期〉的建议游玩超过当前每日结束时间。可调整节奏或查看带警告的草稿；当前结束时刻不会自动延后。"
> **不要用"操作失败""无法保存"这类词——这不是错误，是提醒。**

### 6.6 阻断确认的两段式

`edit_block` / `remove_block` 增加 `confirm: bool` 参数：

- `confirm` 缺省 / false → 算出级联；若有阻断级冲突 → **不写入**（`block_edits` 不变），返回 `status:"blocked"`
- `confirm: true` → 写入，越界项进 `plan["planning_issues"]`（复用现有 `revision_day_end` 形状，`plan_output.py:57-76`），计划书仍可导出且保留提醒

### 6.7 响应体：级联 diff 的传递通道

**不开新端点，挂现有通道。** `app/api/jobs.py` 的 job 结果与 SSE `done` 事件均返回 `ui`；`job_results.finish_ui` 已在用 `ui["conflict"]` 传结构化冲突（`job_results.py:19-20`），前端 `timeline.js:104` 已在渲染 `workspace.ui.conflict`。

新增 `ui["block_cascade"]`：

```json

  "cascade": [
    {"block_id":"...","name":"...","kind":"spot","date":"2026-04-02",
     "before":{"start":"10:30","end":"12:00"},
     "after":{"start":"10:30","end":"13:00"},"delta_minutes":60}
  ],
  "summary": {"affected_count":3,"shift_minutes":60,"day_end_estimate":"19:20"},

```

阻断级走现有 `ui["conflict"]`（前端已有渲染，零新 UI 组件）。

### 6.8 `unknown_route` 的级联取值（不新造、不补造）

正式计划书里的 `unknown_route` **已有 30 分钟占位时长**（`daily_schedule.py:429-438`）：

```python
"start": clock(self.time), "end": clock(self.time + 30),
"note": "路线查询失败，暂留30分钟占位；实际是否足够待核实"
```

级联口径：

1. **沿用这 30 分钟**——它是已写入且已明确标注为占位的时长，不是新造的数据。不做均值、不做距离推算、不写 0。
2. **必须在变更摘要中显式标注**：`pending_routes` 带回「含 N 段未查询路线，按 30 分钟占位估算，实际耗时待核实」。
3. **若编辑产生了从未查询过的新路段**（典型：删除 B 后 A→C 是全新 pair）→ **必须真查**，不得沿用占位。

> **分界规则**：只有"景点有序集合不变"才能沿用已有路线或占位；**一变就走真查**。

### 7.1 MVP 范围（终版）

**用户能感知的四件事**：

1. **查证想去的** — evidence 展开与空态降级（F2）
2. **删掉不想去的** — 删除 spot 块（F1）
3. **微调想改的** — 改 **spot** 停留时长（F5；`rest` 时长编辑已降 P2，见 5.5 说明）
4. **加上自己的安排** — 新增自定义块（F7，限 `free`，`replayable:false`）

**非协商底座**：

- **F0 级联引擎**（复用 `plan_revision.check`）——没有它删一块就时间错乱
- **F4 撤销**（复用服务端 `storage.previous`）——破坏性操作没有补救就是 TripIt 悲剧
- **F3 人工修订保护**（`block_edits` 回放）——没有它，改完下次生成就被冲掉

**进 Backlog**：F6 替换景点（P1）、F1b 删除 rest/free（P2）、F8 改顺序（P2）、F9 删除整天（P2）。

### 7.2 关键产品决策：人工修订保护（F3）

现有 `edit_tools.py` 的编辑工具操作 **workspace 选择层**；块级编辑操作 **plan 事件层**。两层并存必须定义优先级，否则用户逐块改完后一次 `generate_plan` 全冲掉，块编辑就是假功能。

**实现路径（"生成后回放 + 级联"，不侵入生成逻辑）**：

```
1. plan = await _generate(w, progress)                        # 全量，不侵入
2. plan = block_edits.replay(plan, w["plan"]["block_edits"])  # 按 candidate_id 写回用户值
3. plan = block_edits.rechain(plan, affected_dates)           # C 档级联引擎，与 F1/F5 共用
4. plan_revision.check(w, plan)                               # 现有验收闸门
5. 保留 block_edits
```

> 第 3 步复用的就是 F0 级联引擎，所以 F3 边际成本仅 `replay()` 约 30 行 + 一个确认闸门。

**规则**：

- **规则 1**：块编辑后 `plan['stale']` 保持 `False`（计划本身仍有效），但写入 `plan['block_edits']`。
- **规则 2**：触发重新生成且 `block_edits` 有未 superseded 条目时，**必须先展示"本次重新生成将丢弃你的 N 处手工修改"**，由用户选「保留我的修改」或「全部重新生成」。
- **规则 3**：选「保留我的修改」→ 回放 + 级联；**若产生阻断级冲突，不得静默写入，必须回用户逐项确认**（见 AC-4.3a/b）。

## 9. EARS 格式验收标准

### 9.1 evidence 展开与空态降级（F2）

- **AC-2.1** 当用户展开 spot 块的资料区时，系统应渲染该 event `evidence` 数组中每一条攻略资料的原文与来源标识，**不得改写、摘要或补充**。
- **AC-2.2** 若 `evidence` 为空数组或缺失，则系统应显示「暂无官方资料，需自行核实」，且**不得展示任何由模型生成的内容作为替代**。
- **AC-2.3** 资料区默认应处于折叠态；展开操作不得改变该块的起止时刻。
- **AC-2.4** 若某条 evidence 缺少来源字段，则系统应显示"来源未标注"而非留空或推断来源。
- **AC-2.5** 系统应为 evidence 空态渲染独立的可视状态（与"有资料但未展开"明确区分），**不得留白**。
- **AC-2.6** 空态文案与配套视觉**不得暗示"该景点不存在官方资料"**——它陈述的是系统状态（本次未关联到已检索攻略），不是关于外部世界的断言。

### 9.2 删除 spot 块（F1）

- **AC-1.1** 当用户删除某天的 spot 块时，系统应**取消该景点在工作台的选择状态（同步 `selected_spots`）**，而非仅从 `plan['days'][i]['events']` 中移除一行。
- **AC-1.2** 删除后该景点应回到**未选状态但保留在候选列表中**，用户可再次选择。
- **AC-1.3** 若该 spot 存在关联的 `spot_continue` 续段，则系统应一并处理，不得留下孤立续段。
- **AC-1.4** 删除触发重排后，系统应在同一视图内 inline 展示变更摘要（含"后续 N 项提前/顺延 M 分钟"与"当日预计结束时刻"），**不得静默修改**。数据源为服务端返回的 `ui["block_cascade"]`。
- **AC-1.5** 当重排触及锚点（`transport` / `arrival` / `transfer_plan`）时，系统应**在第一个锚点处停止**并报 `anchor_conflict`，锚点及其后的块一律不动。
- **AC-1.6** 若重排结果超出 `day_end`、违反返程接驳约束、或与锚点冲突，则系统应返回 `status:"blocked"` 且**不写入**；仅当请求携带 `confirm:true` 时才写入，并将越界项写入 `plan["planning_issues"]`。
- **AC-1.7** 若编辑产生了从未查询过的新路段（如删除 B 后 A→C 为全新 pair），则系统应**真查该路线**，不得沿用 30 分钟占位。
- **AC-1.8** 重排结果中若含 `unknown_route` 段，系统应在变更摘要中显式标注「含 N 段未查询路线，按 30 分钟占位估算，实际耗时待核实」。
- **AC-1.9** 删除完成后，系统应在被删位置附近展示"已删除〈名称〉 · 撤销"；在该提示存续期间触发撤销，应完整恢复该景点选择状态及全部块的原始起止时刻。
- **AC-1.10** 若某 event 的 `kind` 属于不可删除类型（`route` / `unknown_route` / `transport` / `arrival` / `transfer_plan` / `spot_continue` / **`rest`** / **`free`**），则系统应不提供删除入口，并说明原因。

### 9.3 改停留时长（F5）

> **范围**：MVP 仅覆盖 `spot` 块的 `duration`。`rest` 块的时长编辑降 P2（理由见 5.5），不在本节验收范围内。

- **AC-3.1** 当用户修改 spot 块的 `duration` 时，系统应按链式规则重算该块及其后续所有块的 `start` / `end`，并 inline 展示变更摘要。
- **AC-3.2** 若重算结果超出 `day_end` 或违反返程接驳约束，则系统应展示阻断级提示，在用户显式确认前不写入。
- **AC-3.3** 修改后系统应将该块标记为"用户已设定"，视觉上区别于系统建议时长，并写入 `block_edits`。
- **AC-3.4** 当用户触发撤销时，系统应恢复原 `duration` 及全部后续块的原始时刻。
- **AC-3.5** 修改 `duration` 不得改变该块所在日的景点集合与访问顺序（集合与顺序不变 ⇒ 无需重查路线）。

### 9.4 新增自定义块（F7）

- **AC-7.1** 系统应仅允许新增 `kind:"free"` 的块，**不得提供新增 `spot` 的入口**。
- **AC-7.2** 新增块应在 `block_edits` 中标记 `replayable:false`。
- **AC-7.3** 系统应在新增块上**显式说明「这是你添加的自定义安排，重新生成计划书后不会保留」**，不得让用户误以为它与系统生成的块同等持久。
- **AC-7.4** 新增后插入点之后的块应按链式规则顺延，并 inline 展示变更摘要。
- **AC-7.5** 若新增导致超出 `day_end` 或与锚点冲突，则系统应展示阻断级提示，在用户显式确认前不写入。
- **AC-7.6** 新增的自定义块无 evidence，其资料区应显示空态降级（「暂无官方资料，需自行核实」），**不得显示为错误状态**。

### 9.5 人工修订保护（F3）

- **AC-4.1** 当用户完成任一 event 的增删改后，系统应写入 `plan['block_edits']`，且 `plan['stale']` 保持为 `False`。
- **AC-4.2** 当触发重新生成且 `block_edits` 存在未 superseded 条目时，系统应先展示"本次重新生成将丢弃你的 N 处手工修改"，并提供「保留我的修改」与「全部重新生成」两个选项。
- **AC-4.3a** 若用户选择「保留我的修改」，则系统应先按 `block_edits` 回放用户值、再执行级联重算；**回放后若无阻断级冲突，方可直接写入**。
- **AC-4.3b** 若回放后产生阻断级冲突（如某块被挤到 `day_end` 之后、或与锚点冲突），则系统**不得静默写入**，必须回到用户逐项确认后再写入。
- **AC-4.3c** 回放应以 `candidate_id` 为定位主键；`after` 中**仅回放 `duration` / `note`**，`start` / `end` 由级联重算决定，不得直接写回。
- **AC-4.4** 若用户选择「全部重新生成」，则系统应将全部 `block_edits` 条目置 `superseded:true` 并追加一条 `op:"regen_all"` 记录，**不得清空**（清空会丢失撤销依赖的 `before` 快照与审计轨迹）；同时应告知用户"你之前的 N 处修改已全部丢弃"。

### 9.6 撤销（F4）

- **AC-5.1** 系统应为删除、改时长、新增自定义块提供统一撤销能力，撤销后状态应与操作前**逐字段一致**（含全部级联块的起止时刻与 `selected_spots`）。实现走服务端 `action:"undo"` → `storage.previous(w)`，**刷新页面不失效**。
- **AC-5.2** 系统在编辑操作过程中不得弹出"确定要删除吗"类二次确认对话框（不可逆操作除外）。
- **AC-5.3** 若服务端修订未通过 `plan_revision.check()` 校验，则系统应保留旧计划不变并明确提示原因与可重试，**不得写入未通过校验的计划**。
- **AC-5.4** 若用户在块编辑之后又执行了其他改变 workspace 的操作，则系统应**隐藏"撤销"提示**并说明原因（服务端回滚的是整个 workspace 而非仅 plan），不得静默失败或回滚到意外状态。

### 9.7 边界与异常

- **AC-9.1** 删除当天最后一个 spot 块后，若当日仅剩 rest / free 块，系统应正常展示"当日暂无游览安排"空态，不得报错或移除该天。
- **AC-9.2** 若 `plan['stale']` 为 `True`（上游选择已变）时用户发起块编辑，系统应先提示"当前计划已因条件变化过期，建议先重新生成"，并允许用户选择"仍要编辑此时版本"。
- **AC-9.3** 若编辑操作的服务端写入失败，系统应回滚前端乐观反馈并展示具体失败原因，不得留下"前端已改、后端未改"的不一致状态。
- **AC-9.4** 对于需查路线的操作（D 档及以上），系统应在操作期间展示"重算中"标记；**前端不得预演重排后的时刻**。
- **AC-9.5** 系统在编辑流程中不得展示任何预订、下单、支付相关的入口或引导文案。
- **AC-9.6** 系统不得提供"新增任意景点"的块编辑入口；用户表达加景点意图时，应引导至对话链路。
- **AC-9.7** 若编辑导致当日安排越过 **24:00**，则系统应**阻断并提示**，不得写入。
  > 依据：`time_values.clock()` **不截断**——`clock(1470)` 返回 `"24:30"`，而前端 `planMinute`（`plan.js:2-10`）只接受 `24:00`。**不能依赖 `clock()` 兜底**，级联必须显式校验 24:00 边界（issue code 建议 `block_day_boundary`，阻断级）。
- **AC-9.8** 系统不得对 `meal` 事件提供删除、改时长、改顺序入口，并应在 UI 上说明原因：「餐次由你的餐厅选择与用餐时段推算；如需调整，请改餐次安排。」

## 10. 非功能需求

### 10.1 性能分档（v3.0 已按 C/D 档拆分）

| 档位 | 操作 | 指标 | 说明 |
|------|------|------|------|
| **C 档** | 改时长 / 新增自定义块 | **p95 < 800ms** | 无外部调用，纯计算 |
| **D 档** | 删除 spot 块（含 1 次路线查询） | **p95 < 3s** | 3 modes × 1 pair，Semaphore 3 |
| **E 档** | 调序 / 跨日移动（P2） | 待定 | 多条路线查询 |

> **硬约束：不得为了把 D 档压进 800ms 而改用 30 分钟占位。** 那是用"敢不敢照着走"换一个数字，直接违反项目铁律与差异化定位。若路线查询失败，系统本就会自动降级为占位（`daily_schedule.py:429`），**无需我们主动降级**。

### 10.2 交互口径：乐观更新

- 前端做**轻量乐观反馈**：被改块的数字立即变化 + 后续块标记"重算中"。
- **不在 JS 中重算级联**。在前端复制一份级联逻辑等于制造两份时刻真相，必然漂移——这是本项目要防的头号失效模式。
- 服务端返回后**一次性渲染真实 diff** 与 inline 变更条。
- 100ms 内用户有可见反馈，且不产生双份时刻逻辑。这也贴合 Linear 范式的本意（乐观更新是"先相信"，不是"先自己算一遍"）。

**关于拖拽手柄（产品裁定）**：

MVP **不显示**六点拖拽手柄。理由：MVP 内无调序功能（`move_block` 已降 P2），**一个不可拖的手柄是假的可供性**——比没有更糟，用户会尝试拖拽并失败。

P2 实现调序时，**用「上移 / 下移」按钮，不做原生 HTML5 拖拽**。理由：

1. `views/workspace.js:227` 是整块 `innerHTML` 重绘，拖拽过程中任何 `action()` 重绘都会销毁正在拖的节点、丢失拖拽状态
2. 原生 HTML5 drag 在移动端触屏基本不可用
3. 键盘不可达（违反可访问性要求）
4. 与不做清单第 7 条一致：移动端误触率高，降级为按钮式调序

图标语义应为「上移箭头 / 下移箭头图标」而非「拖拽手柄图标」——**图标必须与实际可用的操作一致**。

**关于撤销提示的存活期**：

不设固定计时器。撤销提示应存活至**用户执行下一个改变 workspace 的操作**（此时 AC-5.4 生效，提示隐藏）或**页面导航**为止。理由：提示的存活期应当**与撤销实际可用的期间对齐**，而非一个拍脑袋的秒数——删除本身要 1–3 秒返回，用户此时还在读变更摘要，8 秒计时器会在用户做决定前就消失。计划书工具栏的常驻「撤销上一步」按钮（`plan.js:130`）作为兜底入口。

### 10.3 其他

| 类别 | 要求 | 优先级 |
|------|------|--------|
| 一致性断言 | 顺序遍历当天 events，`start`/`end` 必须严格单调不重叠。复用现有 `revision_overlap` 校验。**三条必要约束**：① 断言覆盖**所有块**（含 `rest` / `free` / `meal`，它们有真实 start/end），不排除任何 kind；② **`plan.days[].events` 里没有 `end_date` 字段**——`end_date` 只存在于 `plan_rows()` 产出的时间轴行（`schedule.py:753`）。plan 中跨夜班次表现为 **`end <= start`**；③ 因此规则为：若 `end <= start`，**仅当 `kind == "transport"`** 时视为跨夜（`end += 1440` 后继续比较），**其他任何 kind 出现 `end <= start` 直接判为非法** | P0 |

## 11. 数据埋点方案

| 事件类别 | 必埋事件 | 属性 | 说明 |
|----------|----------|------|------|
| 编辑行为 | `block_delete_spot`, `block_duration_change`, `block_add_free`, `block_undo` | `user_id`, `plan_id`, `date`, `event_kind`, `candidate_id`, `cascade_count`, `blocked_by`, `duration_ms`, `confirm_required`, `timestamp` | 验证"哪些操作真高频"；`duration_ms` 校验 C/D 档性能是否达标 |

| 阻断与冲突 | `edit_blocked` | `reason`（day_end / transfer / anchor_conflict）, `date`, `timestamp` | 判断级联策略是否过严或过松 |
| 链路分流 | `add_spot_intent_redirected` | `source`（block_ui / dialogue）, `timestamp` | 验证"加景点走对话"分流是否被用户接受 |
| 修订保护 | `regen_with_block_edits`, `regen_choice`, `regen_replay_conflict` | `edit_count`, `choice`（keep / regenerate_all）, `conflict_count`, `timestamp` | `regen_replay_conflict` 验证 AC-4.3b 触发频率；若 `edit_count` 长期为 0，说明块编辑没被用起来 |
| 撤销可见性 | `undo_suppressed` | `reason`（workspace_revision_changed）, `timestamp` | 验证 AC-5.4 守卫触发频率 |
| 异常 | `edit_error` | `operation`, `error_type`, `timestamp` | 前端错误 + API 错误 |

**实现要求**：事件命名 `{对象}_{动作}`；每事件附 `user_id` / `timestamp` / `device` / `version`；不采集隐私数据，`candidate_id` 只上报稳定 ID。

**上线后第一个验证假设**：若 `block_delete_spot` 与 `evidence_expand` 触发率显著高于"重新生成"，则"局部修改比重新生成更有价值"成立。
