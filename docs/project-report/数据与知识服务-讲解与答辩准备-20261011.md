# 数据与知识服务：讲解与答辩准备

适用范围：正式项目汇报的 4.3，包含数据获取与处理、MCP、Embedding、Qdrant 和 RAG。核对日期：2026-10-11。

## 先掌握这条主线

**我的部分解决的是：让旅行规划有资料和查询依据，并把这些依据交给模型使用。**

例如用户想去青岛游玩：景点介绍可以从保存的官方资料检索；酒店、班次、路线和天气需要按条件查询；取得结果后还要核对坐标、日期和来源。模型结合这些输入提出推荐，程序再校验和执行。

| 层次 | 一句话解释 | 在识途中的例子 |
|---|---|---|
| 数据获取与处理 | 取得信息，并说明它是什么、从哪来、何时可用 | 接口结果核对坐标；公告保留适用日期；失败保留已有有效资料 |
| MCP | 按统一的工具约定连接查询能力 | 调用地点、路线、天气及资料检索工具 |
| RAG | 先检索有关资料，再让模型参考资料生成回答 | 从知识库找出海滨景点介绍和来源，交给推荐或规划阶段 |

MCP 和 RAG 不是两套互相替代的方案。本项目把 RAG 检索包装成 `retrieve_guides` 工具，通过 MCP 提供给业务流程使用。

## 可直接口述的讲稿

> 接下来介绍识途的数据与知识服务。这部分主要解决一个问题：模型可以组织旅游建议，但景点资料、路线、天气和报价需要有实际依据。
>
> 我们将数据分成两类。第一类是按条件查询的信息，例如高德的地点和道路、和风天气的预报，以及途牛的酒店和交通服务。这些结果是查询时的快照。第二类是保存的旅游知识资料，例如景点特色和官方说明，适合通过知识库检索使用。
>
> 为了把查询能力接入系统，我们使用 MCP。它规定工具怎样描述参数、怎样调用和返回结果。项目自建本地 MCP 服务，提供地点搜索、路线、天气和资料检索等八个工具，同时通过网络接入途牛 MCP。模型提出目标后，后端组织工具调用，取得结果再交给模型理解。
>
> 知识检索采用 RAG，也就是先检索再生成。原始资料以 JSON 保存来源和内容，分成父块和子块。子块用于找到相关片段，父块补充完整上下文。BGE 中文模型将文本转换成 512 维向量，存入 Qdrant。查询时同时进行关键词检索和语义检索，再融合排名，将相关内容及来源交给模型。
>
> 数据处理还会保留版本、查询时间和适用范围。无法核对位置的候选不会直接发布，未来日期不能用当前快照作保证。索引失效时会明确降级为关键词检索，避免把旧向量结果当成新资料。
>
> 当前目录覆盖 20 个城市，知识库有 116 条记录、125 个父块和 350 个子块。它仍是有限资料的旅行规划原型，不代表所有地区和所有运营信息已经齐全。下面通过项目演示，展示这些查询和检索结果怎样进入推荐与旅行计划。

按正常语速约 3～4 分钟。时间不足时删去父子块和索引降级的展开，保留“信息来源—MCP 接入—RAG 检索—结果有依据”主线。

## 必须理解的知识

### 1. 数据为什么分成两类？

“栈桥有什么特色”可以参考已有旅游资料；“明天酒店报价多少”“从酒店过去多久”需要按地点和时间查接口。两类信息会进入同一规划流程，但有不同的时效与适用范围。

接口返回的也只是查询时快照，不能保证出游当天一定有房、一定售票或道路一定畅通。带来源不等于已经证明未来适用。

自测：如果知识库保存了去年某一天的限流公告，能不能直接用于今年的行程？答案是不能，需要核对公告适用日期。

### 2. MCP 实际做了什么？

以道路查询为例：业务层整理起终点坐标和出行方式，通过 MCP 客户端调用 `calculate_route`；本地 MCP 服务再访问高德接口，返回预计耗时、可用状态和来源。

这里有三个角色：识途应用组织业务；MCP 客户端负责连接和调用；MCP 服务提供工具实现。本项目既编写本地服务，也接入第三方服务，并没有自行开发整个 MCP 协议。[MCP 官方架构说明](https://modelcontextprotocol.io/docs/2025-11-25/learn/architecture)

本地服务通过 stdio 连接，即两个本机进程的标准输入输出通信；途牛通过 Streamable HTTP 连接，即通过网络发送协议请求。两种方式连接位置不同，但都用于工具通信。

自测：路线耗时是 MCP 自己算的，还是由道路供应商返回的？答案是供应商提供，MCP 负责连接与调用约定。

### 3. RAG 为什么需要向量？

用户说“想轻松一点，看看海边”，资料可能写“沿海散步、滨海景观”。两段话用词不完全相同，关键词检索可能漏掉相关资料。

Embedding 是把文本转成一组数字，使意思相近的文本有机会在向量空间里更接近。我们用 BGE 中文模型产生 512 维向量，也就是每段文本用 512 个数表示；不是 512 个景点，也不是固定保存 512 条记录。

Qdrant 存放这些向量，寻找与查询向量相近的子块，再用子块关联的父块补充上下文。Embedding 模型负责转换，Qdrant 负责存储和查询，生成模型负责阅读结果、组织建议。[Qdrant Python 客户端说明](https://github.com/qdrant/qdrant-client)

自测：Qdrant 能直接生成旅游攻略吗？答案是不能，它返回检索结果。

### 4. 为什么同时保留关键词检索？

具体景点名称适合关键词匹配，体验偏好适合语义匹配。我们用 BM25 进行关键词召回，用向量进行语义召回，再用 RRF 融合两路排名。

BM25 可以理解为根据关键词出现情况判断相关性；RRF 可以理解为综合“在各自结果中排得多靠前”。它融合的是排名，不把两个不同范围的分数直接相加。

命中子块之后按父块聚合，并限制输入模型的上下文长度，避免把整座城市的所有资料都塞进一次请求。

### 5. JSON、Qdrant、SQLite 怎么区分？

| 对象 | 实际用途 |
|---|---|
| 知识 JSON | 原始资料、来源、实体和适用信息 |
| Embedding 缓存 JSON | 复用已计算向量，减少重复计算 |
| 索引清单 JSON | 记录语料版本、模型身份、集合与构建状态 |
| Qdrant | 保存向量集合，执行语义查询 |
| SQLite | 保存账户、旅行选择、版本、任务与缓存等业务数据 |

当前 Qdrant 是持久化本地模式，通过 Python 客户端使用；没有独立部署 Qdrant 服务端。扩大到多进程共同使用时，需要配置服务端连接，不能简单让多个进程同时打开同一份本地存储。

## 常见答辩问答

### MCP 与普通 API 有什么区别？为什么不直接调用 API？

直接调用 API 完全可以。API 规定某个供应商如何提供数据；MCP 提供应用连接工具的统一约定。本项目仍通过供应商 API 获得高德、天气数据，只是在外层把它们注册为 MCP 工具，便于统一发现、调用和校验。它有维护与通信成本，价值在于接入一致性，不保证比直接 API 更快。

### MCP 与 Function Calling 是不是同一个东西？

不是。Function Calling 是模型返回要调用的工具名和参数；MCP 是应用与工具服务之间的通信协议。模型产生业务动作或工具请求后，由后端校验、组织查询，再通过 MCP 获取部分数据。当前模型编辑工具也有直接调用业务实现的部分，并非所有工具都属于 MCP 服务。

### 模型真的直接访问途牛或数据库吗？

不是模型拿着密钥直接访问。后端读取本机配置，执行白名单与参数检查，通过 MCP 客户端调用供应商；将结果提供给模型。模型的判断、后端的执行和供应商的数据提供是三个不同职责。

### 你们具体实现了哪些 MCP 工具？

本地 8 个：`search_places`、`get_spot_candidates`、`get_place_details`、`search_transport_places`、`calculate_route`、`daily_weather`、`retrieve_guides`、`knowledge_status`。前三类核心例子可以记成“查地点、查道路、查资料”。途牛另接酒店、火车、航班和门票服务。

`get_spot_candidates` 每批最多四个，业务可以继续获取下一批；不是每次整个行程只推荐四个。坐标和数据覆盖检查涉及 MCP 工具与业务发布层共同处理。

### MCP 的 Tools、Resources、Prompts 都做了吗？

MCP 服务可以提供工具、数据资源和提示模板。本项目的 MCP 接入主要使用 Tools；提示词按业务阶段在项目内管理，没有作为 MCP Prompts 发布，知识库也主要通过检索工具访问，不声称实现了所有协议能力。[MCP 服务概念](https://modelcontextprotocol.io/docs/learn/server-concepts)

### 你自己的实现贡献在哪里？

从实现职责说明：本地数据工具注册、接口结果适配与校验、途牛 MCP 接入、缓存和计量、知识资料组织、索引构建与版本核对、混合检索、来源和日期适用信息保留。介绍实际负责和参与的内容，不把 MCP 协议、高德服务或途牛服务本身说成自行开发。

### RAG 与训练或微调有什么区别？

RAG 在回答前检索外部资料，不修改生成模型参数；微调通过训练改变模型参数。旅游资料会变化，我们采用更新资料与重建索引的方式维护知识。检索仍可能漏召回，模型也可能误读，RAG 只能减少无依据生成风险，不能保证完全没有幻觉。

### 为什么分父块和子块？

小子块便于准确找到相关内容，较完整的父块用于补充上下文。例如命中“预约要求”时，还需要知道适用日期和说明对象，避免只取半句话后产生错误解释。我们召回子块，再返回关联父块及命中片段。

### 为什么用 BGE 和 Qdrant？

BGE 支持本地中文文本向量计算，减少额外 Embedding API 依赖；Qdrant 支持向量查询、载荷条件和本地持久化，也支持服务端连接。这是符合当前原型规模的选型，没有做完整的多种向量数据库性能对比，不能声称性能一定最好。

### 数据更新后怎么办？索引构建失败怎么办？

更新资料后重新构建索引。新索引完成写入和数量核对后，才切换有效版本清单；失败保留旧清单。如果当前资料与索引版本不一致，则明确降级为 BM25，不将旧向量结果当成新资料。查询运行时不会偷偷下载模型或自动进行完整重建。

### 数据是不是实时的？覆盖全国了吗？

不是全部实时，也没有全国完整覆盖。当前目录覆盖 20 个城市，但城市入库不代表所有地点和日期都齐全。报价、路线、天气是查询时快照；知识资料有来源和适用范围。未覆盖地区会明确提示，不能依靠模型补造数据库没有的数据。

### 接口失败或没有坐标怎么办？

区分“查询失败”“查询成功但无结果”“没有坐标”和“没有可行路线”。缺少坐标的候选不能作为正常可算路推荐直接发布；道路未知不能按零分钟算；查询失败尽量保留旧选择并给出具体问题。知识向量检索不可用时可明确降级为关键词检索。

### 查询慢怎么办？四个账号是不是绕过限流？

缓存、相同进行中请求合并、单次计划道路复用可减少重复调用。途牛按四个独立账号的可用状态轮换，但每个账号仍遵守独立间隔、额度和冷却；同一账号的不同 Key 应共享账号限制。轮换不保证某次供应商请求更快，也不意味着无限请求。

### 如何证明真的用了 MCP 和向量检索？

MCP 可查看本地服务注册、客户端初始化与工具调用，配合实际数据服务检查。RAG 可查看有效索引清单、查询返回的检索模式、来源及降级原因。界面上的推荐效果和语言流畅度本身不能单独证明走了语义检索；降级时应该如实说明当前使用关键词检索。

### 用量、数据规模和协议版本是多少？

2026-10-11 本机核对：20 个覆盖城市、116 条原始记录、125 个父块、350 个子块、512 维向量；SDK 为 `mcp 1.30.0`，支持的协议版本包括 `2025-11-25`。连接使用双方支持的版本协商，不把 SDK 包版本与协议日期混为一谈，也不声称本项目已迁移到官网所有最新规范。

## 演示顺序与临场处理

1. 先展示景点推荐和资料来源，说明“这些依据来自查询和检索”。使用已有覆盖目的地，不临时挑未入库城市。
2. 选择或打开一个已有地点，展示坐标、地图和通行信息，说明“接口结果要通过位置与格式核对才能用于规划”。
3. 展示已有旅行的时间轴和计划书，说明“数据进入业务与排程后形成建议，路线时间和游览时间分开”。
4. 有时间再演示一次明确的局部调整，避免把大量连续供应商查询都放在现场。

演示前确认本机服务、登录、模型和数据连接；准备一个已有选择、来源和计划的工作区。在线查询失效时切换已有结果，说明它是先前查询快照，不冒充新的实时结果。不要展示 `.env`、API Key、密码或个人旅行数据。

遇到陌生追问可以回答：“当前实现到……，这部分我们还没有做系统验证；如果扩展，需要……。”具体说明现有结果与后续方案，比猜测更可靠。
