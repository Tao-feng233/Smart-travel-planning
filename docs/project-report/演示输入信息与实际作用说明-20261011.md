# 演示输入信息与实际作用说明

核对日期：2026-10-11。依据当前本机代码，不是期望功能清单。

## 先区分三个层次

1. **查询条件**：信息直接进入地图、酒店等查询参数，例如城市、入住日期、成人数与儿童年龄。
2. **程序约束**：信息用于计算或检查，例如已选班次的可用时间、固定游玩窗口、房型容量和明确午休。
3. **模型参考**：信息进入上下文，影响推荐理由、顺序或代选判断；不代表程序已经保证每次输出满足它。

一个字段可以同时属于多个层次。“传给了模型”不能直接当成“效果已经验证”或“存在完整优化算法”。

## 各项信息的实际作用

| 输入或已有信息 | 当前用在哪里 | 演示时怎样说明 |
|---|---|---|
| 目的地 | 覆盖检查、地点与酒店查询、知识检索及模型上下文 | 限定推荐与检索范围；未覆盖地区明确提示 |
| 游玩开始日期与天数 | 资料适用范围、有效天气、候选数量、日期分配与住宿安排 | 确定哪几天游玩，而不是仅改计划标题；天数与提前抵达、次日返程分别处理 |
| 成人数 | 酒店查询、房型容量检查、部分费用计算及模型同行上下文 | 影响查询条件与人数口径；不能只把人数当聊天描述 |
| 儿童数与年龄 | 酒店查询参数、儿童相关提示、模型同行上下文 | 酒店查询需要每位儿童年龄；儿童门票、餐费与早餐权益仍需按实际政策核对 |
| 房间数 | 房型查询/选择、房型总容量及住宿参考费用 | 影响房间数量与费用口径；没有选择具体房型也可以继续 |
| 旅行和餐饮偏好 | 查询关键词、推荐及代选上下文 | 引导海滨、人文、慢游或口味推荐；候选范围仍受已有资料与接口结果限制 |
| 老人同行、少走路等备注 | `companion_notes`、`hard_constraints` 等模型上下文 | 模型可结合体力判断，但不能宣称所有文字要求都有独立程序保证 |
| 预算 | 推荐/代选/规划上下文、费用参考汇总、计划页预算比较 | 提供参考消费条件，尚未实现完整总预算优化 |
| 出发城市 | 去返程交通查询、同城判断及模型上下文 | 主要用于城际交通；自驾或自行安排往返可以跳过选票 |
| 本地交通方式与旅行节奏 | 道路方式选择、步行阈值、通行缓冲及模型判断 | 比预算更直接地影响交通安排；当前不是按最便宜路线做优化 |
| 已选去返程班次 | 首尾日窗口、出站/接驳准备、住宿与餐次日期、返程日适配 | 下午才到或较早返程会减少可游玩时间 |
| 已选景点、酒店与餐厅 | 地点衔接、道路端点、按日餐次、住宿锚点与计划生成 | 选择不仅用于展示，也提供计算路线与排程的实际对象 |
| 固定游玩日期/时段/顺序 | 结构化请求校验、模型提案与实际排程 | 固定条件优先保护；放不下时说明具体冲突 |
| 明确午休、每日开始与结束时刻 | 每日可用窗口、休息策略及计划检查 | 已保存的结构化休息要求不能被随意取消以掩盖超时 |
| 天气 | 从接口取得与当前目的地、日期一致的预报，再交给模型 | 用户主要提供日期；没有覆盖的未来日期保持未知，不能假设一定晴天 |

## 预算：有参考作用，尚未完成综合优化

### 已实现

- 推荐、代选与计划生成收到整个 `requirements`，其中包括预算。
- 候选信息中可提供酒店起价、餐厅参考人均、景点费用提示等已有价格资料。
- 代选提示要求结合参考费用，模型可以据此说明价格方面的取舍。
- 计划按已有资料汇总部分住宿、往返交通、餐饮和公共交通参考费用，缺失项单独列出。
- 计划页把已有费用小计与用户总预算比较展示；住宿起价参考单独超过总预算时，有程序提醒。

### 尚未实现或不能保证

- 没有完整的“总预算 → 住宿、餐饮、门票、交通分配 → 候选组合优化”流程。
- 酒店查询没有把用户整趟预算自动转换为每晚价格上限。
- 餐厅当前的程序排序没有启用以用户预算驱动的价格排序，主要按餐次、位置与评分组织候选，再交给模型比较。
- 当前本地道路方式选择基于用户交通偏好、旅行节奏及耗时，不是费用最小化。
- 门票、打车、自驾、未选餐次和儿童消费等不具备完整可计算口径，已有费用小计不能当成整趟总消费。
- 普通推荐提示没有专门的总预算分配规则，因此不能仅凭预算进入上下文就承诺推荐已经严格按预算筛选。

预算本身不是当前阶段引导中的基础必填字段，可以不填预算先比较地点。若填写，表单口径是“整趟总预算”，应明确是全体同行人员的旅行参考金额，而不是默认每人每天的金额。

对老师可以这样回答：

> 预算已经进入模型上下文，也能与已有价格参考和费用汇总结合使用。但目前属于参考条件，没有完成所有费用项的联合优化，所以我们不会保证生成方案一定不超过预算。后续需要补齐费用数据、明确成人和儿童口径，并建立可验证的预算分配与组合筛选机制。

## 两个能解释清楚的例子

### 人数：同时影响模型和程序

假设一个已选餐厅有参考人均 80 元，两个成人的这一餐参考费用会按 `80 × 2 = 160 元` 汇总。这只是说明计算口径，不是实际餐厅报价；儿童消费不会据此自动断定也是 80 元。

如果选择房型，程序还会检查房型可住人数乘以房间数量是否足够。模型收到“老人同行、少走路”等描述，可以据此调整建议，但是否满足所有无障碍条件仍需要现场或专门数据核实。

### 日期与班次：会改变可用时间

游玩两天和三天会改变基础候选目标与日期分配；已选下午到达的班次会减少首日时间，返程班次会产生活动截止窗口。程序根据道路、用餐和休息排程，必要时缩短弹性游览。它是实际时间计算，不只是模型在回答里重复日期。

## 演示建议

第一次输入不需要堆满所有字段。可以先提供“已有覆盖目的地 + 明确日期 + 两天 + 两个成人 + 海滨慢游偏好”，再查看候选和推荐理由。

接着补充“希望少走路”或明确午休，解释模型参考与结构化约束的区别。使用已选班次改变首尾日窗口，更容易展示可验证的时间变化。

预算可以填写，用于解释价格参考和费用展示；不要把“改两个预算数字，模型就一定推荐完全不同组合”当作必须成功的现场演示。没有进行控制变量的效果评测，不能凭一次回答声称已证明预算优化有效。

如果现场被问“为什么需要这么多信息”，可以回答：

> 信息是按任务逐步需要的：目的地确定查询范围，日期决定报价和可用窗口，人数决定住宿与费用口径，偏好帮助模型做取舍。用户可以先查地点，再补充需要的条件；可选信息不是都必须一次填完。当前预算属于参考条件，日期和已选班次等则会直接进入程序计算。
