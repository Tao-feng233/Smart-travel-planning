## 一、技术架构类

### ★★★ Q1：为什么用 LangGraph 而不是自己写流程？【归谁答：汇报人二】

**答**：我们需要**可追踪的节点、条件分支和清楚的输入输出**，方便定位"是意图错了还是业务错了"。
LangGraph 的主图就是 `understand → check → execute`，中间有一个最多一次的意图修复回环。
如果手写，条件分支和回环会散在代码里，出问题难定位。

**主动补一句防混淆**（报告图 4 的注释）：
> 「景点、住宿、交通等是**执行层的业务动作**，不分别等同于图中的独立节点。」

**别说**：不要说"因为 LangGraph 更先进"。选它的理由是**可追踪和可定位**，不是先进。

### ★★★ Q2：为什么前端不用 Vue？【归谁答：汇报人二】

**答**：当前前端是原生 HTML/CSS/JS，**尚未迁移 Vue**。当前文件按职责拆成了
`account.js`、`app.js`、`workbench.js`、`details.js`、`experience.js`、`interactive-map.js`
和几个样式文件。

**这题报告里已经写好了标准答案，照念最有说服力**：
> 「早期原生方案便于直接接入后端和快速验证。随着功能增加，全局状态和渲染函数耦合
> 也成为维护成本；**因此不将"完全不需要复杂状态管理"作为优势**。
> 后续可按实际需要进行组件化。」

**别说**：不要辩解"原生更好"或"不需要状态管理"——报告自己都否掉了这个说法。

### ★★★ Q3：RAG 能不能消除幻觉？【归谁答：汇报人一】

**答**：**不能保证完全消除**。RAG 的作用是让模型能参考已保存的资料，
并在资料更新时**无需重新训练生成模型**。它的价值是**降低无依据生成的风险**，
同时保留来源和适用范围。我们另外用程序校验候选 ID、日期和权限，
以及独立模型审核做复核——但这些都是降低风险，不是保证。

**别说**：千万别说"有了 RAG 就不会编造"。这是最容易被追问的点。

### ★★ Q4：为什么用父子块，不直接用整篇或整句？【归谁答：汇报人一】

**答**：整篇召回会**上下文太长、噪声多**；整句召回会**丢失适用条件**。
父子块是折中：**子块用于召回精度，父块保留更完整的上下文**，
避免只返回一句脱离适用条件的话。当前是 **125 个父块、350 个子块**。

### ★★ Q5：为什么还要 BM25，不只用量向量？【归谁答：汇报人一】

**答**：**关键词和语义各有盲区**。地名、专有名词、数字这类，BM25 更稳；
语义改写、口语化表达，向量更稳。我们用 **RRF（倒数排名融合）** 合并两路。
而且**没有初始化或索引过期时会降级为 BM25**，这也是保留它的原因。

### ★★ Q6：为什么选 Qdrant、BGE？【归谁答：汇报人一】

- **Qdrant**：支持本地持久化，原型部署方便，**同时支持配置服务端连接**，给后续扩展留空间
- **BGE（`bge-small-zh-v1.5`）**：中文向量、**本地运行**，减少额外 Embedding API 依赖；
  代价是初次下载、硬件占用和维护成本

**别说**：不要说"Qdrant 性能最好"——报告明确写了
**不宣称经过与 Chroma 的系统性性能比较**。不知道就答"没做过横向压测"。

### ★★ Q7："试排"是什么，为什么要单独搞一套？【归谁答：汇报人三】

**答**：返程日的问题原先是：**先排完模型建议的时长，到晚餐或回住宿时才检查截止时间**，
于是即使缩短一点弹性游览就能赶上班次，也会直接报冲突。

现在改成：先从班次和接驳准备**推算活动截止时间**，
再用**实际排程逻辑**试排剩余景点、餐次、休息和回住宿道路，
必要时按 **5 分钟单位**缩短弹性游览。

**关键设计**：失败的试排**不写入正式事件**——试排隔离了事件、提醒和餐次记录，
不把失败尝试写进最终计划；试排和最终排程**复用本次道路缓存**，不反复查同一段路。

**为什么不用简单扣减公式**：因为"用餐发生在景点内还是景点之间"会改变排程，
不满足简单的单调扣减关系。

### ★★ Q8：模型审核能改计划吗？审核失败怎么办？【归谁答：汇报人三】

**答**：**不能**。审核读已生成的计划、用户要求和来源，返回问题与说明，
**不能自行修改**。它承担独立角色，但**仍属于当前业务调用流程，
不宣称已经运行完整的多 Agent 团队**。

审核失败时，**保留程序检查结果并提示人工复核，不将失败当成"审核通过"**。

### ★ Q9：并发怎么处理？两个请求同时改一个工作区会怎样？【归谁答：汇报人二】

**答**：工作区操作有**互斥与版本检查**，避免并发修改覆盖已有选择。
另外**正在使用的数据库需要一致性备份**——不能只复制主文件就假定所有写入均已保存。

### ★ Q10：连续执行最多 10 次，10 次不够怎么办？【归谁答：汇报人二】

**答**：这是**执行次数与超时的保护**，避免模型无限循环。
10 次内没做完会返回当前状态并说明还缺什么，用户可以继续发起。
我们没有做成"必须一次跑完"的设计。

### ★ Q11：为什么不直接上 MySQL 和独立 Worker？【归谁答：汇报人二】

**答**：**当前整合版本用 SQLite 和本地持久化 Qdrant，MySQL、独立 Worker
等平台升级不列为本稿已实现成果。** 这在我们边界里写明了。
SQLite 部署要求少，适合单机原型；用户隔离、事务和版本检查由业务实现。
规模上来后升级是合理方向，但**当前没有做**。

**别说**：不要把"计划要做"说成"已经做了"。

## 二、数据与知识类

### ★★★ Q12：只有 20 个城市，数据够吗？【归谁答：汇报人一】

**答**：**不够，这是当前最大的边界**。当前覆盖 **20 个城市、116 条语料、125 个父块、350 个子块**。
而且**覆盖城市不代表该城市所有景点、酒店或未来日期都有完整数据**。

我们的做法是**宁可少给，也不编造**：未入库地区会明确提示数据缺失，
**不用模型自行补造**。扩展方式是往来源注册表加官方来源再重跑采集，不需要改代码。

**别说**：不要含糊成"覆盖了 20 个城市所以够用"。

### ★★★ Q13：数据会不会过期？【归谁答：汇报人一】

**答**：会。**接口结果都是查询时快照**：
- 地图资料**不保证出游当天开放**
- 列表报价**不保证最终可售或预订成功**
- 天气**受预报窗口限制**，超窗日期保留未知

所以我们保留**来源、查询时间和适用范围**，并在计划书里列出"出发前待办"。
**查询时间不等于未来适用日期。**

### ★★ Q14：如果一个景点在高德查不到坐标呢？【归谁答：汇报人一】

**答**：**不会进推荐**。地点进入推荐前必须核对到可用坐标；
无法定位、匹配不明确、或仅为辅助设施（停车场、售票处、入口）的结果
**不直接作为正常游玩候选**。

这也是为什么某些城市的候选数量偏少——**不是没数据，是没通过核实**。

### ★★ Q15：为什么有的城市景点只有几个？【归谁答：汇报人一】

**答**：两个原因叠加：
1. **官方资料收录数量有限**——录入多少就只推荐多少
2. **名称必须与地图登记名一致**才能核实到坐标

我们做过一轮名称对齐，把可用率从 68% 提到 95%。剩下没落地的会如实显示，不会凑数。

### ★★ Q16：途牛接口有额度限制吗？多账号会不会更快？【归谁答：汇报人一】

**答**：有。**多账号按可用状态轮换，每个账号保留独立的间隔、额度和冷却记录**。
查询前会检查剩余额度，**额度不足就停止并如实说明，不会把"查不了"当成零费用**。

**这题报告里有一句必须照念**：
> 「**减少等待不等于保证单次接口更快。**」

### ★ Q17：费用是怎么算的？可靠吗？【归谁答：汇报人三】

**答**：分三类，**明确区分**：
- **已有报价**（如车票单人票价、酒店起价）
- **参考估算**（如餐厅地图人均、未选餐厅时按本地中位数估算）
- **待核实项**（未取得资料的，**不按零计入**）

**口径都写明**：酒店起价 ≠ 总房价，人均 ≠ 实际消费，单人票价 × 人数 = 参考总额。
**尚未完成围绕总预算的综合消费优化**——这在边界里明确列了。

**别说**：不要说"预算很准"。要说"口径清楚、未知项明确"。

### ★ Q18：你们有实时景点热度榜吗？【归谁答：汇报人三】

**答**：**没有**。无偏好推荐目前主要参考**城市代表景点资料和地图评分**，
**不是已实现实时景点热度榜**。这是报告里主动写明的边界。

**别说**：不要说"我们按热度推荐"——一旦被追问数据来源就站不住。

## 三、项目价值与对比类

### ★★★ Q19：这和直接用 ChatGPT / DeepSeek 问旅游有什么区别？【归谁答：主讲人】

**答**：三个具体差别，不是抽象的"更专业"：

1. **数据有出处**：保留来源、查询时间和适用范围
2. **道路真的算了**：活动之间的耗时来自道路查询并纳入衔接
3. **状态能延续**：选择保存在工作区，可以回来继续改

**但这题报告已经给了更稳的说法，建议照念**：
> 「通用助手接入搜索或工具后，**也能够获得外部数据**；识途的重点在于
> **将这些能力组织为专门的旅行规划闭环**。」

**别说**：不要说"大模型做不到"。承认对方也能拿外部数据，再讲我们的组织方式。

### ★★ Q20：如果大模型自己就集成了这些工具呢？【归谁答：主讲人】

**答**：**那对我们反而是好事**，说明方向对。我们的差异不在"能查数据"，而在：
- **约束核对**：把班次、道路、餐次、休息、开放时间连起来算可用窗口
- **选择状态管理**：多轮修改保留已选内容
- **不确定性的表达规范**：事实/建议/未知分开，估算不包装成保证

这些是**规划流程的设计**，不是模型能力。

### ★★ Q21：路线是最优的吗？【归谁答：汇报人三】

**答**：**不保证全局最优**。报告边界里明确写了这一点。
我们做的是约束核对和局部调整：保证活动顺序、道路耗时、开放时间、餐次休息与
首尾日窗口**不冲突**，并在返程日等紧张场景做局部缩短。

**别说**：不要说"我们算的是最优路线"。

### ★★ Q22：这算多 Agent 系统吗？【归谁答：汇报人二或三】

**答**：**不算**。当前是**主 Agent 执行流程 + 工具调整 + 独立模型审核调用**，
报告明确写"**不将其描述为已经部署完整多 Agent 协作系统**"。
这是有意的取舍：原型阶段可追踪的单主流程更容易定位问题。

### ★★ Q23：模型为什么选 DeepSeek？【归谁答：汇报人二】

**答**：主要考虑**中文交互、结构化工具调用和原型接入成本**。

**必须补一句限定**（报告原话）：
> 「**本稿不作未测量的模型能力排名或实时价格比较。**」

**别说**：不要去比较各家模型跑分——我们没测过。

### ★ Q24：项目的核心价值到底是什么？【归谁答：主讲人】

**答**：一句话——**让旅行计划更有依据、更容易修改，也更清楚地展示尚需确认的条件**。

具体是把**分散的信息查询、用户决策与行程核对**连成完整流程。

## 四、演示与工程实践类

### ★★★ Q25：现场演示（最危险，要提前踩点）【归谁答：汇报人三主导】

**必做准备**：
- 提前启动服务、打开浏览器、确认能生成计划书
- 选**数据最全的城市**（青岛、洛阳）
- 准备**可复制的指令文本**，避免现场打字
- 确认途牛额度有余量
- 备好关键界面截图

**如果演示中卡住**：
> 「这一步在查接口，受供应商响应速度影响；我先把后面的流程讲完，稍后回来看结果。」
> ——**不要现场反复刷新或改代码**。兜底切截图。

### ★★ Q26：测试覆盖多少？525 项是全部吗？【归谁答：汇报人二】

**答**：**525 项后端测试通过**，另有计划页面恢复与时间轴交通展示的浏览器回归，
此前的整体重构还做过八项浏览器场景验证。

**这些验证说明已覆盖的业务与页面场景符合预期，不代表所有自然语言表达、
供应商结果或现场出行情况都已穷尽。**

### ★★ Q27：你们踩过什么坑？（这是加分题）【归谁答：主讲人，三人可补充】

**答**（讲真事，比讲概念有说服力）：

1. **返程日排程遗漏**——原先排完才检查截止时间，缩短弹性游览本来能赶上也会报冲突。
   改成隔离试排 + 道路缓存复用。
2. **页面资源表把依赖目录也算进去**——组员装前端依赖后，`node_modules` 的文件
   进了资源版本表。改成只按 `index.html` 实际引用计算。
3. **判断条件与实际数据字段对不上**——例如代码只认 `mode=='taxi'` 读打车费，
   而地图接口返回的是 `'driving'`，导致打车预估完全没算。同类问题出现过几次，
   后来要求**先核对真实数据再写判断条件**。

**这题的价值**：说明我们是**靠复现和验证**发现问题，不是靠猜。

### ★★ Q28：SQLite 能撑住吗？【归谁答：汇报人二】

**答**：**当前适合单机原型**。用户隔离、事务和版本检查由业务实现。
**MySQL 和独立 Worker 等部署升级属于后续扩展方向，当前没有做。**

另一个技术细节：**正在使用的数据库需要一致性备份，不能只复制主文件**，
否则可能丢失部分写入。

### ★ Q29：前端不打包，页面资源怎么管？【归谁答：汇报人二】

**答**：当前仍用原生文件，**尚未迁移 Vue**。
早期原生方案便于直接接入后端和快速验证；随着功能增加，
全局状态和渲染函数耦合成为维护成本，**我们不把它当作优势**。
后续可按实际需要组件化。

### ★ Q30：视频/图片里的数据是真的吗？【归谁答：汇报人三】

**答**：**是真实接口返回，但都是查询时快照**。我们会明确标注来源和查询时间。
**不要把演示中的价格理解成可售或已预订。**

## 五、被质疑时的应对话术

### 当被指出"这个功能好像没有"

**不要辩解**。按组织者要求的方式回应：

> 「这个我需要核对一下。能否说一下具体是哪个操作、什么步骤触发的？
> 我回去对着当前版本复现，确认是没实现、还是实现有边界。」

**为什么这样答**：组织者已明确——**若认为某行为缺失，请给出功能、复现步骤、
来源提交与当前表现，再逐项核对**。整体判断"漏了很多"是站不住的。

### 当被问到不确定的数字

> 「这个数字我需要确认后答复，不在本次汇报材料里。」

**绝对不要现场估算后当成事实说出来。**

### 当被问到"能不能再加一个功能"

> 「方向记下了。当前版本的边界是……，如果要做，需要先解决……。
> 我们可以会后评估工作量。」

**不要当场承诺排期。**

### 当被追问"你们这个是不是就是调 API"

> 「数据确实来自外部接口，但项目的重点不在调接口本身，而在
> **把查询结果、用户选择和约束检查组织成一份可执行、可修改的计划**——
> 例如把班次抵达、接驳准备、景点时长、餐次休息和道路耗时连起来算可用窗口。」
