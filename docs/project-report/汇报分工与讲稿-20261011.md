# 主讲人（总讲）· 第一~第三部分

## 开场（1.5 分钟）

> 各位老师好，我们做的是「识途」，一个 AI 旅行规划智能体。
>
> 先说为什么做。自由行要同时查景点、酒店、班次、路线、餐饮和天气，信息散在多个平台。
> 更麻烦的是，用户不只要知道"有什么"，还要判断"适不适合我""能不能顺路""当天时间够不够"。
>
> 大模型能写出很像样的攻略，但**一份看起来完整的攻略，不等于一份已经核对过的行程**——
> 它可能报过期门票价，可能只写"前往"不给耗时，可能把抵达日当完整游玩日排。

## 项目简介（1 分钟）

- 面向自由行的**交互式**系统：对话理解需求 → 检索资料 → 调用真实接口 → 生成结构化行程
- 流程：确定目的地 → 比较景点 → 选住宿 → 安排交通餐饮 → 生成计划书
- **不强制走完**：住宿、城际车票、餐饮都可跳过或自行安排
- 输出：每日时间表、交通耗时、住宿餐饮、费用参考、天气、出发前待办

## 做这个项目的目的（2 分钟）

**核心问题：让 AI 旅游推荐更接近实际决策和出行准备。**

用报告里"青岛三日游"的五个问题带出来（每条一句）：
开放门票有没有依据 → 住宿到景点要多久 → 下午才到首日够不够 → 预算哪些是报价哪些是估算 → 想调整怎么保留已选。

**三层目标**：
1. **数据可信、依据可追溯**
2. **交互完整、决策可调整**
3. **计划便于执行与复核**（未核实条件保留草稿说明，**不承诺出游当天一定可行**）

## 项目展示（2 分钟）

**界面两栏**：左侧对话区（提需求、问原因、提修改）；右侧工作台（景点/酒店/交通/餐饮/天气/地图/计划书）。
另有时间轴展示当前安排、出行方式与预计耗时。

**六步流程**（每步一句，别展开）：
了解需求 → 比较景点（**每天至少两个候选**）→ 比较住宿（**选定位置即可继续**）→
安排交通（**车票飞机由用户明确选择**）→ 安排餐饮（可自行安排）→ 生成并调整计划书

**自然语言交互**（挑 3 句念）：
「想轻松一点，多推荐几个海边的景点」「返程推后一天，**保留已经选的景点**」「下午才到，帮我看看第一天会不会太赶」

## 痛点与价值（2 分钟）

讲报告 3.1 表格里最有代表性的 4 条：信息过时 / 路程没算 / 首尾日不合理 / 生成后难调整。

**3.2 对比表要念这一句**（报告自己写了，讲出来更有说服力）：
> 「通用助手接入搜索或工具后，也能获得外部数据；**识途的重点在于把这些能力组织为专门的旅行规划闭环。**」

**3.3 五条优势一句话带过**，重点落在第 5 条：**清楚表达不确定性**。

## 当前成果与边界（1.5 分钟，**这段最体现诚实**）

原型已覆盖对话、候选比较、逐晚住宿、交通餐饮、地图、时间轴、规划审核与计划书导出。

**边界逐条念**（这是加分项，不要跳）：
- 接口结果是**查询时快照**：地图资料不保证出游当天开放，列表报价不保证可售或预订成功
- 天气受预报窗口限制，超窗日期保留未知
- 游玩时长/休息/机动是**建议**，受排队、体力和路况影响
- **尚未完成围绕总预算的综合消费优化**
- 当前用 SQLite + 本地 Qdrant；**MySQL、独立 Worker 不列为本稿已实现成果**
- 有模型审核步骤与工具调整机制，但**不描述为已部署完整多 Agent 协作系统或全局最优路线**

## 收尾 + 串到第四部分（1 分钟，由主讲人讲）

> 总结一句：识途把**分散的信息查询、用户决策与行程核对**连成完整流程，价值在于让计划
> **更有依据、更容易修改，也更清楚地展示尚需确认的条件**。

# 汇报人一 · 数据与知识服务（4.1）

**开场一句话定位**（必须点出"链路的第一环"）：

> 我负责这条链路的第一环：**模型用于规划的信息从哪里来、来源和上下文怎么保证可追溯**。

## 1. 数据来源与查询封装（2 分钟）

四类来源：
- **高德地图**：地点搜索、坐标详情、车站机场候选、道路方案与耗时
- **和风天气**：实际覆盖日期的预报与当前预警；**查询失败与没有预警分别处理**
- **途牛 MCP**：酒店、房型、门票、火车、机票；**保留报价条件和查询来源**
- **官方知识资料**：`data/knowledge/*.json`，含介绍、适用范围、来源

**两条硬规则**（重点强调）：
1. 地点进入推荐前**必须核对到可用坐标**；无法定位、匹配不明确、或仅为辅助设施
   （停车场、售票处、入口）的结果，**不直接作为正常游玩候选**
2. 未入库地区或指定景点**明确提示数据缺失，不用模型自行补造**

**供应商封装**还负责参数校验、结果格式、缓存与调用计量。
途牛多账号按可用状态轮换，每个账号保留独立的间隔、额度和冷却记录。
**要补一句**：减少等待**不等于**保证单次接口更快。

## 2. MCP：标准化工具接口（2 分钟）

MCP 提供连接工具和数据的统一协议。识途把本地数据能力注册为工具，
业务层按名称和参数调用，**降低查询逻辑与规划逻辑的耦合**。

八个本地工具（对着报告 4.1.2 的表讲，不用全念）：

| 工具 | 来源 |
| --- | --- |
| `search_places` / `get_place_details` / `search_transport_places` / `calculate_route` | 高德 |
| `get_spot_candidates` | 覆盖目录 + 高德定位 |
| `daily_weather` | 和风 |
| `retrieve_guides` / `knowledge_status` | RAG / 本地索引 |

**两个容易被问的点，主动说明**：
1. **途牛工具通过供应商服务封装调用，不能把火车机票查询说成来自高德**——来源要如实
2. 模型的业务动作与本地 MCP 工具**分属不同层**：例如"查询住宿"会组织供应商查询、
   位置匹配和候选保存，不是一个工具调用就完事

**为什么这样组织**：便于独立测试、统一处理来源和错误、新增工具不必改写整个对话流程——
但**仍需要为新工具补充业务适配与验证**。

## 3. Qdrant、BGE 与 RAG（3 分钟）

**组件**：Qdrant 存向量做相似度查询；**BGE（`BAAI/bge-small-zh-v1.5`）**把中文转
**512 维**向量，通过 FastEmbed + ONNX Runtime **本地运行**。

**索引构建四步**：读知识 JSON 并检查来源城市版本 → 拆**父块/子块**
（子块召回、父块保留上下文）→ 子块生成向量写入 Qdrant → 发布 `manifest` 索引清单。

**在线检索四步**：按城市日期实体筛选 → **BM25 关键词召回 + Qdrant 语义召回（双路）**
→ **RRF 倒数排名融合**、按父块聚合控制长度 → 交给模型（命中片段 + 父块上下文 + 来源 + 适用状态）。

**当前规模**：**116 条原始记录、125 个父块、350 个子块、512 维**。
（⚠️ 报告正文此处写"90条原始记录、181个子块"，已过时，需改）

**降级策略**：没有初始化、索引过期或向量服务异常时，**明确降级为 BM25**，
**不把旧向量结果冒充最新检索**。

**选型依据**（照报告讲，注意哪句是"不宣称"）：
- RAG 降低无依据生成的风险，**但不能保证完全消除幻觉**
- Qdrant 支持本地持久化也可配置服务端；**不宣称经过与 Chroma 的系统性性能比较**
- BGE 本地中文向量，减少额外 API 依赖；初次下载和硬件维护仍有成本
- 父子块兼顾召回精度与上下文完整性

**收束**：数据模块提供带来源、适用范围和未知状态的**事实输入**，供后续 Agent 理解与规划使用。

**串场到汇报人二**：
> 「数据已经准备好了，但用户一句话怎么变成可执行的动作？请汇报人二讲 Agent 与业务系统。」

# 汇报人二 · Agent 与业务系统（4.2）

**开场定位**：

> 我负责链路的第二环：**自然语言请求怎么变成可执行动作，系统怎样保存状态并展示结果**。

## 1. FastAPI：后端服务与任务接口（1.5 分钟）

核心入口 `/api/workspaces/{wid}/actions`，处理聊天、查询、选择和规划。

四点：
- 请求校验后创建任务，浏览器通过 **SSE** 接收进度和分段回复
- 工作区操作有**互斥与版本检查**，避免并发修改覆盖已有选择
- 支持任务状态、取消、失败提示和恢复入口；**按用户隔离访问**
- 可并行处理独立的外部查询，但**仍受供应商间隔、额度和网络时延约束**

**选型理由 + 一句限定**：异步有助于减少可并行请求的串行等待，
**不意味着每次规划都能立即完成**。

## 2. LangGraph：理解、校验、执行（2 分钟）

（对着图 4 讲）主节点就是 `understand → check → execute`。

- **理解**：结合本轮消息、旅行条件和已有选择，返回结构化意图与动作
- **校验**：检查动作和输出是否可用；**不合格输出有限修复，避免无限重试**
- **执行**：业务代码调查询或保存，**校验真实候选 ID、日期与修改权限**

**图 4 的注释要念**（防被问）：
> 「景点、住宿、交通等是**执行层的业务动作**，不分别等同于图中的独立节点。」

**决定权分级**（报告原话）：解释、查询、保存用户指定选择和自动代选具有**不同的决定权**；
需要代选时**先申请用户确认**，不把一次查询等同于授权重新选择整趟旅行。

**和存储的分工**：LangGraph 负责组织执行流程；**跨轮次状态由工作区和存储模块保存**，两者配合。

## 3. DeepSeek：理解与建议生成（1 分钟）

- 用于**意图理解、推荐理由、游玩时长与安排建议、回复与审核**
- **业务不依靠模型记忆确认票价、路线或当天开放情况**
- 模型返回的是**动作提案或规划建议**，程序负责执行与校验
- 回复支持流式显示，任务过程通过 SSE 更新；**外部查询仍可能需要等待**

**选型表述要谨慎**：主要考虑中文交互、结构化工具调用和原型接入成本；
**本稿不作未测量的模型能力排名或实时价格比较**。

## 4. SQLite：工作区与任务状态（1 分钟）

保存账号、工作区、任务与查询计量。每个工作区保留需求、景点、逐晚酒店、班次、餐饮、
计划书和相关状态，**支持回来继续规划和版本恢复**。

**两句限定**：
- 适合当前单机原型；**不等同于已完成 MySQL 或独立 Worker 升级**
- **正在使用的数据库需要一致性备份，不能只复制主文件就假定所有写入均已保存**

## 5. 原生 HTML/CSS/JS：交互界面（1.5 分钟）

**先说清**：当前仍是原生，**尚未迁移 Vue**。

- `index.html` 组织页面与弹窗；`account.js` 处理账号与旅行列表
- `app.js` 基础交互；`workbench.js` / `details.js` / `experience.js` 扩展工作台、详情与时间轴
- `interactive-map.js` 处理地图；样式分布在 `style.css` / `workspace.css` / `product.css`

**这段报告写得很好，要照念**：
> 「早期原生方案便于直接接入后端和快速验证。随着功能增加，全局状态和渲染函数耦合
> 也成为维护成本；**因此不将"完全不需要复杂状态管理"作为优势**。」

**收束**：业务系统把用户请求、模型提案、工具结果和持久化状态连接起来，
提供**可操作、可恢复**的旅行工作台。

**串场到汇报人三**：
> 「动作能执行了、状态能保存了。那这些候选和选择怎么变成合理的每日安排？请汇报人三讲推荐与行程规划。」

# 汇报人三 · 推荐与行程规划（4.3）

**开场定位**：

> 我负责链路的第三环：**取得候选和用户选择后，怎样形成比较合理、可调整的每日安排**。

## 1. 推荐依据与候选数量（1.5 分钟）

**推荐依据**：明确偏好、天数、同行需求、地点范围与位置、有效日期的天气。
模型可估计体验范围与合理停留时长；**开放、费用和道路信息仍以提供的资料为依据**。

**候选机制**：每批最多 **4 个**查询，不足时继续获取，直到达到本轮目标或资料耗尽。
**模型排名只影响顺序，不应因只给一个排名就删除其他有效候选。**

**两句主动澄清**（报告里写了，讲了能少被追问）：
1. **无偏好推荐目前主要参考城市代表景点资料和地图评分，
   不是已实现实时景点热度榜** ← 这句很重要
2. 父景区与已选子地点通过明确关系处理，避免重复推荐、重复占用时间

## 2. 时间轴、道路与休息（2 分钟）

（对着图 5 讲）每日安排要同时考虑五件事：

1. **首尾日窗口**：班次抵达、出站接驳、候车或值机准备；**未知时间不会按零处理**
2. **活动时长**：景点规模、游览范围、拍照慢行、同行体力，**不统一套固定分钟数**
3. **实际道路**：住宿↔景点、景点↔餐厅、活动之间及住宿返回
4. **餐次与休息**：午餐、午休、短暂休息和机动**分别计算**，
   **不能通过删除休息掩盖时间不足**
5. **用户固定选择**：明确日期、时段、顺序和班次优先保留，**无法满足时说明具体冲突**

**住宿的细节**：按夜晚选择，**早晨和当晚可能对应不同酒店**。
选定位置**不代表已经确认房型或入住时刻**。

## 3. 工具调整与冲突分级（1.5 分钟）

用户说"放慢节奏""重新分配""调整时间轴"时，助手可调用 `adjust_timeline`，
调整未固定日期、活动顺序、合理游玩时长和餐次休息建议。
**修改后再核对路线和固定条件，已有景点、酒店、餐厅及班次选择不能被随意替换。**

**冲突分两级**（这是设计亮点）：
- **普通负担不均、稍晚或可调整的** → 优先提供可用安排
- **严重影响固定班次、日期或可用窗口的** → 明确指出日期、相关地点与原因，并提供修改入口

**要强调**：警告与阻止分开处理，**不把"还有空闲时间"当作必须填满的错误**。

## 4. 程序检查与模型审核（1 分钟）

规划先由**程序**检查候选身份、日期、重复安排和时间衔接，
再由**模型**审核是否遗漏用户要求、混淆事实与建议，或仍有明显风险。

**两句限定**：
- 审核步骤承担独立角色，但**仍属于当前业务调用流程，不宣称已运行完整的多 Agent 团队**
- **模型审核失败时保留程序检查结果并提示人工复核，不将失败当成"审核通过"**

## 5. 计划书输出与费用口径（1 分钟）

计划书由结构化日程、选择状态、费用参考、天气和来源组成，前端展示与 Markdown 导出使用这些结果。

四条口径（照念）：
- 道路展示交通方式、预计耗时、距离与已有费用参考，**不展开逐段导航**
- **酒店起价、餐厅人均、单人票价和整段费用明确区分；费用未知不写成零**
- **选定酒店、车票和景点仅用于规划，不等同于下单、出票或预约成功**
- 计划作为**可继续完善的草稿**，保留出发前待办与需再次核实的条件

**收束**：行程规划的关键是让**模型的建议与真实数据、用户决定和程序校验共同作用**，
形成更容易使用和修改的旅行计划书。
