# 识途 · AI 旅行规划智能体

## 让 AI 查着真实数据做规划

---

## 为什么做这个

自由行要同时查：景点 · 酒店 · 班次 · 路线 · 餐饮 · 天气

信息散在四五个平台，用户还要判断——

- **适不适合我**：带老人、想慢节奏，推荐应该不一样
- **能不能顺路**：地图上看着近，实际要两小时
- **当天够不够**：下午三点才到，第一天还能排几个景点？

---

## 只靠大模型回答，会怎样

| 问题 | 表现 |
|---|---|
| 信息过时 | 景点已闭园，模型不知道 |
| 价格没依据 | 门票价来自几年前的训练数据 |
| 路程没算 | 写"前往下一站"，不说怎么去、要多久 |
| 预算糊涂账 | 分不清哪些查过、哪些估的、哪些没数据 |

**一份看起来完整的攻略，不等于一份已经核对过的行程。**

---

## 识途是什么

把 **查资料 → 做选择 → 排行程 → 核对约束** 连成闭环的旅行规划系统

```
确定目的地 → 比较景点 → 选择住宿 → 安排交通 → 安排餐饮 → 生成计划书
```

- 每一步都有真实数据支撑
- 每一步都可以跳过、替换、自行安排
- 车票机票始终由用户自己确认

![用户规划流程](项目汇报配图-20261009/01-用户规划流程.png)

---

## 三个目标

**1 · 数据可信、依据可追溯**
官方资料 + 实时接口，每条信息保留来源与查询时间

**2 · 交互完整、决策可调整**
分步引导比较选择，自然语言修改，保留已选内容

**3 · 计划便于执行与复核**
每日时间表、道路耗时、费用口径、出发前待办

---

## 怎么用

浏览器打开即用

- **左侧对话区** —— 提需求、问原因、提修改
- **右侧工作台** —— 景点 · 酒店 · 交通 · 餐饮 · 天气 · 地图 · 计划书
- **时间轴** —— 当前安排、出行方式、预计耗时

直接说需求，不用记命令：

> 「返程推后一天，保留已选的景点」
> 「下午才到，帮我看看第一天会不会太赶」
> 「不吃海鲜，比较一下其他餐厅」

## 技术架构

![技术架构](项目汇报配图-20261009/02-技术架构.png)

理解 → 校验 → 执行：模型提出动作，程序校验后才执行

- **MCP 工具**：高德（地点/路线）· 和风（天气）· 途牛（酒店/票务）
- **RAG 检索**：官方资料 + BM25 + 语义向量 + RRF 融合
- **SQLite**：工作区状态、版本检查、并发保护

## 汇报分工

围绕**同一条链路**，三人各讲一环：

| 汇报人 | 这一环 | 回答的问题 |
|---|---|---|
| 汇报人一 | 数据与知识服务 | 信息从哪来，来源怎么保证可追溯 |
| 汇报人二 | Agent 与业务系统 | 一句话怎么变成动作，状态怎么保存展示 |
| 汇报人三 | 推荐与行程规划 | 候选和选择怎么变成合理的每日安排 |

## 我们主动说明的边界

- 接口结果是**查询时快照**，不保证出游当天开放或可售
- 天气只覆盖预报窗口内的日期
- 费用分**已有报价 / 参考估算 / 待核实**三档，未知不写成零
- 当前用 SQLite + 本地向量库；MySQL、独立 Worker 是后续方向，**当前没做**
- 是主流程 + 工具调整 + 模型审核，**不是多 Agent 协作系统**
- 不保证全局最优路线，做的是约束核对与局部调整

---

## 总结

识途让旅行计划——

**更有依据 · 更容易修改 · 更清楚展示尚需确认的条件**

不把估算包装成保证，不把未知写成零。
