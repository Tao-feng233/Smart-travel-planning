## 一、我的角色

### 一句话定位

**我是这条链路的第二环：把用户的一句话，变成系统里真正被执行的动作，并把状态存住、把结果展示出来。**

```
第一环（汇报人一）        第二环（我）              第三环（汇报人三）
信息从哪来          →   怎么变成动作、怎么存、怎么展示  →  怎么排成每日行程
```

### 我具体负责什么

| 我负责 | 边界（不属于我） |
|---|---|
| 后端服务与任务接口 | MCP 工具与供应商封装（协调者） |
| Agent 意图理解的执行流程编排 | 向量库、RAG 检索（汇报人一） |
| 工作区状态持久化、版本与并发控制 | 排程算法、冲突检查（汇报人三） |
| 公共存储与任务契约（我牵头设计） | 高德/和风/途牛接口本身 |
| 前端展示层与交互 | 景点推荐排序策略 |

### 我和另两人的接口

- 汇报人一给我：**带来源的事实输入**（地点、道路、天气、资料片段）
- 我给汇报人三：**用户已确认的选择 + 状态** + 一个可复用的执行上下文
- 我给前端：**进度、分段回复、结构化结果**

## 三、逐技术讲深（每个技术回答五个问题）

### ① FastAPI —— 为什么是它

**概念**：Python 的异步 Web 框架。所谓"异步"，是指一个请求在**等外部接口返回**时，
线程不傻等，可以转去处理别的请求。

**我用它做了什么**：对外只开一个核心入口 `/api/workspaces/{wid}/actions`，
聊天、查景点、选酒店、生成计划全走它；顺带做鉴权、版本校验和前端资源挂载。

**为什么不用别的**：

| 候选 | 不选的原因 |
|---|---|
| Flask | 同步为主，一次规划要并发查景点/路线/天气/酒店，同步会串行等待 |
| Django | 自带 ORM、后台管理那一整套，我们只要一个轻接口层，太重 |
| 直接用 uvicorn 手写 | 路由、参数校验、自动生成接口文档都要自己写 |

**优势**：原生异步（适合我们大量并发外部查询）；自带请求校验与接口文档，协作时不用另写文档。

**局限（主动说）**：异步能减少**可并行请求**的串行等待，
**不等于每次规划都能立刻完成**——供应商响应慢，整体就得等。

---

### ② SSE —— 为什么不用 WebSocket

**概念**：Server-Sent Events，服务端向浏览器**单向、持续**推送文本流。
建立在普通 HTTP 上，浏览器原生 `EventSource` 就能收。

**我用它做了什么**：任务一提交，浏览器就持续收到"正在查景点…"、
模型分段吐出的回复、最终结果——用户不用盯着空白页等。

**为什么不用别的**：

| 候选 | 不选的原因 |
|---|---|
| WebSocket | 双向通道。我们只有"服务端→浏览器"一个方向，双向是用不上的复杂度；且要独立握手协议、代理穿透更麻烦 |
| 前端轮询 | 每隔一秒问一次，延迟和无效请求都高，还容易把接口打满 |
| 一次性返回 | 规划动辄几十秒，用户会以为卡死 |

**优势**：基于 HTTP，不用额外协议和端口；断线后浏览器自带重连；单向正好匹配我们的场景。

**局限**：只能服务端推、不能客户端推（客户端要发指令仍走普通 POST，这正好是我们要的分工）。

---

### ③ LangGraph —— 为什么画成"图"

**概念**：把一次处理拆成**节点**（干什么）和**边**（下一步去哪），
流程被显式画出来，而不是散在一堆 if-else 里。

**我的设计**（`app/agents/planner.py:113-126`）：

```
START → understand → check → execute → END
                      │
                      └──(不合格)→ 回到 understand 重来一次
```

| 节点 | 职责 |
|---|---|
| understand | 结合本轮消息 + 旅行条件 + 已有选择，返回结构化意图 |
| check | 检查模型给的动作是否可用；**不合格就带着具体意见回退重来一次** |
| execute | 校验真实候选 ID、日期、权限后，才真正执行 |

**为什么不用别的**：

| 候选 | 不选的原因 |
|---|---|
| 自己写 if-else 状态机 | 分支和回环会散落在代码各处，出问题分不清"是理解错了还是执行错了" |
| 一次性让模型做完 | 模型输出不可控，没法在中间插校验 |
| 线性流水线 | 没法表达"不合格退回重来"这个回环 |

**优势（这才是选它的真正理由）**：**可追踪、可定位**。
每个节点输入输出清晰，出问题能直接判断是"意图理解错"还是"业务执行错"。

**局限（必须说）**：图里只有三个节点。
**景点、住宿、交通是执行层的业务动作，不等于图里的独立节点**——这句要主动澄清，否则会被误认为只有三个功能。

---

### ④ DeepSeek + Function Calling —— 为什么让模型"给动作"而不是"给答案"

**概念**：Function Calling 让模型不直接回答，而是**按约定格式返回一个"要做什么"的结构**
（动作名 + 参数），由程序去执行。

**我怎么设计的**：

1. 先定义**动作契约**（`app/agents/intent_contract.py`）——28 种动作，每种带清晰描述，例如
   `review_timeline` 是"只读检查"、`adjust_timeline` 是"实际修改"、`plan` 是首次生成
2. 模型只返回**动作提案**
3. **程序负责校验和执行**：ID 是否真实存在、日期是否合法、这次修改是否被授权

**为什么这样设计**：这是整个系统最核心的一条原则——
**模型提案，程序把关。** 业务**不依靠模型记忆**确认票价、路线或当天开放情况。

**为什么不用别的**：

| 候选 | 说明 |
|---|---|
| 其他大模型 | 我们选它主要看**中文交互、结构化工具调用能力、原型接入成本**；**本稿不做未测量的模型能力排名**，没测过就不能比较 |
| 让模型直接输出自然语言再由程序解析 | 格式不稳定，一改提示词就崩；结构化输出有 schema 约束 |

**决定权分级（这是我的设计亮点）**：
解释、查询、保存用户明确选择、**自动代选**——四者决定权不同。
需要代选时**必须先申请确认**（`app/agents/auto_selection.py`），
**不会把"帮我查一下"当成"授权重排整趟旅行"**。

---

### ⑤ 工作区状态 + revision —— 我怎么解决"改着改着就乱了"

**问题**：旅行规划是**多轮**的。用户今天选了景点，明天来说"返程推后一天"。
同时如果两个人（或两个标签页）同时改，后提交的会覆盖先提交的。

**我的设计——两层保护**：

| 层 | 机制 | 代码位置 |
|---|---|---|
| 互斥 | 同一工作区有任务在跑时，拒绝新的修改 | `app/api/workspaces.py:86` |
| 乐观并发 | 请求必须带上版本号 `revision`，对不上直接 409 | `app/api/workspaces.py:89` |

**为什么叫"乐观"并发**：不提前加锁阻塞，而是提交时校验版本；
冲突了就明确拒绝（"旅行已更新，请刷新后重试"），**不静默覆盖**。

**优势**：用户已选内容不会被意外冲掉；支持回来继续规划；版本可追溯。

**局限（诚实）**：当前任务是在**进程内**用 `asyncio.create_task` 跑（`app/application/jobs.py:34`），
**不是独立 Worker**——进程重启，运行中的任务不保留。MySQL 和独立 Worker 是后续方向，**当前没做**。

### ⑥ Repository 契约 —— 我为什么先写接口

**背景**：三个人都要碰存储。各写一份，最后一定对不上。

**我的做法**（`app/core/contracts.py`，281 行）：先把**语义**定死，再让三个人照着开发。

| 契约 | 定死了什么 |
|---|---|
| `WorkspaceRepository` | 按 owner 读取；**按 expected_revision 保存，冲突不能静默覆盖** |
| `JobRepository` | 幂等提交、互斥领取、租约、取消、完成/失败 |
| `CacheRepository` | 参数键、过期时间、查询结果 |
| `ProviderBudgetRepository` | 供应商调用额度**原子**申请与检查 |
| `KnowledgeRepository` | 原文/父块、doc_id、版本、来源、城市、适用时间 |
| `DateField` | 日期区分**用户输入 / 班次事实 / 系统建议** |

**为什么先写接口而不是先写代码**：
这是**面向接口编程**——先约定"该长什么样"，实现可以后补、可替换、可单独测试。

**关键取舍（要讲）**：这一批我**只交接口和测试夹具**——
**不启用 MySQL、不迁移任何数据**。目的是先统一语义，不是换存储。
配套 `tests/test_contracts.py` **20 项通过**，现场可跑。

**被采纳的记录**：`docs/collaboration/分支整合复核与待修事项-20261009.md:9`
写明"采用成员二最新版"。

### ⑦ SQLite —— 为什么不用 MySQL

**概念**：整个数据库就是一个文件，不需要装数据库服务。

**为什么选**：

- 原型阶段**部署成本近乎为零**，clone 下来就能跑
- 用户隔离、事务、版本检查由**业务代码**实现，不依赖数据库特性

**为什么不是 MySQL**：**MySQL 和独立 Worker 属于后续扩展方向，当前没有做**——
这是明确写在边界里的，**不能把"计划要做"说成"已经做了"**。

**一个技术细节（体现真懂）**：正在使用的 SQLite 需要**一致性备份**，
不能只复制主库文件就假定所有写入都已落盘。

---

### ⑧ 原生前端分层 —— 为什么不用 Vue

**概念**：不用 React/Vue，直接写 HTML/CSS/JS，但**按职责拆四层**：

| 层 | 内容 |
|---|---|
| `core/` | 账号、接口、全局状态 |
| `components/` | 地图、时间轴、工作台、候选详情 |
| `views/` | 候选、消息、计划书、工作台渲染 |
| `styles/` | 基础 / 产品 / 工作台样式 |

**为什么不用 Vue（标准答法，照念）**：
> 早期原生方案便于直接接入后端和快速验证。随着功能增加，
> 全局状态和渲染函数耦合也成为维护成本；
> **因此不将"完全不需要复杂状态管理"作为优势**。后续可按实际需要组件化。

**别辩解**：不要说"原生更好"或"我们不需要状态管理"——这是报告自己否掉的说法。

## 四、我做的三个设计决策（体现"我怎么设计的"）

### 决策 1：让模型"提案"，程序"把关"

**问题**：模型会编。直接信它，就会把不存在的景点写进计划。

**我的设计**：模型只输出动作提案；执行前**校验真实候选 ID、日期、修改权限**；
校验不过就带着具体反馈退回重来**一次**（不无限重试）。

**代价**：多一次模型调用、多几十毫秒。**收益**：不会出现"计划里有个查无此地的景点"。

### 决定 2：把决定权分级

**问题**：用户说"其余你帮我安排"，系统到底能替他决定到什么程度？

**我的设计**：解释 / 查询 / 保存明确选择 / **自动代选** 四档，权限递增；
到"代选"这一档**必须先申请确认**，用户可撤销。

**为什么**：把一次查询当成授权重排整趟旅行，是我们明确避免的。

### 决策 3：先定契约，再写代码

**问题**：三人并行开发，存储与任务接口各写一份必然对不上。

**我的设计**：先出接口 + 测试夹具，接口不改业务、不换存储，
让三个人按同一份语义开发。

**代价**：前期看起来"没产出功能"。**收益**：后期合并没有接口对不上的返工。
