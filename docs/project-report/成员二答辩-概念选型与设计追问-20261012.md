# 成员二 · 答辩预测问题与应答

> 老师考察的是：**技术概念是否真懂、选型有没有比较过、设计有没有自己的判断、
> 遇到异常怎么办、你在团队里到底做了什么**。
> 本稿按这九个维度组织，每题给【答什么】【别说】——后者是最容易踩的坑。
>
> **D / E / F / H 四组完全不涉及代码**，是答辩最容易被追问、也最容易拉开差距的部分。

**通用原则**：不知道就说不知道，说清"当前未实现/未验证"，**不要现场编**。

---

## A. 概念题（考你懂不懂）

### A1 ★★★ 什么是 Agent？和普通聊天机器人有什么区别？

**答**：普通聊天机器人是"问一句答一句"，输出完就结束。
Agent 的区别在于它**能决定下一步做什么，并且真的去做**——
理解意图后产生一个动作（查景点、保存选择、改时间轴），执行完再根据结果继续判断。

**我们的具体形态**：模型负责"决定做什么"，程序负责"真的做、做前校验"。

**别说**：别说"Agent 就是更聪明的聊天机器人"。核心区别是**有动作、有执行、有状态**。

---

### A2 ★★★ LangGraph 是什么？为什么流程要画成"图"？

**答**：把一次处理拆成**节点**（做什么）和**边**（下一步去哪）。
主图是 `understand → check → execute`：理解意图 → 校验输出 → 执行业务。
check 不合格时会带具体反馈退回 understand 重来**一次**。

**真正理由**：**可追踪、可定位**——出问题能分清是"意图理解错了"还是"业务执行错了"。

**必补防混淆**：景点、住宿、交通是**执行层的业务动作**，不等于图中的独立节点。

**别说**：别说"因为 LangGraph 更先进"。

---

### A3 ★★★ 什么是 Function Calling？你们为什么用它？

**答**：让模型不直接回答，而是**按约定格式返回一个"要做的动作"**（动作名 + 参数），由程序执行。
我们定义了 28 种动作。

**为什么**：模型只给提案，**程序负责校验和执行**——校验真实 ID、日期、权限。
这条原则叫"**模型提案，程序把关**"。

**别说**：别说"这样模型就不会出错"。是**降低**风险，不是消除。

---

### A4 ★★ 什么是"编排"？为什么需要单独一层编排？

**答**：编排是决定"先做什么、后做什么、失败了往哪走"。
把它单独抽一层，好处是**流程变了不用改业务代码**，业务改了也不用动流程。

**类比**：业务动作是"零件"，编排是"装配线"。

---

### A5 ★★ 什么是"幂等"？为什么你们的任务要幂等提交？

**答**：同样的请求提交两次，结果只执行一次。
因为网络重试、用户连点都可能造成重复提交——不幂等就会出现"生成了两份计划"或"重复扣额度"。

---

### A6 ★★ 什么是"乐观并发"？你们的版本号怎么工作？

**答**：不提前加锁，提交时校验版本号。请求必须带 `revision`，对不上直接返回 409，
**不静默覆盖**。另外同一工作区有任务在跑时会拒绝新修改。

**别说**：别说"我们不会冲突"。是**冲突会被明确拒绝**，不是不发生。

---

### A7 ★★ SSE 是什么？和 WebSocket 有什么区别？

**答**：SSE 是服务端向浏览器**单向持续推送**，跑在普通 HTTP 上，浏览器原生支持、自带重连。
WebSocket 是**双向**通道。我们只需要"服务端→浏览器"一个方向，双向是用不上的复杂度。

---

### A8 ★★ 什么是"可观测 / 可追踪"？你们怎么体现？

**答**：一次请求走了哪个节点、调了哪些动作、在哪一步失败，都能查到。
我们把流程画成图、把任务状态与进度持久化，就是为了让**出问题时能定位，而不是靠猜**。

---

### A9 ★★ 你老说"契约"，契约到底是什么？

**答**：先定义"存储/任务该长什么样"的**接口**，再让三个人照着实现（281 行）。
定死的是**语义**：保存必须按 expected_revision、冲突不能静默覆盖；
任务要幂等提交、互斥领取；日期要区分用户输入 / 班次事实 / 系统建议。

**可验证**：`tests/test_contracts.py` 20 项通过。

---

### A10 ★ 前端你们说"分层"，分了哪几层？

**答**：`core`（账号/接口/状态）、`components`（地图、时间轴、工作台、候选详情）、
`views`（候选、消息、计划书、工作台渲染）、`styles`（基础/产品/工作台）。

---

### A11 ★★★ Qdrant 是什么？为什么用它？（成员一主答，我需了解）

**概念**：向量数据库。把文本转成向量后存进去，查询时按**语义相似度**找最接近的片段，
而不是靠关键词是否出现。

**我们怎么用**：

| 项 | 做法 |
|---|---|
| 部署 | **本地持久化模式**（`QdrantClient(path=...)`），也可配 `QDRANT_URL` 连服务端 |
| 索引 | **按"世代"版本化**，索引完成后**原子发布**，避免建到一半被读到 |
| 集合名 | `shitu_guides_<generation>` |
| 向量模型 | `BAAI/bge-small-zh-v1.5`，**512 维**，通过 FastEmbed 本地运行 |
| 规模 | 116 条记录 / 125 父块 / 350 子块 / 20 城市 |

**为什么选它**：支持本地持久化，**原型部署不用额外起服务**；
同时保留配置服务端连接的能力，给后续扩展留空间。

**为什么不用别的**（只讲事实，不做排名）：

| 候选 | 说明 |
|---|---|
| 直接用云向量服务 | 要多一个外部依赖和密钥，原型阶段没必要 |
| 自己用数组算相似度 | 数据量一大就扛不住，也没有持久化与过滤能力 |

**别说**：**不要说"Qdrant 性能最好"**——我们**没有做过与 Chroma 等的系统性性能比较**，
不知道就答"没做过横向压测"。

**降级机制要主动说**：索引没就绪、过期或向量服务异常时，
**明确降级为 BM25**，并在结果里标注"语义检索降级"——**不把旧向量冒充最新检索**。

**⚠️ 演示前必查**：本机当前 `dense_index_ready=False`（向量索引未构建），
**现场演示前必须跑一次索引构建**，否则检索只有 BM25 一路，被问到会很被动。

### A12 ★★ Chroma 和 Qdrant 有什么区别？为什么是 Qdrant？（成员一主答，我需了解）

| 维度 | Chroma | Qdrant |
|---|---|---|
| 定位 | 轻量嵌入式，主打 Python 快速上手 | 面向检索场景的向量引擎，核心用 Rust 实现 |
| 部署 | pip 装完就用，本地文件 / 内存 | **本地持久化模式** + 服务端模式（可连远程） |
| 过滤 | 元数据过滤能力较弱 | 原生支持 payload 过滤与索引（我们要按**城市 / 日期 / 实体**筛） |
| 客户端 | 以 Python 为主 | 多语言 + REST / gRPC |

**我们选 Qdrant 的理由**（只讲事实）：
① 本地持久化，**原型不用额外起服务**；② 保留配置服务端连接的能力，**后续能平滑扩展**；
③ 需要按城市、日期、实体做过滤。

**别说**：**不要说"Qdrant 比 Chroma 快 / 性能更好"**——
我们**没有做过系统性性能比较**。被追问就答："没做过横向压测，选型看的是部署方式和过滤能力。"

## B. 选型题（考你有没有比较过）

### B1 ★★★ 后端为什么用 FastAPI，不用 Flask 或 Django？

**答**：一次规划要**并发**查景点、路线、天气、酒店，FastAPI 原生异步，
等待外部接口时不阻塞别的请求。Django 自带 ORM 和后台整套，我们只要轻接口层。

**必补限定**：异步减少的是**可并行请求的串行等待**，
**不等于每次规划都能立刻完成**——供应商慢，整体就得等。

---

### B2 ★★★ 为什么前端不用 Vue / React？

**答（照念，最有说服力）**：

> 早期原生方案便于直接接入后端和快速验证。随着功能增加，全局状态和渲染函数耦合
> 也成为维护成本；**因此不将"完全不需要复杂状态管理"作为优势**。后续可按实际需要组件化。

**别说**：别辩解"原生更好"——这是报告自己否掉的说法。

---

### B3 ★★★ 为什么选 DeepSeek？和其他模型比过吗？

**答**：主要考虑**中文交互、结构化工具调用能力、原型接入成本**。

**必补限定**：**本稿不做未测量的模型能力排名或实时价格比较**——我们没做过横向评测。

**别说**：别去比各家跑分，一比就被追问"你测过吗"。

---

### B4 ★★★ 为什么用 SQLite 不用 MySQL？两者到底差在哪？

**先讲清区别**（这块最容易被追问）：

| 维度 | SQLite | MySQL |
|---|---|---|
| 形态 | **嵌入式**，整个库就是一个文件 | 独立**服务进程**，客户端/服务器架构 |
| 部署 | 零部署，随应用启动 | 要装服务、建库、建账号、配权限 |
| 并发写 | **库级锁，单写者** | 行级锁，写并发能力强 |
| 访问方式 | 仅本机文件访问 | 支持远程连接、多应用共享 |
| 账号权限 | 无内置，靠应用层实现 | 内置账号与权限体系 |
| 适用 | 单机、嵌入式、原型 | 多用户、服务端、生产 |

**我们选 SQLite 的理由**：原型阶段部署成本近乎为零；
用户隔离、事务、版本检查都由**业务代码**实现，不依赖数据库特性。

**代价要主动说**：写并发受**库级锁**限制，撑不了多用户高并发。
**MySQL 和独立 Worker 是后续扩展方向，当前没有做**——这写在边界里。

**一个能体现真懂的细节**：项目开了 **WAL 模式**（`app/persistence/storage.py:55`），
所以**正在使用的库不能只复制主库文件**——WAL 文件里可能还有未合并的写入，
只拷 `.db` 会丢数据。要做**一致性备份**。

---

### B5 ★★ 为什么任务不用独立 Worker / 消息队列？

**答**：当前任务在**进程内**异步执行，单机原型够用。
独立 Worker 需要额外的进程、租约、崩溃恢复机制，属于后续扩展。

**代价要主动说**：**进程重启，运行中的任务不保留**。

---

### B6 ★★ 为什么状态不用 Redis？

**答**：我们需要的是**可追溯、可恢复**的旅行状态（需求、逐晚酒店、班次、计划书），
不是高频临时缓存；SQLite 单文件即可持久化，也不引入额外服务。
查询结果缓存另有一层（契约里约定了参数键与过期时间）。

---

### B7 ★★ 为什么不做 App / 小程序？

**答**：本项目目标是**验证规划闭环是否成立**，不是做分发渠道。
Web 端迭代最快、无需审核与安装，适合原型验证。移动端适配不在本期范围。

---

### B8 ★ 为什么不用现成的 Agent 平台（低代码编排）来搭？

**答**：那些平台适合快速搭流程，但我们的难点恰恰在**业务约束**——
真实 ID 校验、决定权分级、日期三种来源、逐晚住宿。这些必须落在自己的业务代码里，
用平台反而要绕开它的抽象。

## C. 设计题（考你有没有自己的判断）

### C1 ★★★ "模型提案、程序把关"具体怎么落地？

**答**：模型返回"把某景点加入第二天"。程序校验：ID 是否真在候选里、
日期是否在行程范围内、这个修改是否被授权。不通过就带**具体反馈**退回一次，**不无限重试**。

**追问"为什么不重试到底"**：无限重试会死循环，也会掩盖真实的业务冲突——
重试一次仍不合格就如实告诉用户。

---

### C2 ★★★ 为什么不直接让模型生成整份行程计划书？

**答**：因为模型**不掌握实时事实**，也不知道用户到底确认了什么。
让它直接写，看起来完整，但里面的票价、耗时、开放状态可能都是编的。

**我们的分工**：模型负责"组织与建议"，程序负责"取数、校验、排程"。
**这也是我们和"直接问大模型要攻略"最本质的区别。**

---

### C3 ★★★ 为什么规划要分六步引导，而不是一次生成？

**答**：因为选择权应该在用户手上。一次性生成，用户只能全盘接受或全盘推翻；
分步引导让用户**每一步都能比较、替换、跳过**。

**另一个理由**：规划中途会出现信息缺口（比如还没定住宿），
分步能在缺口出现时就问，而不是到最后才发现排不出来。

---

### C4 ★★★ 你们怎么处理"用户让系统自己安排"？会不会乱选？

**答**：把**决定权分成四档**：解释 / 查询 / 保存用户明确选择 / **自动代选**，权限递增。
到代选这一档**必须先申请确认**，用户可撤销。

**设计理由**：**把一次查询当成授权重排整趟旅行，是我们明确避免的**。
另外**车票机票始终由用户自己确认**——涉及付费和不可逆操作，不代选。

---

### C5 ★★ 为什么系统不自动挑最便宜的酒店和班次？

**答**：因为"最便宜"不等于"合适"。位置、时间、退改条件都要权衡，
而这些是用户的个人偏好，系统不该替他决定。
我们做的是**把口径清楚的候选摆出来**（起价、人均、耗时），让用户自己判断。

---

### C6 ★★ 多人同时改同一个旅行会怎样？

**答**：两层保护。第一层**互斥**：有任务在跑时拒绝新修改；
第二层**乐观并发**：提交必须带版本号，对不上返回 409 让用户刷新，不覆盖。

---

### C7 ★★ 你为什么先写契约再写代码？这不是拖慢进度吗？

**答**：三个人都要碰存储，各写一份最后必然对不上、合并要返工。
先出接口 + 测试夹具，**不改业务、不换存储**，让大家按同一份语义并行开发。

**关键取舍**：那一批我**只交接口**，**不启用 MySQL、不迁移数据**。
看起来前期"没功能"，收益是后期没有接口对不上的返工。

---

### C8 ★★ 日期为什么区分"用户说的 / 班次事实 / 系统建议"？

**答**：因为"游玩结束次日返程"这种**推断**不能当成用户已确认的事实来用。
三种来源分开保存后，未确认的返程保持"建议"或"未知"，
**不会被后续修改无依据覆盖**——否则用户改了景点，返程日期会跟着悄悄变。

---

### C9 ★★ 执行失败或不合���会无限重试吗？

**答**：不会。check 节点不合格时带具体反馈退回 understand **一次**，
再不行就如实上报，不做无意义循环。

---

### C10 ★★★ 你的项目"算法"在哪？如果再加算法，你会加什么？

**先别答"我们没用算法"**——项目里已经有：

| 算法 | 用在哪 |
|---|---|
| **BM25**（词频-逆文档频率） | 关键词召回 |
| **RRF**（倒数排名融合） | 两路召回结果合并 |
| 向量相似度 + ANN | 语义召回 |
| 时间窗排程（贪心 + 约束） | 每日时间表 |
| 试排（按 5 分钟单位缩短弹性游览） | 返程日安排 |

**如果要再加，我优先加这个**：**带时间窗的路线顺序优化**。

**为什么是它**：景点之间的道路耗时**系统里已经查到了**，数据现成；
用**最近邻贪心 + 2-opt 局部搜索**就能做，落地成本低；
效果可以**直接量化**（能报出"省了多少分钟路上时间"）。

**必须说清的两点**：① 它是**启发式，不保证最优**；
② 一天只有 2-4 个景点时，启发式结果通常已接近最优，所以性价比高。

**另外两个方向**（按优先级）：
- **预算约束下的组合选择（背包问题）**——正好补上我们边界里承认的
  "尚未完成围绕总预算的综合消费优化"；难点是**价值函数怎么定义**
- **候选排序的可解释打分模型**——把"为什么这个排前面"变成可解释的加权公式，
  契合我们"依据可追溯"的定位

**归属提醒**：排程与冲突修复是成员三的地盘，**加算法前必须先对齐**，
不要两边各写一套时间窗求解。检索侧（BM25 / RRF / 向量）属成员一。

**别说**：别把"用了大模型"说成算法贡献；也别宣称新算法"一定更优"——
**没有做对比实验就不能下结论**。

## D. 产品与价值题（不涉及代码，最容易被追问）

### D1 ★★★ 你们项目的创新点到底是什么？

**答**：不在"用了某个模型"，而在**把查询、决策、核对组织成闭环**，具体三条：

1. **有依据**：每条信息带来源与查询时间，计划里分"已有报价 / 参考估算 / 待核实"
2. **能改**：多轮修改保留已选内容，改完重新核对约束
3. **敢说不知道**：未知不写成零，估算不包装成保证

**别说**：别说"我们用了 RAG 所以不会幻觉"。

---

### D2 ★★★ 和携程、马蜂窝这类产品有什么区别？

**答**：它们解决的是**"订"**——比价、库存、下单。
我们解决的是**"排"**——把选好的东西排成一份时间上站得住的行程，并说明依据。

**定位差异**：我们不提供预订，输出的是**可继续完善的计划书草稿**。
所以两者不是替代关系，我们是"下单之前那一段"。

---

### D3 ★★★ 如果大模型以后自己就集成了这些工具，你们还有价值吗？

**答**：那对我们反而是好事，说明方向对。但差异不在"能查数据"，而在三点：

- **约束核对**：把班次、道路、餐次、休息、开放时间连起来算可用窗口
- **选择状态管理**：多轮修改保留已选内容
- **不确定性的表达规范**：事实 / 建议 / 未知分开

这些是**规划流程的设计**，不是模型能力。

---

### D4 ★★ 你们解决的最核心的痛点是什么？

**答**：一句话——**一份看起来完整的攻略，不等于一份已经核对过的行程**。
具体表现为信息过时、路程没算、首尾日不合理、预算口径不清、生成后难调整。

---

### D5 ★★ 这个项目有商业化可能吗？做过评估吗？

**答**：**没有做过商业化评估，这是原型项目**。
如果要往前走，最先要解决的是数据覆盖（当前 20 个城市）和预订链路的合规问题。

**别说**：别现场编商业模式和营收数字。

---

### D6 ★★ 你们做过用户调研吗？怎么确定这些痛点是真的？

**答**：**没有做过正式的用户调研**。痛点是团队基于自由行的亲身经历
与公开资料整理出来的，属于**观察与假设**，不是量化结论。
这也是项目的局限之一——如果要做下去，这是必须补的一步。

**诚实加分**：主动承认没做，比现场编一份问卷更有说服力。

---

### D7 ★★ 如果用户根本不按你设计的六步走，怎么办？

**答**：六步是**引导，不是强制**。用户可以随时跳过、直接问别的问题、
或者只完成一部分就生成计划。行程里没定的部分会保留为"待核实"或"自行安排"。
**不会因为没有走完就卡住。**

## E. 场景与异常题（不涉及代码，考你有没有想过失败情况）

### E1 ★★★ 如果所有外部接口都挂了，系统怎么办？

**答**：**明确降级，不假装成功**。查不到天气就说"本次暂未取得天气数据，
其他步骤可以继续"；查不到餐厅就保留餐饮偏好，提示可稍后单独查询。

**原则**：**不把"查不到"当"零"或"没有"**，也不让某一步的失败拖垮整次规划。

---

### E2 ★★★ 模型返回了不存在的景点怎么办？

**答**：执行前会校验这个 ID 是否真在候选里。不在就不执行，
带具体反馈退回一次；仍不合格就如实告诉用户，不会把编造的地点写进计划。

---

### E3 ★★ 用户说"随便""你看着办"，系统会怎么处理？

**答**：先问方向（海滨 / 人文 / 自然 / 亲子 / 慢节奏）；
用户明确表示没偏好，也可以直接看代表景点。
但**涉及自动代选时必须先申请确认**，不会静默替他决定。

---

### E4 ★★ 用户生成计划到一半改主意了，会怎样？

**答**：分两种情况。任务还在跑：同一工作区有任务在跑时会拒绝新修改，
避免状态写乱；也可以**先取消任务**再改。已经生成完：可以直接用自然语言改，
改完系统会**重新核对**道路、日期和固定条件，已选内容保留。

---

### E5 ★★ 用户关掉页面或断网了，之前的规划还在吗？

**答**：状态是**持久化**的，重新打开可以接着规划。
但如果**进程重启**，正在运行的任务不保留——这是当前实现的边界。

---

### E6 ★★ 某个城市数据不全，会硬排吗？

**答**：不会。**宁可少给，也不编造**。
未入库地区会明确提示数据缺失，不用模型自行补造。
这也是为什么某些城市候选偏少——**不是没数据，是没通过核实**。

---

### E7 ★★ 用户预算不够怎么办？

**答**：系统会展示"已有费用参考 vs 您填的预算"的对比，并明确列出待核实项。
但要说明的是：**围绕总预算的综合消费优化尚未完成**——
我们做的是"把口径说清楚"，不是"帮你压到预算内"。

---

### E8 ★★ 两个用户的数据会串吗？

**答**：按用户隔离，每个用户只能访问自己的旅行工作区；任务流也按 owner 校验。
密钥只保存在服务端配置里，**不下发到浏览器**。

## H. 压力追问链（老师会顺着你的答案往下追）

### H1 你说"模型提案、程序把关"→ 那把关就一定拦得住吗？

**答**：**不能保证拦住所有问题**。我们拦的是**可枚举的、确定性的错误**：
ID 是否存在、日期是否合法、是否被授权。
模型**理解层面的偏差**（比如误解了用户的隐含偏好）程序拦不住，
所以我们另外有一步模型审核做复核，并在计划书里保留待办提示。
**这些都是降低风险，不是消除风险。**

---

### H2 你说"不静默覆盖"→ 那用户遇到 409 不会觉得难用吗？

**答**：会，这是**权衡**。我们选的是"宁可让用户刷新一次，也不能悄悄改掉他的选择"。
旅行规划里的选择往往来自反复比较，被静默覆盖的代价远大于一次刷新。
**更好的做法应该是自动合并差异**——**当前没做，属于已知不足。**

---

### H3 你说"不做模型排名"→ 那你们到底凭什么选的？

**答**：凭的是**可验证的三个条件**：中文交互效果、结构化工具调用是否稳定、
接入成本（是否 OpenAI 兼容、是否方便原型接入）。
这三条我们**实际用过**，所以能说。
至于各家模型的跑分、性价比，**我们没测过，不做比较**。

---

### H4 你说"没做用户调研"→ 那你怎么知道用户需要？

**答**：严格说，**我们不知道，只是假设**。
这是项目局限，也是如果要继续做下去必须先补的一步。
我们现在能做的是**把假设摊开、把边界写清楚**，让评审可以检验我们的推理是否成立。

这些是**流程与约束的设计**，不是某个框架自带的。

### I3 "你这个功能好像没有 / 和报告说的不一样"

### I4 被问到不确定的数字

**答**：「这个数字我需要确认后答复，不在本次汇报材料里。」
**绝不现场估算后当事实说。**

### I5 被问"能不能再加个功能"

**答**：「方向记下了。当前版本的边界是……如果要做，需要先解决……我们可以会后评估工作量。」
**不当场承诺排期。**

### I6 被问"你们踩过什么坑"（加分题，讲真事）

后来我们要求**先核对真实数据再写判断条件**。
**这题的价值是说明我们靠复现和验证发现问题，不是靠猜。**

③ **契约更早冻结**，我出契约时业务已经在并行写，有一段时间两边在追。

**答**：**功能完成度可以给到"闭环跑通"，但工程成熟度还差得远**——

任务没有独立 Worker。这些我都写在边界里，不回避。
**主动列不足，比自夸更可信。**

## J. 数据准确性专项（高频必问）

### J1 ★★★ 检索出来的数据，怎么保证是准确的？

**答**：不是靠"检索"这一步，而是靠**四道防线**：

| 防线 | 做什么 |
|---|---|
| ① 来源可控（入库前） | 只用官方知识资料与接口返回，每条保留来源名、查询时间、适用范围 |
| ② 进推荐前核实（最硬） | 地点**必须核对到可用坐标**，核不到就"暂不列入推荐"；名称须与地图登记名一致 |
| ③ 检索策略 | BM25 关键词 + 向量语义**双路召回** + RRF 融合；父子块：子块提精度、父块保上下文 |
| ④ 表达规范 | 事实 / 建议 / 未知**三档分开**，未知不写成零，查不到就明确降级 |

**最能讲的一句**（第②道）：还有一层辅助设施黑名单——
停车场、售票处、出入口、公共厕所、"XX门"**都不作为游玩候选**。
所以**有些城市景点只有几个，不是没数据，是没通过核实**。

**必须同时说的边界**：RAG **降低**无依据生成的风险，**不能保证消除幻觉**；
接口结果是**查询时快照**，不保证出游当天开放或可售；**20 个城市**是最大边界。

**归属提醒**：①③主要是成员一的活，**我负责的是第④层和"执行前校验真实 ID"**——
说"我们整套四道防线"，不要全揽成自己的。

---

### J2 ★★ 检索不到或检索错了，会怎样？

**答**：**明确降级，不假装成功**。
向量索引没就绪、过期或服务异常时，**降级为 BM25，不把旧向量结果冒充最新检索**；
检索参数不合法（如日期无效）直接返回失败原因，**不静默返回空结果**。
查不到就说"未取得"，并提示可稍后单独查询。

---

### J3 ★★ 会不会把停车场、售票处当成景点推荐？

**答**：不会。这类名称在进推荐前就被过滤（停车场、售票处/售票点、出入口、公共厕所、"XX门"），
它们**只是辅助设施，不是游玩对象**。

---

### J4 ★★ 做了这些，是不是就不会出错了？

**答**：**不是**。我们拦的是**可枚举的确定性问题**：坐标是否存在、
ID 是否真实、日期是否合法、是否被授权。
拦不住的是**理解层面的偏差**（比如误解用户隐含的偏好），
也拦不住**数据本身的时效**——官方资料也可能过期。
所以计划书里保留了"出发前待办"，把需要再确认的事项明确列给用户。
**这些都是降低风险，不是消除风险。**

---

## K. 业务与商业化题（老师常问，最容易冷场）

> **总原则**：这个项目是**原型**，没做商业化评估、没做用户调研、没做成本核算。
> 每道题的答法都是：**先给基于项目事实的合理分析，再明确标注"这部分我们没有验证过"**。
> 主动标注比被追问出来好，也显得你知道边界在哪。

### K1 ★★★ 你们的目标用户到底是谁？

**答**：**自由行、且行程有一定复杂度**的人——多日、多地点、有同行约束
（带老人、带小孩、想慢节奏）。

**为什么是这类人**：行程越复杂，**约束越多**（开放时间、道路耗时、首尾日窗口、
同行人体力），出错的代价也越大——而这正是通用 AI 最容易出错的地方
（实测 16 项中 2 项硬错、4 项偏乐观，全部落在政策细节与附加费用上）。

**注意**：不要说"OTA 不帮你排"——**OTA 已经有 AI 行程助手了**，这个说法不成立
（详见 K2）。

**诚实补充**：**我们没有做过正式的用户画像与调研**，这是基于观察与假设。

---

### K2 ★★★ 携程已经有 AI 行程助手了，你们凭什么？（必问，且我原来说错了）

**先纠正一个错误说法**：**不能再说"OTA 只管订、我们才管排"**——
携程、同程、飞猪、马蜂窝都已经有 AI 行程规划 Agent 了，这个分工**已经不成立**，
这么说会被当场指出。

**我们真正测过的是什么**（诚实边界）：
项目里有一份《识途_竞品实测报告》（2026-09-23），实测的是 **2 家通用 AI 平台**，
16 项数字核对。**没有实测过 OTA 的 Agent**。
所以：**不能说"我们比携程的 Agent 准"**——没测过就不能下结论。

**通用 AI 的实测结果**（这部分有数据，可以讲）：

| 结果 | 数字 |
|---|---|
| 准确 | 9 项（含票价、时刻，分毫不差） |
| **硬错** | **2 项**（观光车 10 元 vs 官网 30 元；老人票 60+ 免票 vs 实际 65+） |
| 偏乐观/口径混乱 | 4 项（同一回答里"地铁 50 分钟"与"地铁 2 分钟"并存） |
| 计划状态 | 一轮对话输出 **4 套互相冲突的方案** |
| 来源 | 无逐条可核验来源（只写"官网"） |

**结论是"大体准、细节错"**——而错的全落在**政策细节与附加费用**上，恰是预算的关键输入。

**那差异还能怎么讲？讲设计取向，不讲能力高低**：

| 维度 | OTA 的 Agent | 识途的取向 |
|---|---|---|
| 推荐立场 | 服务于**自家库存**（推荐自己能订的） | **不绑库存**，可以推没合作的店（但也因此离交易更远、变现更难） |
| 确定性表达 | 为促转化，倾向把结果说确定 | **事实 / 建议 / 未知三档分开**，未知不写成零 |
| 计划状态 | — | **单一计划 + 版本号 + 局部修改**，改一处不乱全篇 |
| 可核验 | — | 每条带来源与查询时间；通勤统一口径**可复算** |

**30 秒说法（照念）**：
> 对，OTA 确实已经有 AI 行程助手了，所以"我们做排、OTA 做订"这个说法不成立。
> 我们实测过的是通用 AI——它大体准但细节会错，观光车价格错了三倍，
> 一轮对话还会给出四套互相冲突的方案。
> 识途的差异不在"更聪明"，而在三点取向：**不绑库存的中立推荐、
> 把不确定摊开说、单一计划可局部修改**。
> **至于和 OTA 的 Agent 谁更好，我们没做过对比评测，不下结论。**

**别说**：别说"我们比携程准""OTA 做不了排"——**都没测过，也都不是事实**。

### K4 ★★★ 携程已经做了同样的事，你们这个项目还有什么意义？

**答**：诚实说，**我们也没有能力和巨头比数据与流量**。但分两层讲：

**第一层，需求被验证是好事**——巨头都做了，说明"AI 行程规划"这个需求是真的，
我们不是在做伪需求。

**第二层，作为原型项目，我们的目标不是抢市场**——
我们验证的是**这套流程设计是否成立**：约束核对、选择保留、不确定性表达规范，
能不能真的改善规划质量。这个问题验证清楚了，才有谈竞争的资格。

**诚实补充**：**我们没有做过与 OTA Agent 的对比评测**，所以不能下"谁更好"的结论。

**别说**：别说"我们更懂用户""我们更灵活"——**没有数据支撑的空话最容易被追穿**。
但这类产品有个现实：**行程编排是低毛利、重体验、要处理大量例外的工作**，
未必是巨头愿意投入资源的重点。

**更实在的答法**：作为原型，我们验证的是**这套流程设计是否成立**——
约束核对、选择保留、不确定性表达规范是否真的能改善规划质量。
这个问题验证清楚了，才有谈竞争的资格。

### K5 ★★ 只有 20 个城市，商业上根本不可行吧？

### K6 ★★ 一次规划的成本是多少？算过吗？

### K7 ★★ 数据从哪来？商用合规吗？

**答**：三类来源——公开地图/天气 API、合作方票务接口、

### K8 ★★ 用户数据隐私怎么处理的？

**答**：做了基本的隔离——每个用户只能访问自己的旅行工作区，
密钥只存在服务端配置里，**不下发到浏览器**。

**诚实补充**：**没有做过隐私合规审计**，也没有做数据最小化、留存期限这些设计。
如果要对外提供服务，这是必须补的一步。

### K9 ★★ 你们的核心壁垒是什么？别人容易抄吗？

**答**：**说实话，目前没有强壁垒**——数据和技术都可复制，框架也都是开源的。
如果真要做下去，壁垒只会来自三处慢慢积累的东西：
**数据覆盖广度**、**行程编排质量**、**用户已积累的行程与偏好数据**。

**主动说"没有壁垒"是可信的**，硬编一个护城河反而站不住。

### K10 ★★ AI 给的行程，用户真的敢信吗？

**答**：这正是我们花力气做**"事实 / 建议 / 未知三档分离"**和
**"出发前待办"**的原因。
我们的思路是：**不伪装成确定，反而更容易建立信任**——
把哪些是查实的、哪些是估的、哪些还要再确认，全部摊开给用户。

**反面做法**：如果为了显得"专业"而把估算说成确定，用户出一次错就不会再信。

### K11 ★ 你们为什么不直接做预订？不做预订怎么变现？

**答**：预订涉及**支付、库存、退改规则、经营资质**，不是原型阶段能覆盖的；
而且我们想先把"**排得对**"这件最难的事做扎实，再谈交易。

**代价要承认**：不做预订，就离交易远，**变现路径更长**——这是这个定位的固有代价。
