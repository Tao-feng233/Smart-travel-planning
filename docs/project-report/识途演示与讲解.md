## 一、开场（30 秒，可直接念）

> 识途是一个自由行旅行规划 Agent：用户用自然语言说需求，系统在右侧工作台上一步步比较景点、住宿房型、往返班次、餐饮，最后生成一份**带来源、标明待确认事项**的旅行计划书。
> 我们的出发点是行业调研里反复出现的三个痛点：信息散在多个平台、方案改一次要重查一遍、以及"看起来很确定"的推荐其实没有依据。所以识途的原则是**对话负责意图，程序负责事实**——模型只做判断和表达，所有数字都来自真实接口并保留来源。

## 二、三人分工与实现（对照分工表，逐条讲）

### 我 · Agent 编排与规划生成

| 分工表要求 | 实现位置 | 实际做法 |
| --- | --- | --- |
| LangGraph + DeepSeek Function Calling 实现意图识别与业务编排 | `app/agent.py` | `StateGraph`：`understand → execute` 两节点主链 |
| 提取目的地、日期、预算、人数及偏好 | `app/agent.py` 的 `submit_intent` 工具 schema | 一次 Function Calling 返回 `{action, patch, answer, …}`；`patch` 只做**增量**更新 |
| 根据意图调用查询或选择功能 | `app/agent.py::handle` | 20+ 个受控动作，白名单式分发（`chat/search_spots/complete_hotel/train/flight/ticket/plan/…`） |
| 维护多轮对话中的需求和已选状态 | `app/storage.py` + 工作区 JSON | 每次动作后落库并 `revision+1`；`journey.refine_intent` 保护日期等不可被误改的字段 |
| 生成每日行程提案 | `app/planning.py::_generate` + `app/proposals.py` | 模型只输出候选分组 JSON；程序校验 ID/日期/时长，**最多一次带具体错误的修复** |
| 支持用户修改条件后重新规划 | `app/agent.py::update_requirements` | 改日期/人数→住宿与班次置 stale 并清选择；改城市→整库清空；受影响计划置 `stale` |
| 负责重构与整体集成 | 本次整合提交 | 见第六节"复核与整合记录" |

**讲解要点（回答"模型到底管什么"）**：
- 模型输出的是**动作 + 参数**，不是行程事实。例：`{"action":"search_spots","patch":{"city":"青岛"},"keywords":["人文","美食"]}`。
- 程序校验：候选 ID 必须在已选集合内、每个 ID 恰好出现一次、日期必须在游玩日期内、时长 30–240 分钟；不合法就带错误信息让模型修一次，第二次失败直接报错，**不会静默编一份行程**。
- 长行程：支持 1–60 个游玩日，模型每轮最多处理 16 个已选地点，逐段限定日期与 ID 并核对遗漏/重复（`CONTEXT.md` 中的运行边界）。

### 成员二 · 多源数据与工具服务

| 分工表要求 | 实现位置 | 实际做法 |
| --- | --- | --- |
| 接入高德、途牛 MCP、和风天气 | `app/mcp_server.py`（本地 stdio MCP）+ `app/providers.py`（途牛 Streamable HTTP） | 本地工具 4 个：`search_places`、`get_place_details`、`calculate_route`、`daily_weather`、`retrieve_guides` |
| 封装景点、餐饮、酒店房型、交通班次、天气及路线查询 | `app/discovery.py`、`app/foods.py`、`app/planning.py` | 景点：多关键词并发查询 + 去重（停车场/售票处/出入口/门类过滤）；路线：`walking/transit/driving` 三选一 |
| 统一不同供应商字段、单位、价格口径和来源信息 | `app/providers.py` | 每个候选统一带 `source{name,url,queried_at,kind}`；价格一律标口径（如"单人席别参考票价""指定日期列表起价"） |
| 实现缓存、请求限制、超时与异常处理 | `providers.py` | 高德缓存 TTL 900s、路线 300s、天气 900s、途牛 600s；途牛全局锁 + **40 次/日**预算 + **13 秒**最小间隔 + 45s 超时；HTTP 层屏蔽 URL 日志避免泄漏 key |
| 处理资料缺失、无票、无房及接口兼容问题 | 各业务模块 | 无票班次后端阻止选入；酒店无房/名称匹配歧义标注"待核实"并跳过路线计算；任一数据源失败降级为可读提示，不阻塞其他步骤 |

**讲解要点（回答"数据可靠性怎么保证"）**：
- **接口能力核对**：`官方接口核对.md` 记录了逐条实测结论。例：途牛列车"余票 0 = 无票、null = 该席别不存在"，不能混用；没有总库存就不算"剩余百分比"。
- **限额是真实约束**：途牛开放平台为免费额度，官方限制是 **5 RPM / 50 RPD 且所有 apikey 共享**，项目自己再收紧到 40/日；这是"为什么一次行程只查必要数据"的原因。
- **图片链路**：高德/途牛的图片 CDN 存在 http 源，服务端 CSP 需要显式放行；前端优先取同源原图，失败回退缩略图且不放大。

### 成员三 · 知识检索与规划校验

| 分工表要求 | 实现位置 | 实际做法 |
| --- | --- | --- |
| 建立官方旅游资料库 | `data/knowledge/` | 33 条：青岛景区 26 条 + 青岛背景 3 条 + 目的地概览 4 条（青岛/成都/杭州/西安），均为官方页面摘要并带采集时间 |
| 实现字符 TF-IDF 检索与关键词重排 | `app/rag.py` | 字符二元组 TF-IDF + 关键词加权（`score += min(0.3, Σ0.06)`），阈值 0.035，返回 top-5 |
| 保留来源、采集时间和适用范围 | 资料字段 | 每条带 `url / fetched_at / date_scope`（概览类为 `scope`），界面上以"适用日期需核实"呈现，**不把网页快照当出游当天状态** |
| 校验景点 ID、日期、重复与遗漏 | `app/proposals.py`、`app/planning.py` | 只允许已选 ID、每个 ID 恰好一次、日期在允许集合内、时长范围校验、最多一次修复 |
| 检查到达缓冲、返程准备、用餐时长及时间冲突 | `app/schedule.py`、`app/planning.py::validate_plan` | 到达后 90 分钟缓冲、返程前 120 分钟停车、餐次完整时长；冲突以 `conflicts` 结构化输出并可在界面跳转 |
| 设计独立模型审核 | `app/planning.py` 审核段落 | 独立提示词 + 独立上下文（只给脱敏后的草稿），最多 6 条问题；审核失败降级为"请人工复核"，不阻断交付 |
| 编写回归测试并验证异常场景 | `tests/` 15 个文件 | **143 passed**：账号 24、业务 19、发现 15、交互 v6 13、数据补全 10、v11 体验 9、v8 体验 9、餐饮覆盖 5、锚点跟随 1、地图 7 等 |

**讲解要点（回答"校验怎么不是走过场"）**：
- 三处判否是**程序**做的，不靠模型自觉：① 已选 ID 与日期集合；② `schedule.windows()` 算出的可用窗口（早餐/午餐/晚餐各自窗口 + 到达/返程边界）；③ 路线耗时来自高德接口，程序据此检查衔接。
- `schedule.py` 是 v11 的关键设计：**时间轴与选餐共用同一套窗口口径**，所以不会出现"选择时能选、排程时被静默丢弃"。
- 模型审核是**第二意见**，不是唯一验收者；审核 prompt 明确要求它检查"是否把建议当事实""是否存在时间/位置风险"，并禁止补造数据。

| 步骤 | 操作 | 讲解词（要点） |

| 10 | 生成计划书 | "程序查真实路线、加缓冲、按 5/15 分钟向上取整，再让独立模型审核一遍。" |

**演示中要主动说出的三个"边界"**（比讲功能更能建立可信度）：
1. 未接入实时客流预测、自动支付/出票、跨城多住宿与完整预算；
2. 计划书里的时间是**建议值**，班次时刻与地图耗时是真实查询值，两者在界面上区分标注；
3. 途牛是免费额度（5 RPM / 50 RPD 共享），所以查询节奏被刻意控制，不是性能问题。

## 四、预期提问与答法

| 提问 | 回答要点 |
| --- | --- |
| 和直接用 ChatGPT 规划有什么区别？ | 事实来自接口：路线耗时、班次余票、房型报价、天气都有来源和查询时间；模型不编数字，缺数据就写"待核实"。 |
| 模型会不会瞎编？ | 三层约束：① 工具 schema 限定动作；② 程序校验候选 ID/日期/时长；③ 独立审核模型复核遗漏与风险。三层任何一层失败都会降级为可读提示。 |
| 为什么不用向量数据库？ | 资料量级是 33 条官方摘要，字符 TF-IDF 足够且零外部依赖；等真实检索失败率证明不够时再替换（`rag.py` 里写明了这个判断）。 |
| 为什么前端不上框架？ | 交互是"对话 + 工作台"两栏，Canvas 地图与 SSE 流式回复是核心，用原生 JS 反而少了构建链；`README` 里写明无需前端构建。 |
| 状态怎么保存？ | SQLite（账户/旅行/版本/任务/有限期缓存）；每次动作 `revision+1`，支持撤销与"旧计划需重新生成"的标记。 |
| 多用户并发怎么办？ | 每个工作区一把锁、单用户最多 2 个并发任务、全服务 4 个；超限返回 429/503 并给出可读提示。 |
| 数据合规？ | 仓库不含 `.env`、账户、行程、缓存与体验包；账户可导出数据、可注销；恢复码一次性使用；服务端不下发任何密钥。 |
| 最大的技术难点？ | 时间与约束的一致性：到达缓冲、返程准备、餐次时长、每日结束时刻，一个口径错就会"选得上、排不进"。我们把口径收敛到 `schedule.py` 一处。 |

## 六、复核与整合记录（成员三"验证异常场景"的实际产出）

以下三例都是**体验中真实暴露、定位到根因、修完用真接口回归**的，适合作"我们怎么保证质量"的例证：

1. **审核必失败**：审核投影对资料直接下标取 `date_scope`，而目的地概览类资料只有 `scope` → 命中即 `KeyError`，降级成"请人工复核"。修正为两者兼容，并补回归用例（覆盖成都/杭州/西安这类只有概览资料的城市）。
2. **景点图片全挂**：`img-src` 只放行 `https:`，而高德照片存在 `http://store.is.autonavi.com` → 浏览器按 CSP 拦截。修正为显式放行该 http 源；实测 http/https 均可加载（1080×810）。
3. **景点周边餐饮"0 候选"**：默认按"当地餐厅"这个**意图词**去高德做名称检索，景区周边经常 0 条 → 改为关键词兜底（美食/中餐厅/小吃/面馆/火锅）+ 半径放大 + 城市范围回落，并如实标注范围；同时补"取消这一餐"入口。真接口复验：0 条 → 5 家，全在龙门石窟 0.5 公里内。
4. **锚点餐次跟随**：只在"当天排不了这一餐"时跟随锚点景点，而现实更常见的是"当天排得了、但锚定景点在别的日期" → 补齐该分支，锚定景点的餐次跟随其实际排期日并在计划书说明原因。修前/修后对照：修复前餐次留在第 1 天且无提示，修复后迁到第 2 天并给出调整说明。

## 七、收尾（15 秒）

> 识途现在能跑通"需求 → 景点 → 住宿房型 → 往返交通 → 餐饮 → 计划书"的完整链路，143 项后端检查与 3 套浏览器场景通过，所有事实性字段都带来源。
> 下一步我们想做三件事：把餐饮与住宿的**局部重规划**做成不重跑全流程、把**预算**从"住宿起价参考"扩到分类合计、以及把体验包的**途牛额度**按使用人做隔离，让更多人可以独立体验。
